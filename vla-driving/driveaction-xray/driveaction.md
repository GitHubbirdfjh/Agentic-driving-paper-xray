# 从动作倒着出题：一个靠「决策树」找到 VLA 模型病灶的评测基准

> **全局编号**：59（本领域 51–60）
> **论文**：DriveAction: A Benchmark for Exploring Human-like Driving Decisions in VLA Models
> **作者**：Yuhan Hao, Zhengning Li, Lei Sun, Weilong Wang, Naixin Yi, Sheng Song, Caihong Qin, Mofan Zhou, Yifei Zhan, Peng Jia, Xianpeng Lang（Li Auto Inc.，理想汽车）
> **会议/年份**：arXiv 预印本，2025-06 初版（v2 修订至 2025-09）；正式发表 venue 未确认
> **链接**：https://arxiv.org/abs/2506.05667（全文见 https://ar5iv.org/html/2506.05667）
> **数据**：公开，HuggingFace `LiAuto-DriveAction/drive-action`；**代码**：论文未声明官方仓库，未确认
> **一句话核心洞见**：传统基准顺着感知→决策的正向链条出题，DriveAction 反过来——先把驾驶员真实做出的高层动作钉死，再由这个动作反推出它依赖哪些视觉和语言子任务，把一道"开车"大题拆成一棵可以逐层定位病灶的问答树，让"动作答对了但感知是蒙的"和"感知全对但决策错了"这两种失败不再混在一起。

## 现有基准到底在哪个具体场景下测不准？

先把作者在引言里真正想解决的三个麻烦说清楚。注意这不是文献综述复述，而是三个能具体描述出来的失败场景。

第一个麻烦是**场景的来源太窄**。NuScenesQA、DriveMLLM 这类基准，数据都派生自 nuScenes 这样的开源数据集。开源数据集当年是为 3D 感知任务采集的，采集路线、城市、天气就那么多。于是评测里大量题目是"这张图里有几辆车"这种目标级感知题，而真实驾驶里最要命的场景——高速上并线、施工区绕行、和电动车行人抢路口——在这些数据里本来就没几段。作者的判断是：这不是调参能救的，是数据源头决定的结构性缺失。你想测"像人一样开车"，题库里却连"人"常遇到的难场景都没有。

第二个麻烦更隐蔽：**动作标签是事后补的，决策那一刻的意图已经丢了**。BDD-X、DRAMA 是让标注员看完录像再写解释；DriveLM、DriveBench 的动作标注也是事后手工标的。想象一个具体场景：一段录像里车从中间车道并到了左车道。事后看录像的标注员只能写下"车辆向左变道"，但司机当时到底是因为前方施工被迫变道，还是为了超一辆慢车主动变道，录像里看不出来，标注员只能猜。更糟的是，标注员看到的是结果，看到的是"车确实过去了"，于是天然倾向于把这次操作标成"合理的"。而司机当时可能是犹豫的、甚至是误操作。事后标注把"意图"这个最关键的信息弄丢了，剩下的只是一个看起来合理的动作描述。作者押的第一个赌注就在这里：**动作标签必须来自驾驶员操作的那一刻，而不是事后看录像的人**。

第三个麻烦是**评测的逻辑方向**。Reason2Drive 用 chain，DriveLM 用 graph，都是从感知出发、正向走到规划和动作。这套正向逻辑测不出来两种关键失败：一种是感知全对但决策错了（比如认出了施工区，却选择了不绕行），另一种是感知错了但决策蒙对了（比如没看清车道线，但选项里"保持直行"恰好是正确答案）。正向链条把这两类失败混在一个总分里，你只知道模型得了 85 分，不知道它到底是眼睛不行还是脑子不行。作者的第二个赌注是：**评测应该从最终动作倒着推**——先确定这个动作要做对需要哪些信息，再去测这些信息对应的视觉和语言能力。

这三个麻烦合起来，就是 DriveAction 的起点。它的底牌是数据：理想汽车量产车上真实用户主动采集的驾驶数据，覆盖中国 148 座城市，2610 个驾驶场景，16185 道问答题。一家车企能拿出这种量级的有动作标签的真实驾驶数据，这是学术界实验室很难复制的资源。论文通篇的底气几乎都来自这一张牌。

## 148 座城市、量产车用户主动采集：这张底牌有多硬？

先说数据是怎么来的。DriveAction 的场景来自理想量产车上"内部测试用户"（internal test users）在使用高阶智驾功能时主动采集的真实驾驶记录。注意这个措辞：摘要里写的是 users / drivers of autonomous vehicles，正文 3.1 写的是 internal test users of production-level autonomous vehicles。这两者有微妙的差别，我在怀疑式审读那节会展开。

数据经过多轮人工筛选和质控，最后留下 2610 个场景，每个场景配若干道问答题，共 16185 道。论文把场景分成七类（Table 2）：上下匝道、主辅路切换、导航变道、效率变道（超慢车、躲静止车、施工/拥堵）、绕行弱势交通参与者（行人、自行车）、路口（左转右转直行掉头停车减速等）、普通路段巡航。每一类都配了代表性的高层动作，比如效率变道的动作就是向左/向右变道，绕行 VRU 是向左/向右绕行，路口那一类动作最多，有十来种。

这套分类本身就值得停一下。传统的端到端数据集（比如 nuScenes）是按"采集"组织的：一段 20 秒的录像，里面发生什么算什么，绝大多数时间就是直行。DriveAction 是按"决策类型"组织的：它先定义了人类驾驶员会做的那几类关键决策，再去数据里找这些决策发生的片段。这意味着**简单直行的样本被有意压低了，复杂决策的样本被有意抬高了**。论文引言里点名批评了现有基准里直行样本主导、复杂行为覆盖不足的问题，这个分类法就是它的回答。

标签的可靠性靠三轮人工核验兜底：误操作（比如误触加速或方向盘）、与交通环境矛盾的行为（无障碍物急停）、违反交规的行为（压实线变道）都会被剔除。这个过滤步骤很关键，因为"来自真实操作"不等于"都是好操作"。真实驾驶员也会犯错，基准要的是"人类偏好"，不是"人类失误大全"。

但这张底牌也有它的边界，我先把判断放在这里，论证放在后面的怀疑式审读：第一，internal test users 到底是谁？如果是理想内部员工或深度测试用户，他们的驾驶风格、使用智驾的熟练度，和普通车主不一样，所谓的"人类偏好"可能偏向某一类人群。第二，148 座城市全在中国，交通标志样式、路权习惯、加塞文化都是中国特色，模型在这个基准上测出的"像人"，换到欧洲或美国未必成立。第三，数据来自"使用智驾功能时的用户操作"——用户在智驾开启时接管或干预的那一刻，本身就是一个经过筛选的时刻（通常是系统处理不好的难场景），这反而可能是好事：难场景天然富集。但论文没有量化这个筛选效应。

## 「高层离散动作」到底是什么形状？一次变道在标签里长什么样？

这是全篇最容易被一带而过、但其实是承重设计的一节。DriveAction 的动作标签是**离散的高层动作**，不是连续轨迹。论文 3.2 说得很直白：这样做是为了匹配端到端大模型的输出粒度，也更符合人类驾驶决策的类别本质。

什么叫"类别本质"？想象你在开车，前面有施工，你决定变道。这个决定在你脑子里不是一条每 100 毫秒一个点的轨迹，而是一个离散的念头："往左变道"。轨迹是执行层的事，决策层的事就是"变不变、往哪变"。DriveAction 只记录决策层：在变道场景里，标签就是 lane change left 或 lane change right；在路口场景里，标签是 left / right / straight / U-turn / stop / decelerate 等等；在普通路段，标签就是 keep（保持）。

论文还特意解释了为什么不用稠密轨迹：在变道场景里，传统做法是记录高频采样的整条轨迹，但大模型的决策频率本来就低（VLM 推理一次要几百毫秒到几秒），让它去拟合 10Hz 的轨迹点既不公平也不合理。记录"关键点上的决定"——变不变、往哪变——才是和大模型能力对齐的评测粒度。

这个设计有一个直接的推论：**DriveAction 测的是"决策像不像人"，不是"开得稳不稳"**。一条变道轨迹是画得圆润还是生硬，在这个基准里根本没有分数。这对读者的课题是个重要的分界线，后面"与本课题的关联"会细说。

现在说怀疑。离散化是有代价的。两个司机都选了 lane change left，一个切得果断利落，一个犹豫蹭线，标签一模一样。"人类偏好"被压平成几个离散选项之后，基准能分辨的只是"选 A 还是选 B"，分辨不了"同样是选 A，谁更像老司机"。论文把这称为"反映人类驾驶决策的类别本质"，这个说法只对了一半：决策的"选哪个"确实是类别的，但"怎么执行"也是偏好的一部分，而后者在离散化里被扔掉了。对于 VLA 模型评测的当下阶段，这个取舍是合理的——现在的 VLM 连"该不该变道"都经常答错，确实还没到比拼"变道姿态优不优雅"的时候。但读者要清楚这个天花板在哪里：当未来的模型在 DriveAction 上都拿到 95 分以上时，这个基准就测不出差别了，因为它能测的东西已经被离散化限定死了。

## 树状评测：一次导航变道是怎么被拆成三道题的？

这是论文的第二个赌注，也是它和 DriveLM 的 graph、Reason2Drive 的 chain 真正拉开差距的地方。先看结构：评测框架是一棵三层的树，顶层是动作节点（action），中间是语言任务（language），底层是视觉任务（vision）。一共 14 个独立任务：7 个视觉任务，7 个语言任务。

14 个任务的名字值得完整列出来，因为它们就是这棵树的全部"零件"（附录 B.1）：视觉层是 Navigation Position（自车在道路结构中的定位，比如当前车道及车道方向）、Efficient Route Detection（本车道和相邻车道在当前交通下的可通行性）、Dynamic Object Detection（动态障碍物的位置类型运动）、Static Object Detection（静态障碍物）、Road Marking Detection（车道线、斑马线、停止线、箭头）、Traffic Light Detection（信号灯的数量类型方向）、Traffic Sign Detection（标志内容和位置）；语言层是每个检测任务对应的"理解"版本：Navigation Following（是否在导航推荐车道、有没有错过机动的风险）、Efficient Route Following（路况对本车决策和通行效率的影响）、Avoid Dynamic Collision（动态障碍物是否构成安全风险）、Avoid Static Collision、Road Marking Following（标线对本车行为的影响）、Traffic Light Following（灯态对通行的意义）、Traffic Sign Following（标志是否需要影响本车行为）。

注意这个命名规律：视觉层都是 Detection（看见了什么），语言层都是 Following / Avoid（这意味着什么、该怎么理解）。这不是随便起的名字，它对应了 VLA 链条里的两个不同认知阶段：先看见，再理解，最后决策。

现在拿一个具体场景走一遍。场景：导航提示前方 83 米右转，前方两条车道，左车道只能左转，右车道直行加右转，导航要求使用最右侧车道。驾驶员的真实操作是向右变道。

这棵树会为这个场景生成三道题，共享同一个 question_slice_id（附录 A 的数据结构里，每个 slice 可以对应多道相关题目）：

第一道是动作题（顶层）："当前场景下车辆应该采取什么动作？A：保持当前车道直行；B：向左变道进入左转车道；C：向右变道进入直行加右转车道；D：原地停车。"答案是 C。这道题直接对标驾驶员的真实操作。

第二道是语言题（中间层）："83 米后导航提示右转，前方车道属性左起为左转、直行+右转，要求使用最右侧车道。从最右侧车道右转是否被允许？A：允许右转；B：只允许直行……"答案是 A。这道题测的是模型对导航指令和车道规则的理解。

第三道是视觉题（底层）："你当前车道的车道属性是什么？A：直行+右转；B：左转……"答案是 B。这道题测的是最基础的车道感知。

三道题的关系是依赖倒置的：动作题要答对，理论上需要语言题和视觉题的信息；但评测时三道题是独立打分的。于是四种组合就有了诊断价值：三道全对，说明链条是通的；动作对了但视觉错了（附录 Table 12 里真实出现了这种例子），说明模型是蒙对的，感知有病灶；视觉和语言都对了但动作错了（附录 Table 13 的效率任务例子），说明决策层自己有问题。

论文特别强调了一句容易滑过去的话：评测框架是"从动作往下"的依赖树，但模型推理时依然走常规的 V→L→A 顺序。换句话说，**这棵树是出题的逻辑，不是推理的逻辑**。作者没有要求模型按树的顺序倒着推理，只是用这棵树来决定"为这个动作，我该出哪些 V/L 的题"。这个区分很重要：如果误以为模型要倒着推理，会觉得这个设计很别扭；理解了它是出题框架，就通了。

出题本身是怎么做的？附录 B.2 交代了：所有题目的候选先由 LLM 按两阶段 prompt 生成——第一阶段 LLM 结合场景的关键属性写一份结构化的场景报告，判断哪些环境因素会影响自车行为；第二阶段基于这份报告生成针对性的问答对；然后人工筛选有效性。这个流程里藏着一个后面要审的问题：LLM 出的题，会不会考的更多是"读题能力"而不是"驾驶能力"。

## 场景信息三件套：三帧连拍、导航指令、车速，少了哪样会出什么事？

每个评测 prompt 里，模型会拿到三样场景信息（3.3.2）：决策前连续三帧图像、车载导航系统的直接指令、自车和目标车的速度。

三帧连拍是给时序推理用的：单张图看不出前车是在加速还是减速，三帧连起来，动态才有意义。导航指令直接从车机取，提供路线目标、 upcoming 转弯和目标车道信息。车速最有意思：论文明确说"这个动态信息无法从图像单独推断"，在变道、超车、加速决策里是必需的。

Figure 4 给了一个干净的对照实验来说明导航信息为什么是承重的：同一个路口前变道场景，给导航指令（前方右转）时模型能提前选对变道动作；拿掉导航指令，模型经常做出和真实驾驶目标不一致的"幻觉"决策。想想为什么：没有导航目标，"该变哪条道"这个问题本身就是欠定的——变左变右都"合理"，模型只能瞎猜。这说明**导航指令不是锦上添花，它是把决策问题变成良定义的**。一个评测基准如果不给导航信息就考变道决策，考的其实是模型的猜测运气，不是驾驶能力。

附录里效率任务的例子把车速的作用讲得更具体：一道题里当前车速 8.61 km/h、理想车速 30.0 km/h，问两者差异的最佳解释。选项包括"前方无车道路畅通""下坡需减速""前方有车导致实际车速低于理想""隧道限速"。正确答案是前方有车。这道题不给车速数字就没法出——图像里能看出"有车"，但看不出"8.61 vs 30"这个差距。车速把一道纯视觉题变成了一道需要融合数字信息的推理题。

但这里也有一个评测设计上的微妙之处：导航指令和车速是**直接以文本形式喂给模型的**，不是让模型自己从图像里读出来的。这意味着 DriveAction 测的不是"模型能不能从仪表盘图像里读出车速"，而是"给了车速之后模型会不会用"。这是一个有意的设计选择——把"信息提取"和"信息使用"分开。但它也带来一个捷径风险：如果题目文本里已经把关键信息都写清楚了（比如导航题干里直接写了"前方两条车道，左起属性为……"），那么视觉题可能退化成阅读理解题。附录 Table 7 的 Navigation Position 例题，题干里已经把车道属性全文写出来了，再问"当前车道属性是什么"，模型不看图也能答对。论文没有量化有多少题目存在这种"题干泄漏"，这是后面怀疑式审读要记的一笔。

## 四种评测模式：V-L-A、V-A、L-A、A，各自在隔离什么？

全面评测（comprehensive evaluation）有四种模式，这是论文实验部分的核心设计，也是 3.3% / 4.1% / 8.0% 这组数字的来源。把四种模式的定义说准：

- **V-L-A（全管线模式）**：把上游视觉和语言任务的 QA 对作为已知信息喂给模型，再让它做动作决策。测的是"在信息全给足的情况下，决策能做多好"。
- **V-A（纯视觉模式）**：只给视觉任务的 QA 对，不给语言层的高层理解信息。测动作决策对视觉感知的依赖。
- **L-A（纯语言模式）**：只给语言任务的 QA 对。测对语言理解的依赖。
- **A（无信息模式）**：什么上游 QA 都不给，只给基本场景和任务要求。测模型纯靠内部知识和推理能做到什么程度。

这里有一个必须点破的设计实质：V-L-A 模式**不是端到端测试**。它没有让模型自己去做感知，而是把标准答案级别的上游信息直接喂进去，问的是"假设眼睛和理解都完美，你的决策行不行"。这测的是决策模块的能力上限。反过来，A 模式测的是模型在信息真空里的先验和常识。四种模式的差值，刻画的是模型对外部信息的依赖程度。

这个设计很聪明，但也有代价，我把它拆成两面说。好的一面：它把"感知不行"和"决策不行"彻底解耦了。如果一个模型在 V-L-A 下 93 分、在 A 下 84 分，你知道它的决策模块本身是好的，差的那 9 分是感知和理解没跟上。坏的一面：V-L-A 的分数是一个**乐观上界**，真实部署时模型拿不到标准答案级别的上游信息。论文摘要里"需要 vision 和 language 双重引导"的结论，严格说应该读成"在给定完美上游信息时比不给高 8%"，而不是"模型自己能把 V-L-A 跑通"。论文正文没有犯这个错误，但读者如果只看摘要，容易把上界当成常态。

现在看数字。12 个 VLM（7 个非推理模型：GPT-4o、GPT-4o mini、GPT-4.1、GPT-4.1 mini、Claude 3.5 Sonnet、Claude 3.7 Sonnet、Qwen-Max-Latest；5 个推理模型：o1、o3、Claude 3.7 Sonnet Thinking、豆包 1.5 vision pro、Gemini 2.5 Pro），全部用 VLMEvalKit 跑。表 3 的关键数字：o1 在 V-L-A 下 93.56% 最高；去掉视觉平均掉 3.3%，去掉语言平均掉 4.1%，都去掉掉 8.0%。

三个观察。第一，语言比视觉掉得多（4.1% > 3.3%），说明在这些题目里，高层的理解信息比原始感知信息对决策的贡献更大——这和直觉一致：知道"当前车道不是导航车道"比"看清车道线是实线还是虚线"更直接决定变道。第二，3.3 + 4.1 = 7.4，略小于 8.0，说明视觉和语言有轻微的协同效应，不是完全独立的。第三，推理模型在 V-L-A 下普遍更好（o1、o3 超过 92%），但在 A 模式下优势消失，甚至有非推理模型反超——没有外部信息时，chain-of-thought 反而可能把自己绕进去。

怀疑的部分：这组数字的统计分量。论文 4.4 做了稳定性分析，但只做了两个模型（GPT-4.1 mini 和 Gemini 2.5 Pro）、四个模式各跑三遍，标准差都在 0.3 以内。这能说明"评测本身稳定"，但不能说明"3.3% 这个差值是显著的"。12 个模型的平均差值，没有配对 t 检验，没有置信区间，模型之间的版本差异（比如 GPT-4o mini 90.37 反超 GPT-4o 88.84）也没有讨论是否在噪声范围内。考虑到 VLMEvalKit 跑商业 API 时温度、采样等设置的影响，0.3 的标准差是单次评测的波动，而 3.3% 是跨 12 个模型的平均效应——这两个数字不在同一个层面上，不能直接拿 0.3 去论证 3.3% 显著。论文的措辞是"on average"，没有声称显著性，这一点它没有越界；但读者引用这组数字时，应该知道它的统计支撑就是"12 个模型平均"，没有更强的检验。

## 综合分数掩盖了什么：任务级评测挖出的四个病灶

表 3 的综合分数最高也就 93.56%，看起来大家都还不错。但任务级评测（表 4、表 5、附录图 5 的雷达图）把总分拆开之后，四个病灶露了出来。这也是树状评测真正的价值所在：总分是一个平均数，平均数会撒谎。

**病灶一：导航是持续的短板。** 表 4 里 Navigation 一列，视觉任务各模型大多在 64%–71%，语言任务 71%–82%，动作任务 78%–89%。注意这个顺序：V 和 L 的分数明显低于 A。也就是说，模型经常看不清自己在哪条车道、理解不透导航指令，但最后选变道方向时反而选对了。附录 C.3 的 Table 12 把这个现象钉死了一个具体例子：同一张图，视觉题问"当前车道属性是什么"，模型答错（把"左转"答成"直行+右转"）；语言题问"从最右侧车道右转是否允许"，答对；动作题问"现在该做什么"，选了"向右变道"，答对。模型在不知道自己在哪条车道的情况下，靠导航文本和选项的逻辑排除了错误答案，蒙对了动作。这正是引言里说的第二种失败——感知错了但决策蒙对了——被树状评测抓了个现行。如果只看动作总分，这个模型的导航能力会被高估。

**病灶二：效率任务暴露了保守倾向。** Efficiency 一列的动作分数是全场最低，普遍在 50%–70%。更关键的是附录 Table 13 的例子：视觉题（左车道是否可通行）答对，语言题（当前路况描述）答对，动作题（该不该为了效率向左变道）答错——模型选择了继续直行。V 和 L 全对、A 错，说明问题不在感知也不在理解，在决策层本身：模型看得懂"左车道空着"，但不敢变。论文的解释是模型采取了保守策略，宁可牺牲效率也要避险。这个观察对"人类偏好对齐"是个提醒：人类驾驶员里也有保守派和激进派，DriveAction 的 ground truth 来自真实驾驶员操作，本身就包含了人类在效率和安全之间的真实权衡。模型系统性地偏向保守，说明它没有学到这个权衡，只学到了"别出事"。

**病灶三：红绿灯是跨模型分歧最大的地方。** 附录图 5 的雷达图里，Traffic Light 一类最高分和最低分差了 35.5 个百分点，是所有类别里 spread 最大的。表 5 里 Traffic Light 的视觉任务，Claude 3.7 Sonnet 只有 40.3%，GPT-4.1 mini 44.3%，而 o1 有 59.3%。连"灯在哪个方向、控制哪个车道"这种基础感知都分化成这样，说明红绿灯识别对 VLM 来说是个真瓶颈——小目标、远距离、箭头灯和圆灯的语义差别，这些都不是 VLM 预训练里常见的东西。附录 Table 16 的病例更直接：导航左转、左转箭头灯绿灯，模型选了"停车等待"。绿灯也敢停，这已经不是感知问题，是决策层的过度保守。

**病灶四：动静态障碍物是舒适区。** Dynamic 和 Static 两类的动作分数普遍 98% 以上，视觉语言分数也高。论文的解释是这类样本在训练数据里多、标注清晰。但反过来想：一个基准里最容易的题恰恰是传统感知数据集里最常见的题，这说明 VLM 的驾驶能力目前主要来自预训练里的通用视觉经验，而不是驾驶特有的数据。DriveAction 的价值恰恰在于它用 Navigation、Efficiency、Traffic Light 这些"驾驶特有"的题，把 VLM 的通用视觉能力和驾驶决策能力分开了。

把四个病灶连起来看，树状评测回答了一个总分回答不了的问题：**模型到底是在哪一层犯的错**。导航是 V/L 层错、A 层蒙对；效率是 V/L 层对、A 层不敢动；红绿灯是 V 层就塌了；动静态是全层都好。这四种"错法"需要的修复方法是完全不同的：导航要补车道级感知数据，效率要调决策的风险偏好，红绿灯要补小目标检测，动静态什么都不用做。一个只给总分的基准给不出这种处方。

## 病例走读：GPT-4.1 在信息真空里是怎么一步步错的？

附录 C.2 挑了 GPT-4.1 做病例，专门找那些"V-L-A 答对、A 答错"的题目，也就是信息的有无直接决定对错的题目。这些病例把 8.0% 这个平均数还原成了具体的行为模式。走三个：

**病例一（效率任务，施工封路）。** 图里前方车道被施工设施封死，右车道畅通。题目问该采取什么驾驶行为。A 模式下（无上游信息），GPT-4.1 选了"继续直行，因为前方道路畅通"——它根本没看见施工封路。V-L-A 模式下，上游信息里写明了"前车道被施工设施封闭无法通行，右车道畅通可安全变道"，模型选对"向右变道"。这个病例说明 A 模式错的不是"推理"，是"没看见"。三帧图像给了，但模型没有从中读出施工设施这个关键元素——或者读出了但没意识到它意味着封路。V-L-A 的上游 QA 本质上是把"施工封路"这个结论直接告诉了模型。

**病例二（导航任务，五车道选左转车道）。** 导航提示 155 米后左转，五条车道属性左起是"左转+掉头、潮汐车道、直行、直行、公交车道"，要求用最左车道。A 模式下模型选了"保持当前车道"——默认行为。V-L-A 模式下，上游信息点明"当前车道只允许直行，不是导航车道"，模型选对"向左变道"。这里暴露的是 A 模式的一个系统性默认：**信息不足时，模型倾向于保持现状**（直行、不动）。这在驾驶里是一个看似安全实则危险的先验——路口前不提前变道，本身就是一种错误。

**病例三（红绿灯任务，左转箭头灯）。** 导航左转，前方有左转箭头灯和直行圆灯。A 模式下模型选了"在路口停车等待"；V-L-A 下上游信息说明"左转箭头灯允许左转"，模型选对"跟随左转信号立即左转"。和病例二相反，这里的默认是"停下"。两个默认合在一起看，A 模式的模型行为画像就很清晰了：**纵向保守（该走时停）、横向懒惰（该变时不変）**。这不是某个模型的偶然，这是缺少信息时大语言模型的通用先验——在不确定时选择字面上最安全的选项。而真实驾驶员的"安全"是在保持通行意图下的安全，不是原地不动。

这三个病例也反过来说明了 V-L-A 模式的一个局限：它喂给模型的"上游信息"已经是高度提炼的结论（"前车道被施工设施封闭"），而不是原始感知。模型在 V-L-A 下的高分，证明的是"给定正确结论能做出正确决策"，没有证明"能从图像自己得出正确结论"。论文没有把 V-L-A 的分数包装成端到端能力，这一点它是诚实的；但读者要自己把这句话翻译出来：**DriveAction 测的是决策模块在信息充足时的上限，不是 VLA 系统真实跑起来的样子**。

## 怀疑式审读：这篇论文哪里心虚

前面已经把几个怀疑点埋在了相关章节，这里集中收拢，再补几个新的。先说清楚立场：这是一篇扎实的基准论文，数据和评测设计都是真东西，下面的问题不是要否定它，而是标出它的结论能信到什么程度。

**第一，离散动作的粒度天花板。** 3.2 节论证离散动作"反映人类决策的类别本质"，这个论证只覆盖了"选哪个"，没覆盖"怎么做"。同样是 lane change left，真实驾驶员的执行有激进和温和之分，基准里没有分数区分它们。更实际的问题是：当未来模型的动作选择都接近全对时，这个基准就失效了——它没有第二档难度。论文没有讨论基准的"寿命"问题。一个诚实的基准论文应该回答：什么情况下这个基准会被刷爆，刷爆之后看什么。现在的 DriveAction，动作题全是选择题/判断题，天花板是肉眼可见的。

**第二，"人类偏好"的代表性。** 三个具体问题：一是 internal test users 的身份。摘要说 drivers/users，正文说 internal test users，这两个词指的不是同一群人。如果是理想内部员工或签约测试员，他们的年龄、驾驶经验、对智驾的信任度都和普通车主有系统性差异，"人类偏好"就偏向了这一群人。二是地域。148 城全在中国，交通标志、车道线样式、加塞和让行的潜规则都是中国版本，模型在这里测出的"像人"，不能直接推广。三是数据来源是"智驾开启时的用户操作"，用户接管的那一刻往往是系统搞不定的难场景——这对场景难度是好事，但对"偏好"的代表性是坏事：难场景下的接管操作，可能比日常驾驶更激进或更保守，论文没有量化这个偏差。

**第三，LLM 出题带来的捷径。** 附录 B.2 的两阶段生成流程里，LLM 先写场景报告再出题。LLM 出的题有一个通病：题干为了把场景讲清楚，会把答案相关的关键信息都写进题干。前面举过 Navigation Position 的例子，题干里已经写了"车道属性左起是直行+左转、直行+右转"，再问"当前车道属性是什么"，模型做的是阅读理解，不是视觉感知。论文说人工筛选了有效性，但没有报告"有多少题不看图也能答对"这个关键数字。一个干净的基准应该做一次"盲测"：把图拿掉，看模型光靠题干能拿多少分，以此量化题干泄漏。这个实验论文没做。

**第四，题型本身的猜测基线。** 评测是选择题和判断题二选一式的 QA。判断题随机猜就有 50%，四选一的选择题随机猜 25%。表 4、表 5 里有些格子（比如 Traffic Light 视觉任务 40.3%）已经接近甚至低于随机猜测的水平，这时候"40%"和"25%"之间的差距到底有多少是能力、多少是选项设计的运气，论文没有分析。更重要的是，选择题的干扰项是 LLM 生成的，干扰项如果太弱（比如"把车开上人行道"这种明显荒谬的选项），模型靠常识排除就能答对，测的不是驾驶决策。

**第五，开环评测的固有局限。** DriveAction 的每个场景是独立的：三帧图、一个决策点、一次打分。真实驾驶是闭环的：这一步的决策影响下一步的场景，错误会累积。一个在 DriveAction 上 93 分的模型，开起来可能因为连续小误差的累积而跑偏；而一个 85 分的模型，如果它的错误都是"保守型错误"（该变道时没变），开起来可能反而更安全。论文标题里的"human-like driving decisions"严格说应该是"human-like single-step decisions"。这个基准和 Bench2Drive 这类闭环基准是互补关系，不是替代关系——DriveAction 告诉你决策像不像人、病灶在哪一层，Bench2Drive 告诉你开起来会不会出事。

**第六，统计显著性的缺位。** 前面说过：3.3%/4.1%/8.0% 是 12 个模型的平均差值，没有显著性检验；稳定性实验只覆盖 2 个模型。模型排名（o1 第一、GPT-4o mini 反超 GPT-4o）也没有讨论是否在噪声范围内。对于一篇以"rigorous foundation"为卖点的基准论文，这个缺位是说得过去的（基准论文的主业是数据和方法，不是刷榜），但读者引用排名时要留个心眼。

**第七，哪里做得确实好。** 公平起见：数据来源是真实的、动作标签是操作时刻采集的（不是事后标注），这是全篇最硬的一点；多轮人工质控剔除了误操作和违法行为，说明作者知道"真实"不等于"优质"；任务级评测和附录病例是真材实料，Table 12–16 的例子确实能定位病灶；稳定性实验虽然覆盖小，但至少做了。第一张图（动作树架构）就是作者押的赌注，论文的全部实验都是在为这棵树服务，结构是紧的。

**未确认事项**：正式发表 venue 未确认（只有 arXiv 预印本）；官方代码仓库未找到（论文未声明）；数据集在 HuggingFace 公开但许可细节未细读；各任务 QA 数量的具体分布（图 2 只给了分布图，未读到精确数字）；internal test users 的具体身份和筛选标准论文未交代。

## 两个可以带走的想法

**想法一：从最终决策倒着推评测依赖，这套手法不只适用于开车。** DriveAction 最值得偷的不是数据，而是一个评测设计模式：先把系统的最终决策空间钉死（离散动作），再为每个决策反推出它依赖哪些上游子能力，然后给每个子能力单独出题。传统的评测是顺着系统的处理链条正向出题，结果"感知错但决策蒙对"和"感知对但决策错"混在一起。有了倒推的依赖树，两种失败第一次被分开了。这个模式可以搬到任何多步决策系统上：评测一个 Agent，不要只看它最后做对了没有，要问"它做对的那个决策，依赖哪几个子判断"，然后把每个子判断单独拎出来考。子判断全对但决策错，说明是决策层的问题；子判断错了但决策对，说明是蒙的，换个场景就会露馅。

**想法二：用"信息隔离"给系统做剖腹产式的归因。** V-L-A / V-A / L-A / A 四种模式的本质，是控制变量：一次只撤掉一种信息，看分数掉多少，掉的就是这种信息的贡献。这比端到端跑一个总分更能指导改进——如果撤掉视觉只掉 1% 而撤掉语言掉 6%，那加班的方向应该是理解模块，不是感知模块。任何由多个模块串起来的系统都可以用这套手法：把上游模块的输出换成标准答案喂给下游，测下游的能力上限；再逐步撤掉，看瓶颈在哪。它测的不是真实性能，是"如果上游完美，下游能到哪"，这个上界告诉你改进的优先级。

## 与本课题的关联

读者的课题是"世界模型引导 + 自适应衰减情景记忆的闭环多规划器自动驾驶 Agent"：LLM 调度多个专家规划器，执行开放式自然语言驾驶指令，计划在 Bench2Drive 闭环基准上验证。DriveAction 和这个课题的关系是**评测层面的互补**，下面四点是具体的、可操作的启发。

**第一，Bench2Drive 和 DriveAction 回答的是两个不同的问题，不要互相替代。** Bench2Drive 是闭环仿真：你的 Agent 跑起来，撞没撞、到没到、舒适度如何，它给的是"开起来行不行"的答案。DriveAction 是开环离散决策评测：给定一个场景，你的决策像不像人类驾驶员、病灶在感知还是理解还是决策，它给的是"为什么行 / 为什么不行"的答案。课题的验证主线放在 Bench2Drive 是对的，因为最终要证明的是系统能开。但在论文的实验部分，DriveAction 式的分析是一个很有力的补充：当 Bench2Drive 的某个场景失败时，你可以用"倒推依赖树"的方法定位——是世界模型的未来预测错了，还是情景记忆检索回了错误的经验，还是 LLM 调度器选错了规划器。Bench2Drive 告诉你"这一跤摔了"，依赖树告诉你"是哪条腿绊的"。

**第二，"动作反推任务树"可以直接用来评测你的自然语言指令执行。** 你的系统要执行的是开放式自然语言指令（比如"前面施工，绕过去"），这比 DriveAction 的固定动作空间更难评。一个可行的借鉴是：为每条测试指令，先定义人类驾驶员会做出的期望高层动作（比如"向右变道绕行"），再为这个动作反推它依赖的子问题——世界模型需要预测出施工区的占据变化吗？情景记忆需要检索到"上次遇到施工是怎么绕的"吗？调度器需要理解"绕过去"对应哪个专家规划器吗？每个子问题单独打分。这样，当系统对某条指令执行失败时，你能说出是"没听懂指令""没想起经验"还是"选错了规划器"，而不是只得到一个"任务失败"的二元标签。这正是 DriveAction 的树状评测在你课题上的平移。

**第三，用"信息隔离"量化世界模型和情景记忆各自的贡献。** 你的系统里有两个核心增强模块：世界模型（未来预测先验）和情景记忆（历史经验检索）。DriveAction 的 V-A / L-A 模式提示了一个干净的消融设计：喂给调度器完美的世界模型预测（用真值未来轨迹代替模型预测），看决策上限提高多少——提高的就是世界模型模块的"潜力债"；同样，把情景记忆检索换成标准答案（人工标注的最相关历史经验），看能涨多少。这两组"上界实验"做完，你就知道在有限的时间里应该先优化世界模型还是先优化记忆检索。这比直接端到端调参更能指导资源分配。注意 DriveAction 的教训：这种上界实验测的是潜力，不是真实性能，写论文时要把措辞限定在"在给定完美上游信息时"，不要写成"模块贡献了 X%"。

**第四，清醒认识 DriveAction 式评测在你课题上的天花板。** 你的系统最终输出的是连续轨迹/控制量，要在 Bench2Drive 里闭环跑。离散动作评测有两个够不着的地方：一是它评不出轨迹质量——两个系统都选了"向右变道"，一个变道轨迹平顺、一个生硬，离散评测给同分，Bench2Drive 的舒适度指标才能分开；二是它是开环单步的，测不出误差累积和多步交互（比如变道时和后车的博弈）。所以 DriveAction 的思路适合用在你系统的"诊断层"（定位病灶、写消融、讲故事），不适合作为主验证指标。主指标还是 Bench2Drive 的闭环分数。另外，DriveAction 的数据来自中国 148 城的真实人类操作，如果你的 Bench2Drive 实验主要在 CARLA 的仿真场景里，两个评测的人类偏好基线不在同一个分布上，引用时不要混为一谈。

一句话收拢：DriveAction 给你的不是一套可以直接跑的分数，而是一套"怎么证明你的系统有效"的设计语言——从动作倒着出题、逐层定位病灶、用信息隔离做归因。这套语言用在 Bench2Drive 的闭环结果旁边，你的实验部分会比只有总分的论文扎实得多。
