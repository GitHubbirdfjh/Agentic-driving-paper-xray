> **全局编号**：87

> **作者**：Bo Jiang¹, Shaoyu Chen¹（共同一作）, Qing Xu², Bencheng Liao¹, Jiajie Chen², Helong Zhou², Qian Zhang², Wenyu Liu¹, Chang Huang², Xinggang Wang¹（¹华中科技大学，²地平线）

## 1.8 FPS 的车开不进现实：这篇论文要回答的问题

论文的 Figure 1 并排摆了两张示意图。左边是当时的主流做法：场景被渲染成一堆栅格图——语义地图、占据栅格、流场、代价图，规划模块在这堆像素上做推理。右边是 VAD 的主张：场景是一组向量——边界向量、车道向量、其他车的运动向量、自车的规划向量。作者要回答的问题很具体：前人（ST-P3、UniAD）把规划做进栅格图里，结果是 ST-P3 1.6 FPS、UniAD 1.8 FPS，这样的速度装不上车；同时栅格图把"这是哪一条车道线、那是哪一辆车"的实例结构压扁成了像素，规划时想显式地约束"别撞那辆车"，却找不到可以引用的对象。

这个赌注在 2023 年初并不显然。当时端到端规划的默认信念是：想要可解释、想要安全，就得有 dense 的中间表示（occupancy、cost map），再配手工设计的后处理从代价图里挑轨迹。VAD 反其道而行：中间表示越稀疏越好，约束直接写进训练损失，推理时不留任何后处理。整篇论文就是在为这个反直觉的选择提供证据。

## 栅格表示贵在哪里：dense map 的两笔账

第一笔是计算账。一张 BEV 占据栅格，典型分辨率下是几万个格子，每个格子都要过卷积头输出"被占据的概率"；UniAD 还要再做跟踪、再预测未来多帧的占据、再在上面跑手工规则选轨迹。表 5 给出了 VAD-Tiny 的模块耗时：backbone 23.2ms、BEV encoder 12.3ms、motion 模块 11.5ms、map 模块 9.1ms、planning 模块只有 3.4ms。注意 planning 只占 5.7%——稀疏表示下，规划本身几乎不花钱，钱全花在把图像变成 BEV 特征上。反过来想：前人方案里 dense 占据预测 + 代价图 + 后处理那一整条流水线，在 VAD 里被三个可微损失替代，推理时直接消失。

第二笔是信息账。栅格图把一条车道线存成"这些像素是车道线"，实例身份丢了：规划模块想表达"我的轨迹方向要和我所在的这条车道一致"，在像素表示里没有"这条车道"这个对象可以引用。向量化表示把每条车道线存成一个点序列 $V_m \in \mathbb{R}^{N_m \times N_p \times 2}$（$N_m=100$ 条向量，每条 $N_p=20$ 个点），每个向量自带类别（车道分隔线 / 路缘 / 斑马线）。实例结构保留下来之后，约束才有了可以引用的具体对象：找离规划航点最近的那条车道向量，算它和自车运动向量的夹角，压小这个夹角就是方向约束。

## 作者手里的底牌：MapTR 和 PIP 先把向量化感知做通了

还原时间坐标能解释作者为什么敢下这个赌。向量化地图并不是 VAD 发明的：MapTR（2022）已经证明在线向量化 HD 地图可以和检测头一样端到端训练；PIP（Bo Jiang 等，arXiv:2212.02181，2022 年 12 月，和 VAD 同一拨作者）已经做了"感知 + agent-map 交互 + 运动预测"的端到端流水线。VAD 的一作 Bo Jiang 正是 PIP 的一作——也就是说，动手写 VAD 之前，作者手里已经有一套能稳定输出"向量化地图 + 多模态运动向量"的感知底座。剩下的真正未解的问题只有一个：规划能不能也全建在向量上，不再回头去要 dense 图。

这张底牌的硬度中等偏上。它不是数学上闭式的东西，而是一个工程判断："感知侧已经能给出质量够好的向量，规划侧可以直接消费"。风险在于感知质量波动会直接传导到规划——后面怀疑式审读会回到这一点。

这一步为什么自己想不到？它属于"放弃一个所有人默认的约束"的那一类。2022 到 2023 年初，端到端规划的默认约束是：想要安全、可解释，中间必须有 dense 表示（占据栅格、代价图），规划是"在图上选轨迹"。这个约束看起来是安全本身的要求，其实只是一个习惯：人们把"约束"和"表示"绑在了一起，认为约束必须活在表示上（代价图），于是表示必须 dense。VAD 的关键一步是把两者解绑——约束不需要活在推理时的表示上，它可以活在训练时的损失里。一旦接受"约束只在训练时存在"，dense 表示的唯一理由就消失了，稀疏向量自然成为更便宜的选择。这也是一笔"局部看起来很亏"的交换：稀疏表示丢掉了栅格的冗余（漏检即约束消失，见后文），换来的是速度和实例结构。作者赌的是这笔交换总体划算，表 1 和表 3 是他为这笔账提供的证据。

## 向量长什么样：$V_m$、$V_a$、$V_{ego}$ 的形状和含义

全文的张量就四组，列出来之后整篇论文的机制就没有藏东西的地方了。

| 符号 | 形状 | 含义 |
|---|---|---|
| $Q_m$ | map query，100 个向量 × 20 点位 | 从 BEV 特征里"钓"地图元素的 query，每个 query 负责一条地图向量 |
| $V_m$ | $\mathbb{R}^{100 \times 20 \times 2}$ | 预测出的地图向量：100 条折线，每条 20 个 BEV 坐标点；另有一个类别分数 |
| $Q_a$ | 300 个 | agent query，每个负责一个交通参与者 |
| $V_a$ | $\mathbb{R}^{N_a \times N_k \times T_f \times 2}$ | 每个 agent 的未来轨迹：$N_a$ 个 agent，$N_k$ 种意图模态，$T_f$ 个未来时刻，每个时刻一个 (x, y) 航点；每种模态有一个概率分数 |
| $Q_{ego}$ | 1 个 | 自车 query，随机初始化，负责把场景信息"吸"进来 |
| $V_{ego}$ | $\mathbb{R}^{T_f \times 2}$ | 规划头输出的自车未来轨迹，$T_f$ 个 (x, y) 航点 |

拿一个小实例走一遍。假设 BEV 范围是纵向 60m、横向 30m。map query 里第 7 号 query 负责的向量 $V_m[7]$ 是一条车道分隔线，20 个点从 (5.0, -3.5) 一路排到 (25.0, -3.2)——一条几乎笔直的线，类别分数"车道分隔线" 0.92。agent query 里第 42 号对应左前方一辆车，$V_a[42]$ 有 $N_k$ 条未来轨迹：模态 1（概率 0.7）直行，模态 2（概率 0.2）变道，模态 3（概率 0.1）减速。规划头输出 $V_{ego}$ 是 6 个航点（3 秒 × 2Hz，$T_f=6$ 为按 nuScenes 标注频率的推算，论文未明写）。整个系统的输入输出至此全部具体化：图像进来，三组向量出来。

## 三个 query 的两次握手：ego query 如何从场景里取信息

规划模块的核心是两次 Transformer decoder 交互。第一次，ego query $Q_{ego}$ 去"问" agent queries；第二次，更新后的 $Q'_{ego}$ 再去"问" map queries。公式 (1) 的写法是：

$$Q'_{ego} = \mathrm{TransformerDecoder}(q, k, v, q_{pos}, k_{pos}), \quad q = Q_{ego},\ k = v = Q_a$$

$$q_{pos} = \mathrm{PE}_1(p_{ego}),\quad k_{pos} = \mathrm{PE}_1(p_a)$$

几何上在发生什么：ego query 是一支待填充的向量，它对 300 个 agent query 做注意力。没有位置编码的话，它只能按"内容相似度"去吸信息——但规划需要的是空间关系："左前方 8 米那辆车在减速"。所以作者加了 $q_{pos}$ 和 $k_{pos}$：把自车位置 $p_{ego}$ 和每个 agent 的预测位置 $p_a$ 过一个单层 MLP（$\mathrm{PE}_1$），变成位置嵌入加进注意力里。注意力分数于是同时考虑"这个 agent 的特征和我当前需要什么匹配"和"它在我哪个方向、多远"。第二次交互 (2) 结构完全一样，只是换成 map queries 和另一个位置编码器 $\mathrm{PE}_2$——为什么要两个独立的 MLP？推测是 agent 位置和地图元素位置的分布尺度不同（agent 是点，地图元素是折线），共用一个编码器会互相干扰；论文没做这个消融，这里标为推断。

规划头本身简单到让人意外：就是一个 MLP。

$$V_{ego} = \mathrm{PlanHead}(f_{ego}, cmd=c),\quad f_{ego} = [Q'_{ego}, Q''_{ego}, s_{ego}]$$

输入是两次交互后的 ego query 拼接自车状态 $s_{ego}$（可选），再加一个离散导航命令 $c \in \{\text{左转}, \text{右转}, \text{直行}\}$。没有代价图，没有采样-打分-选最优，没有后处理。

拿一个具体时刻把两次握手走一遍。假设左前方 8 米有一辆车在减速（agent query 第 42 号负责它），右后方 15 米有一辆车在加速（第 137 号）。ego query 对 300 个 agent query 做注意力时，$k_{pos}$ 把两车的位置都编进了 key 里，注意力权重会偏向第 42 号——规划最需要的是"正前方、近、减速"这个组合，右后方那辆车对未来 3 秒的轨迹几乎没有影响。更新后的 $Q'_{ego}$ 里于是混入了"左前方有车在减速"的信息。第二次交互同理：$Q'_{ego}$ 去问 100 条地图向量，离自车最近的那几条车道分隔线权重最高，"我正沿着一条直道行驶"的信息被吸进来。两次握手之后，$Q''_{ego}$ 是一个 256 维向量，里面压缩了"周围谁在动、路怎么走"。规划头 MLP 的全部任务，就是把这 256 维解码成 6 个 (x, y) 航点。所有"智能"都必须被压缩进这一个向量里——这正是下面三个显式约束要干的活：训练时用向量级的几何损失去"管教"这个 MLP，让它输出的轨迹不敢撞、不敢出界、不敢逆行。

## 规划约束的三条铁律：碰撞、越界、方向怎么写进损失

三个约束只在训练时存在（论文图 2 明确标注了 training phase / inferring phase 的分界），推理时零开销。这是全文最值得细看的部分。

**碰撞约束 $L_{col}$（公式 4）。** 先把低置信度的 agent 预测按阈值 $\epsilon_a = 0.5$ 滤掉，多模态轨迹只取概率最高的那一条。然后对每个未来时刻 $t$、每个方向 $i \in \{X, Y\}$，找一定范围 $\delta_a = 3.0m$ 内最近的 agent，记距离为 $d^{it}_a$：

$$L_{col} = \frac{1}{T_f}\sum_{t=1}^{T_f}\sum_{i \in \{X,Y\}} L^{it}_{col},\quad L^{it}_{col} = \begin{cases} \delta_i - d^{it}_a, & d^{it}_a < \delta_i \\ 0, & d^{it}_a \ge \delta_i \end{cases}$$

这是一个铰链（hinge）损失：距离大于安全阈值 $\delta_i$ 时梯度为零，网络爱怎么走怎么走；一旦侵入安全距离，损失随侵入深度线性增长，梯度把规划航点往外推。走一个具体数：$t=3$ 时刻规划航点在 (12.0, 0.3)，最近 agent 的最高置信度预测航点在 (11.2, -0.2)，纵向距离 0.8m < $\delta_X = 1.5m$，横向距离 0.5m < $\delta_Y = 3.0m$，于是 $L^{3X}_{col} = 0.7$、$L^{3Y}_{col} = 2.5$，反传时规划头会收到"把第 3 个航点往远离那辆车的方向挪"的梯度。**记号疑点**：正文说纵向需要更长的安全距离，但实现里 $\delta_X = 1.5m$、$\delta_Y = 3.0m$；论文没有交代 X/Y 哪个是纵向，两处放在一起看是矛盾的，至少是记号不清。此处记为未确认。

**越界约束 $L_{bd}$（公式 5）。** 同样的铰链结构：对每个未来时刻，算规划航点到最近路缘向量的距离 $d^t_{bd}$，阈值 $\delta_{bd} = 1.0m$，侵入则 $L^t_{bd} = \delta_{bd} - d^t_{bd}$。作用是把轨迹"推"回可行驶区域。注意它惩罚的是"离边界太近"，而不是"压线"——1.0m 的缓冲带让梯度在真正出界之前就开始工作。

**方向约束 $L_{dir}$（公式 6）。** 找离规划航点最近（$\delta_{dir} = 2.0m$ 范围内）的车道分隔线向量 $\hat{v}^t_m$，算它与自车运动向量 $\hat{v}^t_{ego}$（从 $t-1$ 航点指向 $t$ 航点）之间的夹角，时间平均：

$$L_{dir} = \frac{1}{T_f}\sum_{t=1}^{T_f} F_{ang}(\hat{v}^t_m, \hat{v}^t_{ego})$$

几何意义很直观：你开车的方向应该和你所在的车道指向一致。这是三个约束里唯一一个"引导型"而非"惩罚型"的——前两个是"别做错事"，这个是"照着车道走"。

模仿学习损失 $L_{imi}$（公式 7）是常规的 $l_1$：规划轨迹与专家轨迹逐航点取 $l_1$ 距离再平均。总损失（公式 8）是六项加权和：

$$L = \omega_1 L_{map} + \omega_2 L_{mot} + \omega_3 L_{col} + \omega_4 L_{bd} + \omega_5 L_{dir} + \omega_6 L_{imi}$$

**$\omega_1$ 到 $\omega_6$ 的具体数值在正文和实现细节里都没有给出**，记为未确认。地图损失用曼哈曼距离做回归、focal loss 做分类；运动预测对匹配上的 agent 取 minFDE 那条轨迹做 $l_1$ 回归、focal loss 做多模态分类。这些细节都在，但六个权重的量级和敏感性无从判断——这是怀疑式审读要记的一笔。

## 表 1 的数字在什么条件下成立

nuScenes val 上的开环结果（论文表 1 主行，不带 ego 状态）：

| 模型 | L2 1s / 2s / 3s / 平均 | 碰撞率 1s / 2s / 3s / 平均 | 延迟 / FPS |
|---|---|---|---|
| UniAD | 0.48 / 0.96 / 1.65 / **1.03m** | 0.05 / 0.17 / 0.71 / **0.31%** | 555.6ms / 1.8 |
| VAD-Tiny | 0.46 / 0.76 / 1.12 / **0.78m** | 0.21 / 0.35 / 0.58 / **0.38%** | 59.5ms / 16.8 |
| VAD-Base | 0.41 / 0.70 / 1.05 / **0.72m** | 0.07 / 0.17 / 0.41 / **0.22%** | 224.3ms / 4.5 |

三个 headline 数字都能对上：平均位移误差 1.03m → 0.72m，降幅 (1.03−0.72)/1.03 = 30.1%；平均碰撞率 0.31% → 0.22%，降幅 29.0%；FPS 1.8 → 4.5（2.5 倍）、1.8 → 16.8（9.3 倍）。但读表时要注意三个条件。第一，**表注写明 ST-P3 和 VAD 的 FPS 测在一块 RTX 3090 上，UniAD 的 FPS 测在 A100 上**——跨卡对比 FPS，VAD 其实是吃了点亏的（A100 通常更快），这一点作者如实标注了，值得肯定。第二，主结果**关掉了 ego 状态输入**，理由是开环评测下 ego 状态会导致 shortcut learning（论文引了 [50] Zhai 等人的 "Rethinking the open-loop evaluation"）；带 ego 状态的行（VAD-Base L2 平均 0.37m）只放在表里供参考，作者明确不拿它当成绩。第三，Tiny 的碰撞率（0.38%）其实比 UniAD（0.31%）还高一截——"可比的规划性能"这个说法里，L2 确实可比，碰撞率是打了折扣的。

## 16.8 FPS 到底省在哪：模块耗时拆解

"快 9.3 倍"很容易被误读成"向量化表示本身快 9.3 倍"。表 5 把 VAD-Tiny 的 59.5ms 拆开：backbone 23.2ms（39.0%）、BEV encoder 12.3ms（20.7%）、motion 模块 11.5ms（19.3%）、map 模块 9.1ms（15.3%）、planning 模块 3.4ms（5.7%）。读出三层信息。

一，planning 只占 5.7%——稀疏表示下规划确实便宜，这是向量化表示的真实红利。省掉的是 UniAD/ST-P3 那边 dense 占据预测、代价图构建、手工后处理选轨迹的一整条流水线。

二，Tiny 相对 Base 的提速里，有相当一部分来自"更小的模型"而非"更好的表示"：输入图像从 1280×720 降到 640×360（像素数降为约 1/4，backbone 的 23.2ms 里有直接贡献）、BEV query 从 200×200 降到 100×100、encoder/decoder 层数从 6 降到 3。论文没有给出"同样 backbone 下栅格 vs 向量"的纯净对比，所以 9.3 倍里表示和模型尺寸各占多少，论文没有提供能区分的信息。

三，即使向量化了，backbone + BEV encoder 依然吃掉近 60% 的时间。想再快，瓶颈在图像到 BEV 这段，不在规划。

## UniAD 的 1.8 FPS 到底花在了哪里

要理解 VAD 省掉了什么，得看 UniAD 的账单花在哪。UniAD 是一个"大而全"的端到端系统：除了检测和建图，它还做多目标跟踪、未来多帧的 dense 占据预测，然后基于占据构建代价图，再用手工设计的后处理从候选轨迹里挑最优。VAD 把这三样——跟踪、占据预测、代价图后处理——全部删掉，一样都没留。跟踪删掉的代价是：agent query 之间没有显式的时序关联，运动预测全靠 2 秒历史 BEV 特征里的时序信息；占据预测删掉的代价是：上面说的漏检即约束消失；后处理删掉的代价是：规划头输出什么就是什么，没有第二道检查。这三笔"删掉"换来了从 555.6ms 到 224.3ms（Base）再到 59.5ms（Tiny）的延迟下降。

但这里有一个论文没有控制的变量：backbone 和输入尺寸。VAD-Base 和 VAD-Tiny 都用 ResNet50，而论文没有交代 UniAD 的 backbone 配置，两个模型的输入图像尺寸也不在同一档。Tiny 从 Base 的 1280×720 降到 640×360，光像素数就砍到约四分之一。所以"9.3 倍"这个数字里，向量化表示的贡献和"模型更小"的贡献是混在一起的，论文没有提供把两者分开的证据。严格来说，表 3 的栅格对照实验（同 backbone、同尺寸下只换地图表示）才是表示本身的红利：碰撞率 0.39% → 0.26%，而速度差异在那张表里没有报告。

## 消融表告诉我们哪个设计真正承重

表 2（VAD-Base 上的七组配置）里，承重结构分得比较清楚。去掉全部三个显式约束（ID 3，只有两次 query 交互）：平均 L2 0.76m、碰撞率 0.28%；三个约束全加上（ID 7）：0.72m、0.22%。约束主要压的是碰撞率，L2 只动了 0.04m。去掉 ego-map 交互（ID 1）：L2 恶化到 0.86m——地图信息对"走得准"最关键；去掉 ego-agent 交互（ID 2）：碰撞率升到 0.26%——agent 信息对"别撞"最关键。隐式交互和显式约束各管一摊，分工干净。

表 3 是最有信息量的一张：把 VAD 的地图头换成栅格分割（其余不变），碰撞率从 0.26% 跳到 0.39%，而 L2 反而略好（0.74m vs 0.77m）。也就是说，**向量化表示真正的红利在安全性（实例级约束能抓住具体对象），不在拟合精度**。这和论文的 headline 叙事一致，也是全篇最诚实的一个对照。

## 怀疑式审读

**开环指标的上限：这篇论文引了 [50]，但主力证据还是开环。** 任务简报里写"VAD 只有 nuScenes 开环评测"，这个说法不准确——论文表 4 给了 CARLA Town05 的闭环结果：VAD-Base 短路线 DS 64.29 / RC 87.26，长路线 DS 30.31 / RC 75.20，超过 ST-P3（55.14 / 11.45），接近激光雷达的 Transfuser（长路线 DS 33.15）。但要注意：Town05 是 2021 年的老基准，场景复杂度远低于今天的 Bench2Drive，而且它的长路线指标（DS 30.31）其实没有拉开和激光雷达方法的差距上限；而且闭环只占了半页篇幅，论文的全部 headline 数字（30.1%、29.0%、9.3×）都来自 nuScenes 开环。作者自己引了 [50] 指出开环评测有 shortcut learning 问题，并为此关掉了 ego 状态——这个处理是诚实的，但它也意味着：开环 L2 从 1.03 降到 0.72，有多少是"规划变好了"，有多少是"开环指标本身对向量表示更友好"，论文没有提供区分的证据。

**闭环评测里藏着一个补丁。** 4.1 节交代：为了跑 CARLA 闭环，作者额外加了一个红绿灯分类分支——一个独立的 ResNet50 加 MLP，输入是前视图像上半部分裁剪，展平后的特征送进规划头。这个分支只在闭环评测里出现，开环的 nuScenes 模型里没有。按 skill 的标准，这就是一个"技巧"：主干的向量化表示处理不了红绿灯语义（红绿灯在 BEV 向量里没有位置），只好在外面挂一个补丁。它不影响论文的主张，但说明"全向量化"在当时并没有走通到底——交通语义这类信息还是靠外挂解决的。结论节作者也承认，车道图、路标、限速这些信息如何并入系统，是未来的工作。

**query 消失时，约束也一起消失。** 这是向量化表示最脆弱的一点。碰撞约束的第一步是"按 $\epsilon_a = 0.5$ 滤掉低置信度预测"——如果检测头漏检了一辆车，这辆车就没有运动向量，碰撞约束对它恒为零，规划头收不到任何关于它的梯度（训练时）或信息（推理时）。栅格占据表示在这里有冗余优势：即使实例身份错了、分类错了，一团"被占据"的像素还在，代价图依然会避开。稀疏表示把"检测"和"约束"绑死在同一个 query 上，漏检的代价从"精度下降"变成了"约束凭空消失"。论文没有报告漏检场景下的表现，这是一个真实的缺口。

**多模态预测只用了最自信的那一条。** $V_a$ 输出 $N_k$ 种意图模态，但碰撞约束只取概率最高的一条。结论节作者自己承认了这是未解问题。如果最高置信度模态是"直行 0.55"，而"切入我车道 0.30"才是危险的那条，约束看到的恰恰是安全的那条。这个简化让约束的计算量可控，但安全论证上打了折。

**基线选择偏窄。** 端到端规划基线只有 UniAD 和 ST-P3（加上几个激光雷达方法和早期工作）。没有和同期的其他向量化/稀疏规划工作对比，1.8 FPS 的 UniAD 作为"前 SOTA"在速度上本来就是个软目标——打败一个 1.8 FPS 的基线拿到 9.3 倍，和打败一个 10 FPS 的基线不是一回事。

**$\omega$ 权重和阈值的敏感性未知。** 六个损失权重没有在论文里给出数值；$\epsilon_a = \epsilon_m = 0.5$、$\delta_a = 3.0m$、$\delta_{bd} = 1.0m$、$\delta_{dir} = 2.0m$ 这些阈值也没有敏感性分析。铰链损失对阈值通常是敏感的：$\delta_{bd}$ 从 1.0m 改成 0.5m，越界约束的触发频率会完全不同。复现者只能去代码里找答案。

公平地说，论文也有做得漂亮的地方：FPS 跨卡对比在表注里如实标注；ego 状态的 shortcut 问题主动处理而不是藏起数字；表 3 的栅格对照实验诚实地显示了向量化在 L2 上并不占优。这些都是审稿人会加分的老实写法。

## 能带走的两个想法

**把安全约束写成训练时的可微损失，推理时零开销。** 这是 VAD 最值得偷的一个模式。传统做法是：感知输出 → 建代价图 → 手工规则选轨迹，约束活在推理时，每一帧都付账。VAD 把"别撞、别出界、别逆行"写成铰链损失，直接加在规划头的训练目标里，推理时约束全部撤下，只剩一个 MLP 前向。这个模式不依赖自动驾驶：任何"输出是连续量、约束是几何关系"的问题（机械臂避障、轨迹优化），都可以把约束写成"侵入深度"的铰链项塞进训练。关键条件是中间表示必须稀疏且带实例结构——dense 栅格上写不出"离那辆车多远"这种损失。

**稀疏 query + 显式几何损失是一对必须同时出现的设计，缺一不可。** 表 3 说明：光有向量表示、没有显式约束，碰撞率只降到 0.26%；约束加上之后才到 0.22%。反过来，没有向量表示，约束连"抓住哪个对象"都做不到。做系统设计时可以照这个检查：如果你的中间表示是 dense 的，就别指望实例级约束；如果表示是稀疏的，约束一定要显式写出来，不能指望网络自己从数据里"悟"出别撞车——ID 3（无约束）0.28% 的碰撞率就是"悟"不出来的证据。

## 与本课题的关联：VAD 做专家规划器，还缺的三块拼图

用户的课题是"世界模型引导 + 自适应衰减情景记忆的闭环多规划器自动驾驶 Agent"：LLM 调度多个专家规划器执行开放式自然语言驾驶指令，在 Bench2Drive 上闭环验证。VAD 在这个蓝图里的位置很自然：**专家规划器池里的高速端到端候选**。16.8 FPS 的纯视觉端到端规划、开环 L2 0.78m、代码公开且已有 Bench2Drive 上的 CARLA 实现（仓库动态里明确提到），把它接进 Bench2Drive 闭环管线的工程阻力很小。它的 sparse query 接口也方便：agent 运动向量和地图向量可以直接作为下游风险校验模块的输入，不需要再解码 dense 图。

但 VAD 恰好缺用户课题要补的三块拼图，缺口对得非常齐：

一，**开放式指令理解**。VAD 的导航输入只有三档离散命令（左转 / 右转 / 直行），论文 4.1 节闭环评测里导航信息是一个稀疏目标点加离散命令。它听不懂"前面路口掉头后停在便利店门口"这种自然语言指令——这正是用户课题里 LLM 调度器的位置：把开放式指令翻译成专家规划器能消费的约束或命令。

二，**情景记忆**。VAD 的时间窗口只有 2 秒历史 BEV，没有跨场景的长期记忆。用户课题里的"自适应衰减情景记忆"要解决的是：把过去见过的长尾场景（比如某种特殊的施工绕行）存下来、按相关性衰减检索。VAD 的 query 交互是纯前馈的，没有记忆写入和检索的通路。

三，**独立风险校验**。这是最关键的一块：VAD 的三个安全约束**只在训练时存在**，推理时规划头是裸奔的——图 2 的 training/inferring 分界写得明明白白。用户课题里的"闭环风险校验 / 冲突仲裁"恰好是推理时的独立模块：不信任任何一个专家规划器的输出，用世界模型预测 + 显式几何检查做二次把关。VAD 的向量化表示（$V_a$、$V_m$）正好是这种校验器最想消费的输入格式——稀疏、带实例结构、带置信度。所以一个自然的分工是：VAD（或其 Tiny 变体）当快速专家出轨迹，用户的风险校验模块用它的 $V_a$/$V_m$ 做独立的碰撞复核，LLM 在多个专家的候选之间做仲裁。

一句话：VAD 证明了"向量化 + 显式几何约束"这条路又快又有效；用户课题要做的，是在它周围补上指令理解、长期记忆和推理时校验——而这三块正是 VAD 论文里明确写进"未来工作"、没有碰的部分。
