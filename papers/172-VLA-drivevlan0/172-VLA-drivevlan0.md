## 这篇论文赌的是哪一个观察

开篇先看一个所有做端到端驾驶的人都见过的现象：同一个模型，在同一类场景下反复犯同一个错。不是随机失误，是系统性的——某个无保护左转的路口，它上周撞过，这周换个光照条件再来，还撞。批量训练的问题在这里暴露得很彻底：几十万个场景的梯度平均下来，"这个路口要让行"这种只占万分之一的教训，权重更新里连个水花都看不见。

作者的起点是认知科学里的两个老引用（[2,3]）：人类会把当前情境和历史错误关联起来，预估"我这次栽的概率"，然后调整行为。论文把这句话翻译成工程：给 VLA 配一个只记失败的情景记忆，推理时做关联检索，认出危险就地修正。

Figure 1 是作者押的赌注，值得单独读。(a) 是经典 VLA：VLM 做推理，中间特征喂给 Action Decoder 出轨迹，红色的"模型可能选的轨迹"画在危险的位置上——作者想让你相信的是"基座模型在失败场景下根本没有好选项可选"。(b) 是他们的方法：从 latent memory 里捡回结构相似的失败案例，用梯度下降（decoupled LoRA TTT）把教训注回去，轨迹变绿（安全）。(c) 是两条 SOTA 曲线：Navtest（NAVSIMv1）蓝色、Navhard（NAVSIMv2）橙色。

但真正硬的证据不在 Figure 1，在 Table 3 里藏着：用语言特征 $F_{lang}$ 做检索键，PDMS 是 90.7，**比不做任何事的基座（91.0）还低**。这个数字是全文最诚实的一处——它说明作者的核心押注（"检索键必须是结构的，不能是语义的"）不是先验信念，是被数据逼出来的：如果随便拿个 embedding 做检索，记忆反而帮倒忙。

## 为什么拿语言特征做检索是个坏主意

先把驾驶规划真正依赖的信息拆开。论文在引言里给了两类，值得展开：

第一类是**动态信息**：周围智能体的运动——前车在减速、对向车道有车逼近、行人站在路缘试探。第二类是**场景结构信息**：路网拓扑——这是十字路口还是环岛、车道线怎么画、可行驶区域的边界在哪。

语言特征 $F_{lang}$ 是什么？它是 VLM 最后一层 hidden state $h_{-1}$ 经 Q-Former 压缩后的 16×256 表示，训练目标是回答驾驶问答（"前面红灯吗""该让行吗"）。它擅长的是**语义**："这是一个左转场景"。但"左转"这个词底下，十字路口的左转和环岛的左转在拓扑上完全是两回事，对向车流的动态也完全不同。用语义相似度检索，捡回来的可能是一个"看起来都是左转、但路网结构迥异"的案例，TTT 在它上面做梯度更新，等于让模型学错路口的教训——Table 3 的 90.7 就是这么来的。

Figure 3 把这一点画出来了：map embedding 的注意力落在车道线和道路边界上，agent embedding 的注意力落在前方车辆上。两路特征各管一摊，拼起来才是"这个场景在结构上长什么样"。

这里要诚实地补一个怀疑：这个对比不完全公平。$F_{lang}$ 是被 1050 倍压缩过的表示（2800×1536 → 16×256，下面细算），而且从没为检索训练过；而 map/agent 特征来自 DINOv2 + 占位栅格监督，专为结构表示炼过。所以 Table 3 严格来说比较的是"一个为检索训练过的结构表示 vs 一个没为检索训练过的语义表示"，而不是"结构 vs 语义"本身。但方向性结论站得住：**检索键必须和下游任务（规划纠错）对齐**，拿现成的 VLM 特征当万能钥匙，在驾驶这个任务上是行不通的。

## 检索模型是怎么炼出来的

Retrieve Model 的结构（Figure 5，§3.2）值得逐行读，因为它是全文"解耦"这个词的第一次落地。

输入是前视图像 $I$。骨干是一个轻量的预训练 DINOv2，上面挂**两套 LoRA 分支**，并行前向，一次出两套特征：

$$F_{map}, F_{agent} = \text{DINOLoRA}(I), \tag{6}$$

$F_{map}$ 管静态路网，$F_{agent}$ 管动态智能体。每套特征再过一个带可学习 query 的 Transformer decoder 聚合成紧凑表示，最后各接一个 head，输出 BEV 占位栅格预测 $\hat{M}_{map}$ 和 $\hat{M}_{agent}$。

训练目标是占位栅格的二元交叉熵，沿用 TransFuser 的范式：

$$L_{Retrieve} = \text{BCE}(\hat{M}_{map}, M_{map}) + \alpha \cdot \text{BCE}(\hat{M}_{agent}, M_{agent}), \tag{7}$$

$\alpha = 10$。论文给了理由：agent 分支的损失量级比 map 分支小得多，不加权会被淹没。这是一个典型的工程权衡——占位栅格里"路"占的像素远多于"车"，BCE 会被大面积的道路像素主导，$\alpha=10$ 是把两路拉回同一量级的手动旋钮。附录没有给 $\alpha$ 的敏感性分析，这是个小缺口，但 10 这个数量级从"像素占比差一个量级"的角度看是合理的。

为什么用占位栅格做监督，而不是对比学习或重建？因为占位栅格是**结构表示最直接的载体**：BEV 网格上每个格子回答"这里是路吗/这里有车吗"，map 分支被逼着学会拓扑，agent 分支被逼着学会布局。检索时用的 $F_{map}$、$F_{agent}$ 是出占位栅格之前的特征——它们已经被占位监督"调教"成了结构敏感的表示。这就是"结构化检索"的全部秘密：不是检索算法多 clever，是**表示本身就是为结构炼的**。

## 记忆里到底存了什么：一条 entry 的三件套

§3.3 的记忆设计是全文最工整的部分。记忆 $M$ 是 case 集合，每条 entry 是三元组：

$$M = \{(k_i, x_i, y_i)\}_{i=1}^{N}, \tag{8}$$

$$(k_i, x_i, y_i) = \big((F^{(i)}_{map}, F^{(i)}_{agent}),\; (F^{(i)}_{lang}, F^{(i)}_{ego}, \hat{T}^{(i)}),\; (\tau^{(i)}, S^{(i)})\big). \tag{9}$$

三件套各有分工，值得一个个看：

- **$k$：检索键**。$(F_{map}, F_{agent})$，就是上一节炼出来的结构表示。只存这两样，不存语言特征——这是 Table 3 的结论在数据结构上的落地。
- **$x$：适配输入**。$(F_{lang}, F_{ego}, \hat{T})$——语言 embedding、自车状态 embedding、基座解码出的轨迹簇。这些是 Action Decoder 的中间表示，TTT 时要拿它们当"模型输入"重新前向。注意 $\hat{T} \in \mathbb{R}^{M \times 8 \times 3}$：$M$ 条候选轨迹（$M$ 的具体值论文没给，是个小缺口），每条 8 个 waypoint，每个点 $(x, y, \text{heading})$。
- **$y$：监督标签**。$(\tau, S)$——专家轨迹 $\tau$（给 Trajectory Head 的回归目标），$S = \{s_k\}_{k=1}^{K}$（给 Score Head 的打分目标，来自 oracle 仿真）。

什么时候一条场景值得被记住？基座模型先在场景 $s$ 上跑一遍，得到预测轨迹 $\hat{\tau}$，oracle（PDM scorer [7]）在仿真里给它打分 $Q(\hat{\tau}) \in [0,1]$（乘法+加法聚合，仿照 PDMS 的结构）。判定规则：

$$M \leftarrow M \cup \big(((F_{lang}, F_{ego}, \hat{T})), (F_{map}, F_{agent}), (\tau, S)\big) \quad \text{if } Q(\hat{\tau}) < \beta, \tag{10}$$

$\beta = 0.5$。论文给了依据：按 NAVSIM 的打分惯例，NC（无责任碰撞）和 DAC（可行驶区域遵守）低于 0.5 意味着真撞了或真开出去了。注意 NC 的取值是 $\{0, \frac{1}{2}, 1\}$、DAC 是 $\{0,1\}$——乘法聚合下，只要撞了，$Q$ 直接归零，稳稳低于 0.5。所以这条规则实际效果是：**只记住那些真出事的场景**，不是"开得不够好"的场景。记忆是失败记忆，不是经验记忆——"failure-aware" 落在这一个不等式上。

写入前还有一步余弦相似度去重：太像的场景不重复存，把记忆规模压住。去重的阈值论文没给，这是复现缺口之一。Base 配置记忆约 4K 条，Scale 配置扩到 10K。

## 什么时候值得花那几十毫秒：Trigger 门

TTT 不是每个场景都做。§3.4 的 Trigger 是一个二值门：

$$g = \begin{cases} 1, & \text{if } \dfrac{F^\top F^*}{\|F\|_2 \|F^*\|_2} > \lambda, \\ 0, & \text{otherwise,} \end{cases} \tag{11}$$

$F^*$ 是从记忆里捡回来的特征，$\lambda = 0.9$。Algorithm 1 的流程是：map 通道和 agent 通道各取 top-$k$（相似度超过 $\lambda$ 的才算），两个通道都空就直接返回基座轨迹 $\hat{\tau}_0$，跳过 TTT。

Table 5 是这扇门的消融（map-only 检索配置下），四个阈值排开：

| $\lambda$ | 0.70 | 0.90 | 0.95 | 0.99 |
|---|---|---|---|---|
| PDMS | 90.4 | **91.7** | 91.4 | 89.4 |

两头的故事都很清楚。$\lambda = 0.7$ 太松：不相似的场景也被捡回来，TTT 的监督变成噪声，NC 和 TTC 掉得最多（98.0/93.8 vs 98.4/94.5）——**在错误的教训上做梯度更新，不如不更新**。$\lambda = 0.99$ 太严：几乎没有场景能触发，PDMS 掉到 89.4，比基座的 91.0 还低 1.6。注意这个 89.4 低于基座的现象：门太严时，只有极少数"和某条失败记忆几乎一模一样"的场景触发 TTT，更新反而把模型带偏——说明 TTT 的收益来自"相似但不相同"的泛化，完全相同的案例上做梯度步是过拟合。

这里有两个诚实的问题。第一，**触发率没有报告**：navtest 里到底百分之几的场景走了 TTT？不知道这个数，平均延迟就算不出来，"适度开销"的说法就缺了一条腿。第二，门的动机（引言里引用的认知科学：评估当前情境的失败概率）和实现（和历史失败的余弦相似度）之间有一小段距离——相似度高不等于失败概率高，它隐含假设"长得像的失败场景，当前场景也会栽"。这个假设在驾驶里大体成立（同一路口同一走位），但论文没有把它说破。

## 核心机制：Decoupled LoRA TTT 到底在训练什么

这是全文承重的那根梁，值得放慢。先把基座的 Action Decoder 讲清楚，因为 TTT 动的就是它。

基座解码器是 proposal-and-score 两段式（沿 iPad [11]、VADv2 [5]、GTRS [23] 的路线）。Trajectory Head 先把自车状态压成 $F_{ego} \in \mathbb{R}^{1 \times D}$，和语言特征 $F_{lang} \in \mathbb{R}^{16 \times 256}$ 一起解码出轨迹簇：

$$F_{proposals} = \text{Transformer}\big((Q_{ego} + F_{ego}), F_{lang}, F_{lang}\big), \tag{2}$$
$$\hat{T} = \text{MLP}(F_{proposals}), \tag{3}$$

$Q_{ego} \in \mathbb{R}^{M \times D}$ 是可学习的 mode embedding，$M$ 个 mode 各自去"认领"一种走法（直行、左转、让行……），$F_{ego}$ 广播加到每个 mode 上。Score Head 再把 $\hat{T}$ 重编码、和 $F_{lang}$ 融合，给每条候选打 $K$ 个子分数（碰撞、可行驶区、TTC、舒适度……）：

$$F_{scores} = \text{Transformer}\big((F'_{proposals} + F_{ego}), F_{lang}, F_{lang}\big), \tag{4}$$
$$\hat{S} = \{\text{MLP}_i(F_{scores}) \mid i = 1, \dots, K\}, \tag{5}$$

$\hat{S} \in \mathbb{R}^{M \times K}$，最后按聚合分数最高的选一条 $\hat{\tau}$ 输出。

基座训练分两段（附录 A）：VLM 骨干（InternVL3）在 775K 驾驶问答对上微调——这是从 RecogDrive 收集的 3.1M 对里过滤出来的高质量子集，覆盖 12 个公开数据集；然后冻结 VLM，只训 Action Decoder，损失是两项相加：

$$L_{total} = L_{traj} + L_{score}, \tag{12}$$
$$L_{traj} = \min_{i \in \{1,\dots,N\}} \|\hat{\tau}_i - \tau^*\|_1, \tag{13}$$
$$L_{score} = -\frac{1}{N}\sum_{i=1}^{N} \big[s_i \log(\hat{s}_i) + (1 - s_i)\log(1 - \hat{s}_i)\big]. \tag{14}$$

(13) 是 min-over-$N$ 的 L1：$N$ 条候选里只要有一条贴近专家轨迹 $\tau^*$ 就行——这是在**鼓励多模态**，不惩罚那些"合理但和专家不一样"的走法。(14) 是 BCE，软目标 $s_i$ 是 oracle PDM scorer 给每条候选打的真实质量分。两项的分工：$L_{traj}$ 保证"至少有一条像人开的"，$L_{score}$ 保证"打分器能认出哪条好"。

现在看 TTT。触发之后发生的事（Algorithm 1 第 18–22 行）：

1. **LoRA 权重为当前场景重新初始化**。标准 LoRA 零初值意味着：更新前模型行为和基座完全一致，TTT 只做"增量修正"，不做"重写"。
2. **两条分支吃不同的数据**：map 通道捡回的案例 $C_{map}$ 只训 map（静态）LoRA 分支，agent 通道捡回的 $C_{agent}$ 只训 agent（动态）LoRA 分支。3 步，AdamW，lr $2\times10^{-4}$。
3. **路径感知的分数融合**：两条分支各自独立地给轨迹簇打分；选最终轨迹时，道路理解类子分数（比如 DAC）取 Static LoRA 的预测，动态能力类子分数（比如碰撞）取 Dynamic LoRA 的预测，再按 PDMS 式聚合挑最优 $\hat{\tau}^*$。

"解耦"在这里有两层含义，论文把它们用同一个词包在一起，读的时候要分开：第一层是**检索的解耦**（map/agent 两路特征），第二层是**适应的解耦**（两路 LoRA 吃不同的检索集、管不同的分数维度）。第二层是这篇论文真正的手笔：它假设"静态知识"和"动态知识"在参数空间里也是可分的——修路网理解的梯度不应该干扰修碰撞判断的梯度。

Figure 4 是这个机制的可视化，值得细读。上半：TTT 之前，失败场景下基座的轨迹簇集中在零分附近——**候选池里根本没有好选项**，这就是为什么"只调打分器"救不了它，必须动生成端。下半：注入之后，整簇的 GT 分数密度右移，好选项出现了，打分器才有东西可挑。这个图把"记忆+TTT"的分工说清楚了：记忆提供"正确的方向"（检索案例的专家轨迹 $\tau$ 做回归目标），TTT 负责把方向写进参数。

### 论文没写出来的那一行：$L_{TTT}$ 到底长什么样

这里必须指出来：**$L_{TTT}$ 在全文没有显式公式**。Algorithm 1 第 20 行只写了 "Optimize trajectory and score losses on retrieved cases"，第 21 行 $\theta \leftarrow \theta - \eta\nabla_\theta L_{TTT}(C_{map}, C_{agent})$。复现者只能推断：大概率是 $L_{traj} + L_{score}$ 的同一套形式，作用在检索案例的 $(x, y)$ 上——用专家轨迹 $\tau$ 做 min-L1 回归目标，用 oracle 分数 $S$ 做 BCE 软目标，再按分支路由（map 分支的更新只影响静态相关的分数 head，agent 分支只影响动态相关的）。但"按分支路由"具体是数据路由（不同分支见不同案例）还是梯度路由（不同分支只更新对应分数 head 的参数），论文没有说死。从 "map-retrieved cases are used to fine-tune the map (static) LoRA branch" 的措辞看，至少数据是路由的；融合阶段"Static LoRA 管 DAC 类分数"的描述暗示参数层面也有分工。这是审稿人一定会追问的点，也是复现的最大缺口。

### 为什么是 LoRA 而不是全量微调：Table 4 的 0.1 分

Table 4 是全文最漂亮的一张消融（NAVSIMv1，基座 PDMS=91.0）：

| 注入方式 | PDMS |
|---|---|
| Base（无记忆） | 91.0 |
| Offline（失败案例上继续训 10 epoch，Action Decoder 加 LoRA） | 91.2 |
| TTT Full（全量微调 Action Decoder） | 92.4 |
| TTT LoRA（Decoupled LoRA） | 92.3 |

两个结论。第一，TTT Full 只比 TTT LoRA 高 0.1——低秩约束几乎没损失性能，但反向延迟从 55.42ms 降到 26.44ms（Table 6）。这就是 "decoupled LoRA" 存在的全部理由：**用可忽略的性能代价换一半的延迟**。

第二，Offline 只涨了 0.2。作者的解释是"分布不匹配"：离线是在固定的失败数据混合上训练，没有场景特异性。这个解释要拆开读。Offline 基线见过的数据比 TTT 多得多（全部失败案例 × 10 epoch vs 当前场景的 top-$k$ 邻居 × 3 步），输的不是数据量，是**平均化**——几千个失败场景的梯度平均下来，"这个路口"的那一点教训又被稀释了。所以这张表真正隔离的是"全局失败微调 vs 场景特异微调"（两者都是 LoRA 容量），结论成立；但它不能被读作"TTT 范式全面胜过离线训练"，因为离线基线的失败恰恰印证了论文的动机：失败知识必须按场景取用，不能混在一起训。

Table 8（附录 D）补了 TTT 超参的鲁棒性：lr 在 $\{5\times10^{-5}, 1\times10^{-4}, 2\times10^{-4}\}$、步数在 $\{1,3,5\}$ 之间，PDMS 只在 92.0–92.3 之间浮动（最多差 0.3）。作者的解释是低秩适应的正则化效应——更新被约束在小子空间里，3 步小更新掀不起大浪。这个解释是站得住的，而且它回答了一个实际问题：**测试时梯度更新最怕的是把模型搞坏**，不敏感性就是安全垫。连 1 步更新都能到 92.0–92.2，说明大部分收益来自"往正确方向推一把"，而不是"精细收敛"。

这里有个笔误必须记录：附录 D 的正文写的是 "learning rates of $2\times10^{-5}$ to $5\times10^{-5}$"，和表格里的 $\{5\times10^{-5}, 1\times10^{-4}, 2\times10^{-4}\}$ 对不上，默认配置也是 $2\times10^{-4}$。纯笔误，不影响结论，但说明附录这段是赶工写的。

## "加记忆不用再训练也能涨点"：94.1 是怎么来的

摘要里最抓眼球的承诺之一：扩记忆就能涨点，不用重训。§4.2 的 "Scaling with Memory Size" 给了数据：用 SimScale [40] 合成额外场景，把记忆从 4K 扩到 10K，基座参数完全不动，PDMS 从 92.3（Base）涨到 94.1（Scale）。

先说好的：作者把两行数字都摆在 Table 1 里了——DriveVLA-M0-Base 92.3、DriveVLA-M0-Scale 94.1，没有把 94.1 伪装成默认配置。记忆条目是 $(k,x,y)$ 三元组，写入不需要梯度，所以"训练无关的扩容"在机制上是自洽的：检索池变大 → 更可能捡到高度相关的失败案例 → TTT 的监督质量更高。

再说怀疑的三点。第一，SimScale 是"真实世界规模仿真"生成的合成数据，**合成场景和 navtest 的分布关系论文没有讨论**。+1.8 的增益里，多少是"更多相关经验"，多少是"合成数据恰好覆盖了测试集的长尾"，拆不开。如果合成器本身见过类似 navtest 的场景（都是 nuPlan/OpenScene 系的数据源），那这个"训练无关"的涨点里就藏着数据层面的信息泄露——论文没有做这个对照。

第二，Navhard（NAVSIMv2）只报告了 Base 配置的 47.0 EPDMS，没有 Scale。摘要把 "94.1 PDMS on Navtest"（Scale 配置）和 "47.0 EPDMS on Navhard"（Base 配置）并列，**没说明两个数字来自不同配置**。不算错，但读摘要的人会默认是同一个模型。

第三，横向看：不加合成记忆时，Base 的 92.3 略低于同样做 TTT 的 Centaur（92.6，arXiv'25）。94.1 的 SOTA 位置，1.8 分里有 1.8 分来自记忆扩容。**这篇论文的 SOTA 数字，一半是方法挣的，一半是数据（合成记忆）挣的**。作者没有藏这个信息，但读者要自己算这笔账。

## 延迟那笔账：26.44ms 到底是什么

Table 6 给了分项延迟（单张 NVIDIA H20，4K 记忆）：

| 检索 | 前向 | LoRA 反向 | 全量反向 |
|---|---|---|---|
| 15.19ms | 30.79ms | 26.44ms | 55.42ms |

摘要的 "only 26.44 ms TTT backward latency overhead" 指的是**单步 LoRA 反向传播**。但默认配置是 3 步 TTT，每步在检索案例上都要前向+反向；触发时还要先花 15.19ms 检索。论文没有给"触发一次 TTT 的端到端延迟"，也没有给触发率——navtest 里百分之几的场景走了 TTT 未知。所以"适度开销"的完整账本是算不出来的：最坏情况下，一个场景的额外开销是检索 + 3×(前向+反向) 的量级，而不是 26.44ms。

公允地说，作者给了分项表而不是只报一个总数，这比很多论文诚实；26.44 vs 55.42 的对比也是实的，说明了 LoRA 的效率价值。但摘要把单步反向延迟写成 "TTT overhead"，是把最好看的那个分项拎出来当了门面。

还有一个部署细节在附录 B：NAVSIM 里有很多"空旷路段"（无周围车辆行人），这时 agent embedding 全是噪声。作者的做法是分层检索——先用 map embedding 粗筛 top-$k_1$（$k_1 = 3k_2$），再用 agent embedding 精选 top-$k_2$（$k_2 = 3$）。这是个聪明的工程补丁：**动态特征在空场景下是噪声源，先用静态特征把候选池限定在"路长得像"的范围内**。它也侧面印证了"解耦"的价值：两路特征失效模式不同，可以互相做守门员。

## 作者的底牌是什么

从论文的组织方式反推，作者手里有三张牌，一张比一张硬。

第一张是**结构化检索的单调性证据**（Table 3）：lang 90.7 → map 91.7 → map+agent 92.3，基座 91.0。检索键每向"结构"走一步，分数涨一截；走错一步（lang）反而掉分。这张牌的价值在于它把一个设计选择（解耦检索）变成了几乎无法反驳的实证序列。审稿人可以质疑很多东西，但很难质疑一个单调递增的消融。

第二张是**LoRA 在测试时的正则化红利**：TTT Full 和 TTT LoRA 只差 0.1（Table 4），超参大范围不敏感（Table 8）。这张牌回答的是测试时训练最致命的质疑——"在线梯度更新会不会把模型搞坏"。作者的答案是：低秩+小步数+每场景重置，天然就是安全的。这是一个"不增加风险、只增加收益"的设计，审稿人很难投反对票。

第三张最硬：**前视单目达到 SOTA**。Table 1 的 Input 列值得逐行看：DriveSuprim（93.5）用三前视相机，Centaur（92.6）用三前视，iPad（91.7）用环视；DriveVLA-M0-Base/Scale 只用**前视单目**，拿到 92.3/94.1。输入更少、分数更高——这张牌打的是"我们的方法不需要堆传感器"的故事，对 ACM MM 这种偏系统的会的审稿人口味很正。

会议口味也值得一说。NAVSIM 是驾驶社区的标准尺子，但"记忆+检索+测试时适应"的故事框架是多媒体/系统会议熟悉的语言（JARVIS-1、MemGen 这些引用就是写给 MM 审稿人看的）。同期竞品里，ELF-VLA（CVPR'26）也在做"从失败中学习"，但走的是离线 RL 路线；Centaur（arXiv'25）也在做 TTT，但用的是无监督的聚类熵目标。这篇的差异化位置很清晰：**有监督的失败记忆 × 场景特异的在线适应**——两个维度各踩了一个竞品的对立面。

## 怀疑式阅读：数字逐个过堂

把前面散落的质疑收拢，逐条给结论。

**站得住的**：Table 3 的检索策略消融（隔离了检索键设计，结论单调）；Table 4 的注入策略对比（隔离了"场景特异 vs 全局"，0.1 的 Full-vs-LoRA 差距说明低秩约束不伤性能）；Table 8 的 TTT 鲁棒性（0.3 的浮动范围，支撑"在线更新安全"的说法）；Table 6 的分项延迟（26.44 vs 55.42 的对比是实的）；前视单目 SOTA（输入列的对比无水分）。

**缺信息的**：$L_{TTT}$ 无显式公式（复现缺口，见上）；记忆去重的余弦阈值未给；$\beta = 0.5$ 无敏感性分析（为什么不是 0.4 或 0.6）；TTT 触发率未报告（平均延迟算不出）；$M$（轨迹 mode 数）、$K$（子分数个数）的具体值未在正文给出；Navhard 无 Scale 配置；合成记忆与测试集的分布关系未讨论。

**笔误/小瑕疵**：附录 D 学习率范围笔误（正文 $2\times10^{-5}$–$5\times10^{-5}$ vs 表格 $5\times10^{-5}$–$2\times10^{-4}$）；正文把 MemoryVLA [36] 放在驾驶语境下描述（"introduces perceptual-cognitive memory into VLA planning"），实际那是 robotic manipulation 的工作；摘要并列了两个配置的数字（94.1@Scale/Navtest，47.0@Base/Navhard）而未说明。

**代码诚实性**：论文写 "The code is available at https://github.com/ZebinX/DriveVLA-M0"。2026-10-14 核实：仓库存在（34 star，Apache-2.0），内容是 NAVSIM 1.1 部署包——Base Model、Retrieve Model、评测脚本、文档，**没有记忆生成和 Decoupled LoRA TTT 的代码**。技术上"有代码"不算虚假陈述，但论文最核心的两个机制（失败记忆的构建、测试时注入）无法从公开仓库复现验证。README 里 Hugging Face 权重链接在抓取快照中显示为占位账号，权重是否可下载未确认。复现这篇论文，目前只能复现它的基座和检索器。

**基线选择**：Navtest 对比了 16 个方法，覆盖经典 E2E 和 VLA 两类，算是齐全；Navhard 上"很多 VLA 方法还没报数"，主要和 E2E 强基线比，这个说明是诚实的。直接竞品 ELF-VLA（同样"从失败中学习"，CVPR'26）在 Table 1 里出现了（91.0 vs 94.1），但论文没有在正文里正面讨论"离线失败学习 vs 在线失败适应"的差异——related work 里提了一句，没有展开打，这是个小遗憾，因为这正是这篇论文差异化最锋利的地方。

## 与 RAMP 的血缘/划界

DriveVLA-M0 是"记忆 + 测试时"这条轴上，离 RAMP 最近的公开邻居。先把血缘说清楚，再划界。

**血缘有三处**。第一，两边都认为**失败/风险是最有信息量的信号**，都给它配了专门的情景记忆：DriveVLA-M0 的记忆只存 $Q(\hat{\tau}) < 0.5$ 的失败案例，RAMP 的情景记忆按风险加权——都是"不平均对待所有经验"的记忆观。第二，两边都做**测试时适应**：DriveVLA-M0 推理时检索+TTT，RAMP 推理时记忆检索权重自适应——都不动基座/骨干的离线参数。第三，两边都把**结构/异构**当作设计原则：DriveVLA-M0 把检索键解耦成静态路网与动态交互两路，RAMP 把规划器池做成异构的、把世界模型的前向复用做成异构的——都是"一路表示不够用，要分开处理"的思路。

**划界有四条**，每条都决定 related work 里怎么写它。

第一，**参数化 vs 非参数的测试时适应**。DriveVLA-M0 的适应是参数化的：每个场景重新初始化 LoRA，做 3 步梯度更新，把检索知识**写进权重**（用完即弃）。RAMP 的适应是非参数的：记忆只调检索权重，规划头的参数不动。这是两者在"记忆+测试时"轴上最本质的分岔——一个相信"临时改参数"，一个相信"参数一个字都别动"。有趣的是，Table 8 给 DriveVLA-M0 的参数化路线提供了安全论据（不敏感、难搞坏），而 RAMP 的非参数路线天然就没有这个风险。两条路线的优劣，取决于"改参数的收益"是否大于"改参数的风险"，目前没有 head-to-head 的证据。

第二，**失败二值筛选 vs 风险连续调制**。DriveVLA-M0 的记忆写入是二值的：$Q < 0.5$ 存，否则丢；记忆内部没有"多失败"的排序，也没有遗忘机制（只有去重）。RAMP 的记忆按风险等级连续调制衰减速率——高风险忘得慢。这两条是**正交可叠加**的：完全可以设想一个"失败感知 + 风险加权衰减"的记忆，既按失败筛选写入，又按风险调制遗忘。写 related work 时，这是一个现成的 future work 句式。

第三，**单规划器 vs 多规划器池**。DriveVLA-M0 只有一个基座规划器（VLA + Action Decoder），"调度"只发生在分数融合层（Static/Dynamic LoRA 各管一类子分数）。RAMP 的 (a) 是 LLM 调度异构规划器池——这是架构层面的差异，DriveVLA-M0 没有规划器选择问题，它的问题是"怎么把检索知识注进唯一的规划器"。

第四，**世界模型与风险仲裁的缺席**。DriveVLA-M0 没有世界模型先验（RAMP 的 (b)），它的"校验"只是开环的 PDM 打分选轨迹——用 oracle scorer 给候选打分、挑最高分，没有独立 rollout 做风险仲裁（RAMP 的 (d)）。它的安全论据来自"检索到的失败案例把轨迹簇推向了安全区"（Figure 4），而不是"有一个独立的模块在验证"。这是 related work 里必须写清楚的一句：两者都谈"安全"，但 DriveVLA-M0 的安全是**纠正式**的（把错的改对），RAMP 的安全是**校验式**的（独立的第二双眼睛）。

**一句话 related work 定位**：DriveVLA-M0 是"记忆+测试时"轴上与 RAMP 最近的公开工作——同样用失败/风险驱动的情景记忆做测试时适应，但它把检索到的失败案例做参数化注入（每场景重置的 LoRA 梯度更新），RAMP 走非参数路线（记忆只调检索权重、规划头不动）；它的记忆按失败二值筛选、RAMP 按风险连续调制衰减，两条轴正交可叠加；此外它没有多规划器池、没有 LLM 调度器、没有世界模型先验，风险"校验"只是开环 PDM 打分选轨迹，而非独立 rollout 仲裁。

## 能带走的东西

这篇论文留下的可迁移想法有两个。第一个是**检索键必须和下游任务对齐**：Table 3 里 lang 检索不如不检索，这个 90.7 < 91.0 的数字应该贴在每个做 RAG-for-driving 的人的墙上——"拿现成的 VLM 特征当万能检索键"在驾驶规划上是行不通的，因为规划要的是拓扑和动态，不是语义。RAMP 的情景记忆检索如果直接用 VLM 特征，可能会踩同一个坑；DriveVLA-M0 的解耦检索（静态路网/动态交互分开）是一个现成的参考设计。

第二个是**测试时参数更新的安全垫设计**：零初值 LoRA（更新前行为恒等于基座）+ 低秩约束 + 小步数 + 每场景重置，这四件套合在一起，让"推理时做梯度下降"从一个吓人的想法变成一个可部署的选项。Table 8 的不敏感性是这套设计最好的广告。RAMP 如果未来考虑任何参数化的测试时组件，这四条是 checklist。

真正值得做的具体问题也有两个。第一，DriveVLA-M0 的记忆是只增不减的（除了去重），没有遗忘机制——RAMP 的风险加权衰减正好补这一块，"失败感知写入 × 风险调制遗忘"的混合记忆是一个没人做过的设计点。第二，$L_{TTT}$ 的缺失意味着"检索知识到底该以什么目标注入"还是开放问题：DriveVLA-M0 用的是和基座训练相同的 $L_{traj} + L_{score}$，但检索案例是"别人的失败"，当前场景是"我的现在"，两者之间的 domain gap 在 TTT 目标里没有任何显式处理——一个显式建模"检索案例与当前场景差异"的 TTT 目标，是这条路线上下一步最自然的增量。
