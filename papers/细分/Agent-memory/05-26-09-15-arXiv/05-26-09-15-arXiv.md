## 2. 作者到底在跟什么死磕？——从三个部署痛点到设计定型

**前人真正撞墙的场景。** 引言点名的不是学术 benchmark 分数，而是三个部署时会变成事故报告的痛点：第一，合规与可更新性——交通法规按国家、州、甚至市镇变化，还随时间修订，把规则塞进模型权重或长提示词里，验证难、更新贵；第二，可追溯性——安全 case 要求事后重建"当时依据哪条规则、看到了什么才给出这个建议"；第三，延迟与鲁棒性——一次大推理同时做感知、规则推理和决策，又慢又容易在分布外翻车，尤其当"标志+暴雨+车辆故障"多因素叠加时。这三个痛点直接对应后文 Table I 的五行设计需求。

**作者的底牌。** 三张牌分别来自三个社区：Model Context Protocol（MCP，工具发现与结构化调用的标准接口，论文引 [15]），DriveLM（ECCV 2024 的图结构视觉问答驾驶模型，引 [5]），以及 RSS（Mobileye 的责任敏感安全形式化，引 [20]）。底牌的组合方式是关键：作者没有选"更大的端到端 VLM"，而是选了"VLM 当感知前端 + 外部专家服务 + 显式仲裁器"的分工。论文反复强调一句定位（第 2 页）："目标不是用 LLM 替代已认证的 ADAS 控制器，而是构建一个辅助层"——这是一个 ADAS 论文，不是自动驾驶论文，这个定位决定了后面所有实验的解读方式。

**从朴素尝试到定型的生成过程**（以下为基于正文结构的推断，已标明）。最朴素的尝试是 VLM-Direct：单次 DriveLM 推理，读图加一段文字版感知摘要，直接输出建议。它撞的墙是合规——跨司法管辖区时违规率最高（CROSS-BORDER 0.9 次/10km，Table V）。第二次修正是 VLM-Direct+RAG：把检索到的法规段落拼进提示词。违规降了（0.9→0.5），但延迟从 0.61s 涨到 0.71s，hazard response 几乎没动（1.02→0.95s）——上下文变长拖慢了推理，而"知道规则"不等于"反应更快"。第三次修正是 VLM-Tools-NoArbiter：事件驱动选工具、并行调用、结构化 JSON 传 world_state。违规再降（0.5→0.3），hazard response 大幅改善（0.95→0.70s）——工具分工确实干活了。但它撞上最后一堵墙：没有显式安全过滤时会触发不必要的 escalation。于是定型为 DriveMCP：加上 RSS/TTC 仲裁器，用一条不等式决定 speak 还是 act。四个基线的排列本身就是一篇"设计修正史"，Table IV 把检索/工具/仲裁三个开关做成了正交的消融维度，这一点做得干净。

**一个容易被忽略的设计原点。** 第 4 节开头有个很硬的决定：关键合规字段（限速、司法管辖区线索）不从仿真器真值直接注入，而是走 `image → DriveLM → sign reading → parser → speed_limit_kph = 80`（公式 1）。作者宁可承受 DriveLM 读错的风险，也要让"感知不完美"真实地流进下游——因为只有这样，world_state 腐蚀实验（第 8.D 节）才有意义。这是一个"为了诚实度量而主动放弃作弊"的选择，后文所有鲁棒性数字都建立在这个决定上。

## 3. 承重墙在哪里？——四个真干活的设计与三处装饰

先看总装图，确认数据流向（论文第 4 页 Fig. 1）：

![](/home/hatch/workspace/github-release/agentic-driving-paper-xray/papers/细分/Agent-memory/05-26-09-15-arXiv/fig-1.png)

*看这张图抓住三条线：左路"传感器→感知栈/DriveLM→world_state 构建器"是事实生产线；中路 Orchestrator（状态图）按事件选中路三个 MCP 服务器并行调用；右路"融合→安全仲裁→HMI 输出"是决策线。注意 DriveLM 的输出必须先过 parser 才能进 world_state，VLM 没有直通决策的捷径。*

**承重设计一：事件驱动的工具路由（公式 2）。** Orchestrator 每个 tick 把 world_state 变成离散事件集合 E = {ei | gi(φ(world_state), c(world_state)) > ηi}，只有事件命中的工具才被调用。事件例子：foreign_sign、jurisdiction_change、dynamic_limit_update、low_friction、vehicle_fault。这套机制同时解决 Table I 里的两行需求：实时性（不相关的工具不调用，省延迟、省打扰）和鲁棒性（低置信度解析触发保守回退，而不是硬路由）。置信度门限 ηi 是整套"保守主义"的阀门。

**承重设计二：Rules 服务器的混合检索 + rulepack 版本化。** 这是论文里工程思考最密的一节。检索分数 S(q,d) = (1−λ)·BM25(q,d) + λ·cos(φ(q),φ(d))（公式 4），稀疏管精确匹配（标志编号、法条原文），稠密管语义（"环岛路权"这类问法）。rulepack 是按司法管辖区打包的版本化法规束：交通法条摘录 + 标志表 + 单位元数据（km/h vs mph、左行 vs 右行），带语义版本号和内容哈希。实验用了三个：DEU-v1（km/h 右行）、GBR-v1（mph 左行）、DEU-v1-VSL（可变限速龙门架+"when wet"条款）。冲突裁决有显式优先级：成文法 > 官方标志表 > 次级指引，仍有歧义取最保守限速；rulepack 过期（effective_date 比车载配置旧）则降置信度、回退保守建议。消融实验里"去掉 Rules 的 RAG"让 CROSS-BORDER 违规从 0.20 飙到 0.90（Table VIII），说明这整套东西是跨司法管辖场景下唯一真正的承重墙。Rules 服务器内部的检索流水线如下（论文第 5 页 Fig. 2）：

![](/home/hatch/workspace/github-release/agentic-driving-paper-xray/papers/细分/Agent-memory/05-26-09-15-arXiv/fig-2.png)

*看这张图注意三处：左上虚线框是 MCP 工具封装（JSON schema + policy gates + 查询缓存），中间虚线框是检索增强步（混合 scorer 从版本化 rulepack 里取 top-k 段落），最右输出 rules_out 永远携带 citations、confidence 和 rulepack_version——可审计性是焊死在输出 schema 里的，不是事后补的。*

**承重设计三：speak-vs-act 仲裁器（公式 11–13）。** 干预被建模为比建议更高代价的动作：Uact = r − Cact − Cerr，Uspeak = Badv·r − Cfat；决策规则是 ACT 当且仅当 (Uact − Uspeak) > Δ 且 rss_viol = 1，否则一律 SPEAK。这个设计的硬核之处在于那个合取项：RSS 违例是动手的必要条件，不是充分条件——先有"解析式安全条件被违反"的事实，再谈效用是否划算。这是一种"保险丝"思维：把"能不能动手"的开关从 LLM 的自由裁量里拿出来，交给可审计的参数表（Table II 全部列出）。但这节有个数学上的大问题，留到第 6 节细说。

**承重设计四：world_state 的三元组表示。** 每个字段存成 (value, confidence, provenance)，provenance 记录字段来自感知栈、DriveLM 解析、CAN/OBD 还是地图，外加时间戳。缺失或低置信字段留空不填，由事件提取和安全层的保守默认接管。这套表示是"可追溯性"需求的真正载体——事后审计能精确定位到"这条限速是 DriveLM 在 14:02:11 读的，置信度 0.62"。

**装饰一：MCP 协议本身。** 论文标题里最显眼的词，恰恰是最不承重的一层。MCP 在这里的实际用法就是：带 JSON schema 的工具目录 + 结构化调用/返回 + capability 分级（纯上下文工具始终启用，可能影响动作的工具默认禁用、需带外授权）+ 调用日志哈希。这套东西完全可以用普通 RPC 实现；"增量更新 rulepack 不用重训"、"热插拔新服务器"的故事在实验里一次也没有被真正演练（三个服务器全程固定，rulepack 从未在线更新）。MCP 是好的工程接口选择，但论文的实证增益里没有一分来自"MCP"这个协议本身。

**装饰二：GVQA 的图结构。** DriveLM 的卖点是图结构视觉问答，但 DriveMCP 实际只用了它"读标志牌文字"这个扁平事实提取能力，图上的逻辑依赖（感知→预测→规划）在 pipeline 里没有对应物。公式 1 的 parser 之后，GVQA 的图就消失了。

**装饰三：多进程 RPC 架构。** Orchestrator、检索服务、三个 MCP 服务器、日志/记忆服务拆成六个进程经 RPC 通信（第 7.A 节）。这是实现细节，对论文的科学主张没有增量，延迟数字反而因此更难解读（见第 6 节）。

**MCP 在驾驶系统中的具体用法**（值得单独说清，因为标题党容易误导）：三个服务器暴露的工具语义分别是——Rules：`get_compliance(q, j, w)`，输入驾驶员问题 q、司法管辖区标签 j、世界上下文 w，输出 {legal_action, limit, citations, confidence} 外加 rulepack_version；Weather：输出 {µest（摩擦系数估计）, risk_level, speed_factor, confidence}，其中 speed_factor 把法定限速缩放成牵引力感知的建议速度；MCP-CAN：解码 CAN 帧（DBC 定义）、读 OBD-II 故障码（DTC），默认只读。调用策略：按事件选择性调用、多因子场景并行调用、路由段 TTL 缓存、单工具超时、超时则本 tick 降级为纯 SPEAK 保守建议（迟到的响应留到下一个 tick）。这套"选择性+并行+缓存+超时降级"就是论文"sub-second advisory latency"说法的全部支撑。

## 4. 公式逐个拆开：每个符号的形状、含义和一次手算

**公式 2——事件提取（工具路由的总开关）。** E = {ei | gi(φ(world_state), c(world_state)) > ηi}。φ(·)：world_state 上的特征函数，输出向量（比如 [标志类别 one-hot,  jurisdictiton_tag, 车速, DTC 标志位…]）；c(·)：各字段的置信度向量；gi：第 i 个事件检测器，可以是规则（"新解析出的标志且置信度 > 阈值"）也可以是学出来的分类器，输出标量分数；ηi：该事件的触发阈值。小实例：φ 抽出 {sign_class=限速牌, jurisdiction=DEU, parsed_value=80}，c 给出 DriveLM 解析置信度 0.85；foreign_sign 检测器 g 输出 0.85（规则型：jurisdiction ≠ home 且 c > 0.7）；η=0.7，0.85 > 0.7，事件触发 → Orchestrator 调用 Rules MCP。几何意义：这是在"特征×置信度"空间里画了若干个带软边界的触发区，只有落进区的事件才配消耗一次工具调用。

**公式 4——混合检索分数。** S(q,d) = (1−λ)·BM25(q,d) + λ·cos(φ(q), φ(d))。q：查询串（驾驶员问题 + 事件标签）；d：法规文档段落；φ：embedding 模型（输出 dense 向量，维度未报告）；λ∈[0,1]：稀疏/稠密权重，按语料类型调（成文法 vs 标志表），具体取值未报告。两项的量纲都是"相关度分数"，加权平均后取 top-k。小实例：查"roundabout right-of-way"，某段落 BM25=0.9（逐字命中"right-of-way"）、cos=0.4；λ=0.5 时 S=0.65。物理意义：BM25 是"字面证据"，cos 是"语义证据"，λ 是作者对"法规问答里字面命中更可信"这个先验的旋钮。

**公式 7、8——TTC 与 RSS 违例旗。** TTC = d / max(ε, Δv)：d 是与前车的相对距离（米，标量），Δv 是接近速度（米/秒，标量；远离时为负），ε=0.1 是分母下限（Table II），防止 Δv→0 时 TTC 爆炸。rss_viol = 𝟙[d < dmin(v, µest)]：示性函数，当前间距小于最小安全间距时取 1。几何意义：TTC 是"按当前接近速率，还有几秒撞上"——时间维度的风险；rss_viol 是"按保守刹车模型，现在这个间距已经兜不住了"——空间维度的二值 verdict。

**公式 14——最小安全间距。** dmin(v, µest) = v·tr + v²/(2·abrake(µest)) + d0，abrake(µest) = µest·g。三项分别是：反应距离（tr=0.7s，论文称这是 ADAS 安全模型常用的保守人类反应时间假设）、以估计摩擦系数为上限的匀减速刹车距离、静止缓冲 d0=2.0m。µest 取雨天估计区间的下界——处处取保守值，这是全文"conservative by construction"风格的一个缩影。

**公式 9、10——健康分与风险分。** h = σ(Σk wk·ψk(can_signals))：ψk 是归一化健康指示器（ABS 故障=1/0、刹车温度高、胎压低等，无量纲标量），wk 是权重（未报告），σ 是 squash 函数（把加和压到 [0,1]，具体形式未报告）。r = α·max(0, (τ−TTC)/τ) + β·rss_viol + γ·h：三项分别是 TTC 紧迫度（τ=2.5s 为参考，TTC 越小项越大，上限 α）、RSS 违例旗（权重 β）、车辆健康恶化度（权重 γ）；Table II 给 α,β,γ = 0.6, 0.3, 0.1。r 无量纲，上限为 1.0（TTC→0 且 rss_viol=1 且 h=1 时）。

**一次完整手算（走 SPEAK 路径）。** 取 v=25 m/s（90 km/h），µest=0.5（潮湿路面），g=9.81：abrake=4.905 m/s²；dmin = 25×0.7 + 625/(2×4.905) + 2 = 17.5 + 63.7 + 2 = 83.2 m。前车 d=40 m、Δv=6 m/s：TTC = 40/6 ≈ 6.67 s；rss_viol = 𝟙[40 < 83.2] = 1（间距已小于保守刹车模型要求——注意 40 米在 90 km/h 下确实偏近）；r = 0.6×max(0,(2.5−6.67)/2.5) + 0.3×1 + 0.1×0 = 0.3。效用：Uact = 0.3 − 0.4 − 0.2 = −0.3；Uspeak = 0.6×0.3 − 0.05 = 0.13。Uact − Uspeak = −0.43，不大于 Δ=0.2 → SPEAK。翻译成动作：系统判定"间距偏近但接近速率不高"，选择语音/文字建议减速，而不是触发有界干预。

把 (11)(12) 代入决策不等式左边：Uact − Uspeak = r(1−Badv) − (Cact + Cerr − Cfat) = 0.4r − 0.55（代入 Table II：Badv=0.6, Cact=0.4, Cerr=0.2, Cfat=0.05）。r 的理论上限是 1.0，所以左边的理论上限是 −0.15——**恒小于 Δ=0.2**。这个算术后果放到第 6 节展开，它是全文最值得细看的一个裂缝。

**公式 15、16——有界在线自适应。** Δ ← [Δ − klate·nlate]（钳在 [Δmin, Δmax] 内），Cmin ← [Cmin + kfp·nfp]（钳在 [Cmin, Cmax] 内）。nlate 是 late_warning 反馈计数，nfp 是 false_positive 计数。直觉：迟报多了 → Δ 缩小 → 更容易 ACT（减少迟报）；误报多了 → Cmin 抬高 → 更难干预（压制误报）。单调、无振荡。但两个硬伤：Cmin 在全文其他地方没有定义（推断是干预的最低置信度门槛，原文未明说）；klate、kfp、四个边界值全部未报告。消融显示去掉反馈自适应只让 CROSS-BORDER 违规从 0.20 升到 0.26（Table VIII）——这部分是"有比没有好"的点缀，不是承重墙。

## 5. 实验数字放在什么条件下才成立

**实验台。** CARLA 0.9.8（注意是 0.9.8，不是现在常用的 0.9.15），多 town、日夜光照、天气可控。三个场景族：URB-RAIN-MULTILINGUAL（暴雨+外语标志）、CROSS-BORDER（跨司法管辖区：标志惯例、左右行、km/h vs mph 切换）、DYNAMIC-VSL（可变限速龙门架+天气条件限速）。所有方法吃同样的传感器快照、同样的 DriveLM checkpoint、同样的 prompt 结构——基线隔离做得规矩。VLM-Direct 与 VLM-Direct+RAG 被 prompt 限制为只能输出建议（不能动手）；VLM-Tools-NoArbiter 与 DriveMCP 可给出有界动作建议，但只有 DriveMCP 过 RSS/TTC 仲裁器。每个条件跑 10 次，Table V 只给违规列报了 ±std，其余列只有均值。

**主表（Table V）的三层信息。** 第一层，RAG 改善合规但拖慢延迟：CROSS-BORDER 违规 0.9→0.5，延迟 0.61→0.71s——"知道规则"和"反应更快"是两回事，RAG 只解决了前者。第二层，工具层是真正的分水岭：VLM-Direct+RAG → VLM-Tools-NoArbiter，违规 0.5→0.3、hazard response 0.95→0.70s，延迟反而从 0.71s 掉到 0.27s（sub-second 的说法主要靠这一跳；为什么工具版比单次 VLM 推理还快，原文没解释清楚，见第 6 节）。第三层，仲裁器是"用一点 earliness 换更少误报"：DriveMCP vs NoArbiter，违规 0.3→0.2、超速 0.8→0.7%，但 hazard response 从 0.70 微升到 0.72s、首次升级时的 TTC 从 2.3 降到 2.1s——仲裁器让系统更克制，代价是升级稍晚。这个 trade-off 的方向是对的，但幅度很小：仲裁器贡献的增益远小于工具层。

**腐蚀实验（Table VI，CROSS-BORDER，DriveMCP）。** 干净栈：事件 F1 92%、正确工具率 94%、违规 0.2±0.1。标志漏检 30%：事件 F1 掉到 70%、违规升到 0.8±0.3——合规链路对"看见标志"高度敏感；actor 丢失 30%：hazard response 从 0.72 恶化到 1.05s，但违规只到 0.5——跟踪丢失主要打的是 hazard 响应，不是合规。这个"哪种腐蚀打哪条链路"的分离度，是全文实验设计里最诚实的一块：它承认了 pipeline 的脆弱点具体在哪。

**Δ 灵敏度（Table VII，DYNAMIC-VSL）。** Δ 从 0.0→0.4：干预频次 3.2→0.9 次/10km，误报率 18%→4%，升级时 TTC 2.3→1.9s。单调 trade-off，符合预期：Δ 越大越不轻易动手，误报越少，但升级越晚。Table II 取 Δ=0.2（干预 1.8 次/10km、误报 8%、TTC 2.1s）是中间点。

**消融（Table VIII，CROSS-BORDER，均值+95% CI，10 runs）。** 去掉 Rules 的 RAG：违规 0.20→0.90±0.19——断崖式，跨区场景下合规几乎全靠检索；去掉工具并行：只影响延迟 0.31→0.42s，违规几乎不动（0.20→0.24）——并行是纯工程优化；去掉 CAN 上下文：违规 0.20→0.22，纹丝不动——CAN 在合规场景里确实没用，它的战场在下一张表；去掉反馈自适应：0.20→0.26，小幅；Oracle（仿真器真值替代 DriveLM 解析）：0.20→0.15——DriveLM 解析与真值的差距只值 0.05，说明在这组场景里感知不是瓶颈。

**CAN 故障注入（Table IX，制动退化 + ABS 故障/低胎压 DTC，视觉场景不变）。** DriveMCP 建议目标车速 65 km/h（VLM-Direct 78、RAG 77、NoArbiter 70），升级时 TTC 2.2s（vs 1.5/1.6/2.0），near-collision 0.2 次/10km（vs 0.9/0.8/0.4）。这是 CAN 服务器唯一的高光时刻：视觉看不见的制动退化，只有读 DTC 的链路能捕捉。但注意基线选择：VLM-Direct 和 RAG 在结构上就看不见 CAN 信号，拿它们当陪跑有"田忌赛马"的味道；真正有信息量的对比是 NoArbiter（70 km/h）vs DriveMCP（65 km/h）——仲裁器在健康分 h 的加持下更保守。

**基线选择评价。** 公平的一面：同一 DriveLM checkpoint、同一传感器快照、固定 prompt 结构，四个基线把检索/工具/仲裁做成了正交开关，NoArbiter 对仲裁器的隔离尤其干净。缺的一面：没有"不用 MCP 的普通工具调用"基线（比如 ReAct 风格的 LLM+tools），所以"MCP 协议"这个标题级主张没有任何对照；没有非 VLM 的传统 ADAS 基线；没有闭环驾驶 benchmark（Bench2Drive/CARLA Leaderboard 都没跑）——这与论文"辅助层"的自我定位一致，但也意味着所有"减少违规"的数字都是在"建议质量"层面度量的，没有一辆车真的被这些建议开起来过。

## 6. 怀疑式审读：证据链哪里薄，先说最硬的一处

**最硬的一处：按白纸黑字的公式和参数，ACT 分支数学上不可达。** 把公式 (11)(12) 代入决策不等式左边：Uact − Uspeak = r(1−Badv) − (Cact+Cerr−Cfat)。代入 Table II（Badv=0.6, Cact=0.4, Cerr=0.2, Cfat=0.05）得 0.4r − 0.55。而 r = α·max(0,(τ−TTC)/τ) + β·rss_viol + γ·h 的理论上限是 α+β+γ = 1.0（TTC→0、rss_viol=1、h=1 同时成立时）。于是 Uact − Uspeak ≤ −0.15，恒小于 Δ=0.2——注意是对一切 Δ≥0 都成立。可是 Table VII 在 Δ=0.2 处报告了 1.8 次干预/10km、8% 误报率；在 Δ=0.0 处还有 3.2 次/10km。公式说"一次都不会动手"，表格说"每 10 公里动手近两次"，两者对不上。公平起见，三种可能：一是 Table II 的常数与实验代码里的不一致（比如代码里 Cact 更小）；二是 Table VII 的"intervention"计数口径与公式 (13) 的 ACT 定义不同（比如把强建议也算了进去）；三是公式 (11)(12) 有笔误。无论哪种，审稿人按图索骥都会卡在这里——这是正文、公式、表格三处互锁的一个裂缝，作者需要澄清。Table VII 自身的单调趋势（Δ 越大干预越少、误报越低、升级越晚）倒是自洽的，说明实验里确实有个随 Δ 单调变化的量，只是它可能不是公式 (13) 字面写的那一个。

**延迟数字的悖论。** 所有方法都跑同一个 DriveLM checkpoint 做事实提取/推理，VLM-Direct 的建议延迟却是 0.61–0.68s，而 VLM-Tools-NoArbiter 只有 0.25–0.27s。单次 VLM 推理怎么会比"VLM 解析 + 事件提取 + 并行调三个工具 + 融合"还慢两倍多？原文没有解释。可能的解释是 VLM-Direct 每次生成冗长的自由文本建议，而工具链只做短结构化调用——但这只是推断。更关键的是：全文没有报告任何硬件/GPU 配置，"sub-second advisory latency"的说法挂在一个没有分母的数字上。延迟优化的四个手段（选择性调用、并行、缓存、超时）里，只有"去掉并行"被消融过（0.31→0.42s，Table VIII），其余三项的贡献都是断言。

**未定义与未报告的参数。** Cmin 只在公式 (16) 出现一次，全文没有定义（从上下文推断是干预的最低置信度门槛，但这是推断）；klate、kfp、Δmin/Δmax、Cmin/Cmax 全部未报告；混合检索的 λ "按语料调"，调完的值没给；事件检测器 gi 哪些是规则、哪些是学出来的、学出来的怎么训练的，没说；健康分里的 wk 和 squash 函数 σ 的形式，没说。这些不是吹毛求疵——Table II 之所以值得表扬（仲裁器常数全公开），恰恰反衬出其余参数的不透明。

**列为指标却没有数字的。** 第 8.F 节的指标清单里有"定性评分：通过 debriefing 问卷收集的解释清晰度与感知有用性"，但全文没有任何表格报告这两个数字。第 10.B 节讨论了双层解释设计（短指令 + 可选 justification），也停留在定性描述。既然人类因素是 ADAS 论文的核心，这组缺失的数字是个明显的洞。

**仿真与数据的老问题。** CARLA 0.9.8 是 2019 年左右的版本（当前 Bench2Drive 基线用 0.9.15）；DriveLM checkpoint 的具体版本未指明，而 DriveLM 本身在 CARLA 数据上训练过——训练/测试场景重叠的可能性没有被讨论，Oracle 消融（0.20→0.15）只能说明"解析接近真值"，不能排除"在见过的数据上解析得好"。路线总里程、towns、episode 数量未报告，"违规/10km"的归一化分母不透明。每个条件 10 次运行，只有 Table VIII 给了 95% CI，没有显著性检验。

**基线设计的"田忌赛马"。** CAN 故障注入实验里，VLM-Direct 和 VLM-Direct+RAG 在结构上就看不见 CAN 信号（prompt 里没有），拿它们对比"能不能利用 CAN"没有信息量；真正公平的对比是 VLM-Tools-NoArbiter（目标 70 km/h、near-collision 0.4）vs DriveMCP（65 km/h、0.2）——这一档对比依然支持结论，但增益幅度比表格第一眼看上去小得多。

**标题级主张没有对照实验。** "MCP 带来可更新性"的故事（rulepack 热更新不用重训）在实验里一次也没有发生：三个服务器全程固定，没有在线换过 rulepack，没有加过第四个服务器。同样，GVQA 的图结构推理在 pipeline 里没有对应物（parser 之后就是扁平字段）。这些属于"架构宣言"，不是"实证结论"，读的时候要分开。

**要给的 credit。** 作者在第 2.E 节和第 11.D 节两次明确声明：RSS/TTC 仲裁器是研究原型的透明护栏，不是认证安全机制，不替代认证的控制与制动系统。这种"我知道这不是安全认证"的清醒，在 VLM 驾驶论文里并不多见。world_state 腐蚀实验主动暴露 pipeline 的脆弱点（标志漏检 30% 时违规翻四倍），也是诚实分。以及，Table IV 把检索/工具/仲裁做成正交开关的基线设计，确实干净。

## 7. 与 RAMP 的血缘/划界：四个轴逐个过

先对齐 RAMP 的三块：**风险加权自适应衰减情景记忆**（高风险经历衰减慢、低风险衰减快，非参数检索）＋**世界模型单次前向复用**（每周期只做一次前向编码得到共同初始潜状态，各规划器的候选轨迹从该潜状态做 action-conditioned rollout）＋**闭环多规划器仲裁**（LLM/SLM 调度多个独立规划器，每个输出多条候选轨迹，风险仲裁选最优）。DriveMCP 与这三块的关系按四个轴拆：

**轴一 · 记忆机制：正交为主，工程细节可借用。** DriveMCP 的记忆是"事实缓存"：短期缓存存 world_state 快照和工具返回（带时间戳和有效期，去重、限流、复用），长期存储存 rulepack 版本历史、用户偏好（建议啰嗦度）、反馈标签。它记的是"工具刚才返回了什么"，且长期记忆没有任何基于风险的衰减——它的"自适应"（公式 15/16）调的是仲裁器参数 Δ/Cmin，不是记忆权重。RAMP 的记忆是"经验记忆"：记的是"上次遇到类似险情时发生了什么"，按风险加权衰减、按场景相似度检索。两者语义完全不同，这是划界。但工程上可借用一处：DriveMCP 给每条缓存打时间戳 + validity window、过期则刷新或降级的管理方式，正是 RAMP 情景记忆需要的 stale-control——记忆条目不能只有"风险权重"，还得有"新鲜度"，否则一次过时的高风险记忆会长期误导检索。

**轴二 · 规划器调度：划界为主，触发思想同构。** DriveMCP 没有规划器。它所谓的编排是"事件→工具路由"（公式 2），所谓的仲裁是"开口建议还是动手干预"的二选一，输出的是单条建议目标速度。RAMP 是 LLM/SLM 调度多个独立规划器、每个规划器输出多条候选轨迹、再做风险仲裁——仲裁对象是"轨迹集合"，层级完全不同。这是表面相似（都有 orchestration/arbitration 字样）实则不同的典型划界。但有一处血缘值得拿走：事件驱动的条件触发（只有相关事件才激活重型模块）与 RAMP 的"场景驱动动态模块旁路"是同一个思想的不同实例——"按需激活"这件事，DriveMCP 用公式 2 的置信度门限实现了，RAMP 可以参考它的事件本体设计（foreign_sign、jurisdiction_change 这类离散事件标签）来定义自己的旁路触发条件。另外，MCP 式的专家封装（JSON schema + capability 分级 + 调用日志哈希）可以直接套用到 RAMP 的多规划器封装上：每个规划器变成一个"工具"，调度器统一调用、统一审计——这是接口层面的直接血缘。

**轴三 · 世界模型使用：划界，可叠加。** DriveMCP 没有世界模型。离"预测未来"最近的三样东西是：常速卡尔曼跟踪器（短时外推 actor 位置）、µest 摩擦系数估计、TTC/dmin 解析式。没有潜变量、没有生成式 rollout、没有"如果我这么开会发生什么"的反事实推理。RAMP 的世界模型是每周期一次前向编码、各候选轨迹做 action-conditioned rollout——这是 DriveMCP 完全没有的一层。这是 clean 的划界。但正交可叠加：DriveMCP 的 TTC/dmin 解析式风险度量，可以直接作为 RAMP 风险仲裁器里的 cheap pre-filter——先用解析式把明显危险的候选轨迹快速筛掉，只对剩下的做重型 world-model rollout。这种"解析式粗筛 + 世界模型精排"的两级结构，DriveMCP 的公式 (7)(8)(14) 已经给了一个现成的、参数全公开的粗筛实现。

**轴四 · 闭环校验：部分血缘，校验对象不同。** DriveMCP 的校验链是：RSS/TTC 解析式护栏 → speak-vs-act 效用决策 → 超时降级为纯 SPEAK → 事后 trace 审计（工具调用、文档 id+偏移、风险计算全记录）。它的校验对象是"给人类司机的建议"，评估停留在"建议质量"层面（违规率、超速率），没有闭环驾驶控制评估；它自称的"闭环"其实是公式 15/16 的慢速反馈调参环，不是驾驶控制闭环。RAMP 的校验对象是"要执行的轨迹"，在 Bench2Drive 闭环基准上验证——这是划界。但有两处血缘可直接借用：第一，speak-vs-act 的显式代价建模（Cact 干预代价、Cerr 误干预惩罚、Cfat 驾驶员疲劳代价）是 RAMP 风险仲裁可以直接抄的模板——把"选哪条轨迹"写成带代价项的效用比较，而不是纯风险分数的 argmax，代价项让"保守"的程度可审计、可调参；第二，"RSS 违例作为高风险动作的必要条件"（公式 13 的合取项）是一个值得复制的保守性模式：RAMP 可以规定，只有解析式安全条件违例时才允许选择高风险机动。不过要记住第 6 节的裂缝：按 Table II 的常数，这个 ACT 分支数学上不可达——借用这个模板时，得先把参数重标定一遍，不能照抄 Table II。

| 轴 | 关系 | 一句话 |
|---|---|---|
| 记忆机制 | 正交为主、工程可借用 | DriveMCP 记"工具返回了什么"（事实缓存），RAMP 记"上次险情发生了什么"（经验记忆）；可借用时间戳+有效期的 stale 管理 |
| 规划器调度 | 划界为主、思想同构 | DriveMCP 没有规划器，仲裁的是"说/动手"二选一；可借用事件驱动的条件触发与 MCP 式专家封装 |
| 世界模型使用 | 划界、可叠加 | DriveMCP 无世界模型，只有卡尔曼外推与解析式；TTC/dmin 可作 RAMP 仲裁的 cheap pre-filter |
| 闭环校验 | 部分血缘、对象不同 | 校验对象是"建议"vs"轨迹"；可借用显式代价建模（Cact/Cerr/Cfat）与"RSS 违例为必要条件"模式，但 Table II 参数不可照抄 |

## 8. 一句话总结 + 关联阅读

**一句话。** DriveMCP 的价值不在"MCP"三个字母，而在它示范了一种分工纪律：VLM 只负责把图像翻译成带置信度的事实，法规知识住在可版本化的外部工具里，"能不能动手"由一条显式不等式说了算——读完这篇，RAMP 可以直接拿走的是它的代价建模模板、事件驱动触发和解析式粗筛，划清界限的是它的记忆语义、规划器调度和"建议而非轨迹"的校验对象。

**关联阅读**（均出自本文参考文献，编号为原文编号）：DriveLM [5]（GVQA 前端，理解"翻译官"角色的来源）；RAG-Driver [10]（检索增强的驾驶解释，DriveMCP 的 RAG 对照）；Shalev-Shwartz 等人的 RSS [20]（仲裁器解析式部分的源头）；ReAct [18]、MRKL [17]、Toolformer [19]（工具编排的思想谱系，读完会明白 DriveMCP 的编排为什么偏保守）；MCP 规范 [15] 与 LangGraph [16]（工程实现侧的两份手册）。

*读者可带走的一个想法：每当看到"agentic 驾驶框架"，先问三个问题——知识住在哪里（权重里还是工具里）、保险丝在谁手里（提示词里还是显式不等式里）、记忆记的是事实还是经验。DriveMCP 在前两个问题上答得清楚，在第三个问题上几乎交了白卷——而这正是 RAMP 要答的那一题。*
