# 把"做完之后发生了什么"告诉规划器:Inner Monologue 的闭环语言反馈

> **信息块**
> - 论文:Inner Monologue: Embodied Reasoning through Planning with Language Models
> - 作者:Wenlong Huang、Fei Xia、Ted Xiao(共同一作,按字母序)等 17 人,Google Robotics;arXiv 2207.05608 v1(2022-07-12,之后无修订版)
> - 会议:CoRL 2022(多方论文列表与项目页 https://innermonologue.github.io 均标注 CoRL 2022)
> - 链接:https://arxiv.org/abs/2207.05608
> - 代码:**未找到官方代码**(项目页只有视频与论文)。注意:SayCan 有限开源了 tabletop Colab,Inner Monologue 连这个都没有,三个实验域的代码均未公开
> - 一句话核心洞见:**LLM 开环规划的最大敌人不是"想得不够聪明",而是"做完之后没人告诉它发生了什么"——把成功检测、场景描述、人类回答翻译成文字、逐轮追加进 prompt,规划器就从"一次性算命"变成了"边做边改"的闭环。**

## 它到底补了谁的洞

时间线:SayCan(2022-04)用"LLM 打分 × affordance"选技能,但选完就执行,执行成没成 LLM 不知道;Huang et al. 的 zero-shot planners(2022-01,ICML 2022,一作正是本文一作 Wenlong Huang)用 prompt 让 LLM 直接生成多步计划,同样开环。两篇论文的共同假设是:**每一步都被成功执行**。在真实机器人上,这个假设第一天就破了:吸盘没吸住、物体被挡住、人中途改主意。

Inner Monologue 的起点就是把这个假设删掉。它的技术动作只有一句话:**把所有能拿到文字形式的环境反馈,在每一步之后追加进 LLM 的 prompt**。反馈分四种(§3.3,图 2):

- **Success**(成功检测):二分类——上一步做成了吗?"Success: False"。
- **Object**(被动场景描述):每步自动给,比如 MDETR 列出的可见物体清单。
- **Scene**(任务进度描述):语义子目标完成了几个,比如"已达成['黄块进蓝碗']"。
- **Human**(主动场景描述):LLM 自己提问,人(或 VQA 模型)回答,比如"抽屉是开着的吗?"→"关着。"这是开环规划里没有的信息获取动作。

用大白话说:SayCan 是"想好再做,做完不管";Inner Monologue 是"做一步、看一眼、再想下一步"。论文图 1 的例子:机器人去拿可乐,Success 反馈说"没拿起来",LLM 就再试一次,拿起来后再"送给用户"。没有 Success 反馈的开环系统,第一步失败后会继续执行"送可乐"——手里是空的。

## 三个实验域,三种配方

论文坦承(§3.2)这不是一个统一系统,而是一个**case study**(案例研究):三个域用了不同的 LLM、不同的技能、不同的反馈来源,共享的只是"反馈进 prompt"这个 formulation。

**域一:仿真桌面整理**(Ravens 仿真,InstructGPT 规划,CLIPort 做 pick-place,反馈全用脚本模块生成)。表 1:8 个任务(4 见过/4 没见过),50 回合平均,加测试时扰动。Object+Scene 最好;unseen 的"把块放进错配的碗"上,Object 62%、Object+Success 76%、Object+Scene 86%,而 CLIPort 基线(无 LLM)在 unseen 上全是 0%。**CLIPort 在 seen 任务上不加 oracle 终止只有 2~24%**,说明单步策略没有"做完了吗"的概念,这是层级系统的结构性优势,不是调参差距。

**域二:真实桌面整理**(UR5e + 腕载 RealSense,MDETR 做物体识别,吸盘脚本抓取,人工注入 4mm 动作噪声逼出失败)。表 2:两个任务各跑 10 次,Object+Success 总计 **90%**,纯 LLM 基线 20%。最能说明问题的是 3-block 堆叠:开环基线(只在开头看一次场景)因遮挡漏看了物体,只做一步就停了;闭环版每步重看、失败重试,100% 做成。

**域三:真实厨房移动操作**(直接复用 SayCan 的厨房、PaLM 规划、value 函数做 affordance grounding,加 learned 成功检测器 + 人工物体识别)。表 3:120 次评估,3 个任务家族 × (无扰动/有人为扰动)。总数:SayCan **30.8%**,+Success **48.7%**,+Success+Object **60.4%**。**有人为扰动时 SayCan 跌到 0~12.5%**(它没有重试逻辑,一步失败整串全废),Inner Monologue 变体 25~75%。图 4 的失败归因显示,Success 和 Object 反馈主要减少的是"LLM 规划失败",代价是引入新的失败模式(反馈模块自己错了)。

## 怀疑式审读:闭环的代价是"反馈从哪来"

**1. 反馈大多是 oracle(神谕,指用上帝视角或人工提供的完美信息),不是学出来的。** §5  limitations 自己承认:仿真域用脚本模块、厨房域用**人工**做物体识别。也就是说,"闭环"的下半环(环境→文字)靠的是开挂。在真实部署里,MDETR 会误检、成功检测器会误判——论文说误报的代价是"假阴性导致多试几次,假阳性等于给环境加了对抗性部分可观测"(§5 原话,这是个诚实的表述)。但**实验数字里没有量化反馈噪声对总成功率的影响**,附录表 5 研究了 learned 反馈的可行性,正文却用了 oracle 跑主结果——读者看到的 60.4% 是"反馈开挂版"的成绩。

**2. ReAct 的批评一针见血:"这不叫内心独白"。** ReAct §4 说 Inner Monologue 的"thought"只是环境反馈的复读。看论文图 5 的真实例子:"Robot thought: Goal state is […]."——这确实是在**复述目标**,不是在推理。真正的推理(目标分解、常识、异常处理)很少出现,智能主要来自反馈模块的设计,而不是 LLM 的思考。公平地说,Inner Monologue 的贡献本来就不是"让 LLM 更会想",而是"证明反馈有用";但名字"Inner Monologue"确实 oversell(过度包装)了。

**3. 反馈没有强制力,LLM 可以不听。** §5:"我们发现 LLM 规划器有时会忽略环境反馈,仍然提出涉及场景中不存在物体的技能"。整个闭环是软性的——反馈只是 prompt 里的文字,LLM 可以不看。没有校验、没有否决机制。这是 prompt-based agent 的通病,但论文没有讨论"当反馈和 LLM 先验冲突时,谁说了算"。

**4. SayCan 基线在扰动下 0% 有点胜之不武。** SayCan 从没声称能处理对抗扰动,它的设计目标就是开环选技能。拿"有扰动"打"没设计扰动恢复"的基线,赢是应该的。真正的信息在表 3 的无扰动行:SayCan 50~83%,+反馈后 62.5~100%——**反馈的价值在自然失败下也有,但差距比扰动行小得多**。论文把最戏剧化的数字放在前面,阅读时要自己把两行分开看。

**5. "涌现能力"一节是定性 demo,论文自己都打了折。** §4.4 的持续适应新指令、 infeasible 时自提目标、多语言、场景问答,全是单个例子,没有成功率统计。原文:"we observe that they are of varying levels of consistency"(一致性参差)。这些例子证明的是"LLM 的通用能力可以透过反馈接口用起来",不是"系统可靠地具备这些能力"。引用时只能当存在性证明,不能当性能声明。

**6. 三个域、三种 LLM、没有统一实现。** InstructGPT(域一/二)、PaLM(域三),技能从 CLIPort 到 SayCan 的全套不等。因为没有开源代码,后人无法复现任何一个域。这篇论文的定位更接近"position paper + 实证案例",它的引用价值在思想(闭环反馈),不在实现。

## Lineage:承上启下的"补丁论文"

往前:它是 SayCan(开环选技能)和 zero-shot planners(开环生成计划)的**直接补丁**——两篇的前作作者都在本文作者名单里(Wenlong Huang 是 zero-shot planners 一作,Fei Xia/Ted Xiao/Karol Hausman/Brian Ichter 横跨两篇)。可以说,Google 机器人团队在 2022 年 4~7 月走完了"开环→发现失败→闭环"的一个完整认知循环。

往后:ReAct(2022-10)把它做成自己的消融基线(ReAct-IM)并批评;Reflexion、Voyager 的自我验证都吸收了"执行后给 LLM 反馈"的思想。它的历史位置是:**第一个把"闭环"写成 LLM agent 一等概念的工作**——在此之前,闭环是控制论的词;在此之后,所有 agent 论文都要回答"你的反馈是什么"。

## 与 RAMP 的血缘/划界

Inner Monologue 与 RAMP 的关系:**闭环思想的直接血缘;但 RAMP 的"闭环"比它深两层**。

- **对"闭环风险校验/安全盾"模块:思想血缘最深,但校验对象完全不同。** Inner Monologue 的闭环回答的是"**上一步做成了吗**"(事后校验,靠成功检测器);RAMP 的安全盾回答的是"**这一步敢不敢做**"(事前校验,靠世界模型预测风险)。两者合起来才是完整的闭环:**事前用世界模型否决高风险候选,事后用执行反馈修正模型与记忆**。RAMP 的论文里可以把 Inner Monologue 定位成"reactive closed-loop"(反应式闭环:错了再改),而 RAMP 是"proactive + reactive"(前摄式:没做先算风险;反应式:做完更新记忆)。在驾驶里,只有反应式是不够的——撞了再改代价太大,这是 RAMP 必须做事前校验的论证起点。
- **对"LLM 在线多规划器调度"模块:弱正交。** Inner Monologue 的 LLM 一次只定一个技能,没有多候选比较;它的"调度"就是贪心单步。RAMP 的多规划器调度可以借鉴它的 prompt 组织方式(把反馈拼成结构化文字),但仲裁机制是新增的。
- **对"世界模型中间分布复用"与"情景记忆"模块:正交。** Inner Monologue 没有预测、没有记忆:反馈只活在当前 prompt 里,任务结束就扔。RAMP 的情景记忆恰好是把"有用的反馈"沉淀下来——Inner Monologue 证明了反馈有用,RAMP 回答"有用的反馈怎么存、怎么衰减、怎么按风险检索"。两者是上下游关系:Inner Monologue 是"反馈的消费者",RAMP 的记忆是"反馈的仓库"。

一句话:Inner Monologue 教会领域"**规划器必须看到执行结果**";RAMP 把这句话向前推了一步变成"**执行之前先看到预测结果**",向后推了一步变成"**执行结果要沉淀成风险加权的记忆**"。Related work 里把它放在"closed-loop agents"的起点,划界词是"reactive vs proactive"——ICAPS 审稿人对这种 planning 术语敏感的 framing 会很受用。
