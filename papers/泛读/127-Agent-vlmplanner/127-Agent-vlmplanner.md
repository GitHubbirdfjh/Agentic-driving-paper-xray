## 图 1 的三代划分：每一代在为什么还不够

论文用图 1 把 LLM 进规划的历史切成三代，这个划分比很多综述都清楚：

**(a) LLM/VLM 直接规划**：场景转成自然语言或 BEV 图，LLM 直接输出轨迹。死因有两个：token 限制吃不下细粒度场景；LLM 的数值计算和几何推理是弱项，轨迹精度差。

**(b) LLM 指导实时规划器**：AsyncDrive、LLM-Assist。LLM 不画轨迹，只给实时规划器"指导"。AsyncDrive 还把 LLM 解耦成低频固定频率。但它们的输入是**压缩过的感知/map 输出**——作者的核心论点：压缩丢掉了长尾细节。大水坑、打手势要转弯的自行车、潮汐车道——这些在感知输出里要么没有、要么要复杂推理才能提取，但**原图里直接看得见**。

**(c) VLMPlanner**：VLM 吃**多视角原图** + CAI-Gate 动态调频。

这个论证链条里最值得玩味的是 (b) 到 (c) 的那一步：作者不是在拼更大的 VLM，而是在争**输入的信息量**。"感知输出是压缩的，原图是无损的"——和 071 DriveAgent-R1 的"分辨率放大器"论点异曲同工（071 说的是裁高分辨率区域，这里说的是别用压缩过的感知结果）。2025 年的 LLM4AD 正在集体意识到：**VLM 的瓶颈不在模型，在喂给它的东西**。

## 架构：VLM 当"参谋"，不碰方向盘

图 2 的双路设计：

**快路（实时规划器）**：只吃 map 信息（自车/邻车历史状态、车道/斑马线特征，GameFormer 的 MapEncoder 编码），10Hz 跑，输出轨迹。这是保底——VLM 挂了，快路自己也能开（就是原来的 GameFormer/PlanTF）。

**慢路（VLM）**：LLaVA-v1.5-7b，吃四样东西——system message、导航指令（"Go straight for 110.9m"）、map token、**多视角图像 token**。图像处理是关键工程：CLIP 编码多视角图 → 3D 位置编码 $P_{3D}$ + Q-Former 式的 3D-aware 模块（可学习的 3D 参考点 $Q_{3D}$ 做 cross-attention，把图像特征投影到 3D 空间）→ ImgAdapter 对齐维度。3D-aware 模块一石二鸟：**降 token 数**（多视角图直接喂会爆 context）+ **提 3D 理解**。

**接口（Adaptive Injection Block，式 7，借自 AsyncDriver）**：取 VLM 最后一个 token 的隐状态 $h_n$，过 FeatureAdapter 得到 $\tilde{h}$，注入实时规划器解码器的每一层：

$s_{l+1} = g \cdot \text{MultiHeadAttn}(Q, K_{\tilde{h}}, V_{\tilde{h}}) + \text{MultiHeadAttn}(Q, K_{s_l}, V_{s_l})$

$g$ 是自适应门控标量。直觉：解码器的 query 除了看原来的场景特征 $s_l`，再看一眼"VLM 理解到的东西"$\tilde{h}$，$g$ 决定看多重。**VLM 不输出轨迹、不输出文本决策，只输出一个向量**——这是"参谋"定位最彻底的实现：连自然语言中间件都省了，直接 hidden state 注入，延迟和解析风险都最小。

## CAI-Gate：学人类司机"复杂才抬头"

3.3 节的 CAI-Gate 是全文命名最多的模块，机制其实简单：把场景复杂度分 5 级，每级对应一个 VLM 推理间隔（setting1: [10,20,40,60,90] 步……setting3: [40,60,90,120,160] 步）。两个版本：

- **learning-based**：EfficientNet-B0 做序回归分类器。训练标签是 **Gemini 给 7,503 张图打的复杂度分**（70% 训/30% 测）。注意这个标签链：Gemini 的主观打分 → 轻量分类器拟合 → 门控决策。标签质量完全取决于 Gemini 的 prompt，论文没公开 prompt。
- **rule-based**：数周围车/行人、车道数、自车速度加速度、距路口距离，加权成复杂度。附录有细节，正文没展开。

表 4 的数字是全文最值得细读的：

| | 分数 | 平均间隔 |
|---|---|---|
| GameFormer 基线 | 76.22 | – |
| fixed interval 20 | 76.17 | 20 |
| fixed interval 60 | 76.16 | 60 |
| learning setting1 | **76.50** | 28.79 |
| learning setting3 | 76.16 | **91.00** |
| 每步都问（Ours） | 76.54 | 1 |

三个观察。第一，**自适应的涨分效应很薄**：最好的 setting1（76.50）只比固定间隔 20（76.17）高 0.33 分，比基线（76.22）高 0.28 分。第二，**VLM 指导的增益很快饱和**：每步都问（76.54）和 91 步问一次（76.16）只差 0.38 分——VLM 的 hidden state 注入一次管很久，频繁问是浪费。第三，所以 CAI-Gate 的真正价值是**省算力**不是涨分：91 步一问 ≈ 每步都问的分数，VLM 调用量降到 1/91。

但"省了多少"论文没给绝对数字——VLM 单次推理在什么硬件上要多久？省 90 次调用 = 省多少秒？没有。这是个缺口：门控的工程价值需要"VLM 延迟 × 调用次数"才能量化，论文只给了后半截。

## 数据集与训练：DriveVQA 5 万条，ReasoningVQA 只有 1099 条

两个自建数据集（都基于 nuPlan + GPT-4 生成）：

- **DriveVQA（49,673 条）**：指令/轨迹/控制信号的问答，规则生成（自车状态+历史/未来轨迹+多视角图，按随机排列组合拼 QA）。教 VLM"开车的话怎么说"。
- **ReasoningVQA（1,099 条）**：场景理解+推理链，规则转文本 + GPT-4 生成"决策+详细理由"。教 VLM"按交规想"。

训练两阶段：预训练两轮 LoRA（R=8, alpha=32，先 DriveVQA 再 ReasoningVQA+少量 DriveVQA）→ 微调 10,000 条 nuPlan 样本（类别分布与 trainval 一致）+ 实时规划器 loss（$L = L_{plan} + L_{aux}$，aux 是速度/加速度/红绿灯/邻车道/变道预测，借自 AsyncDriver）。

表 5：无预训练 CLS_NR 74.42/CLS_R 65.53 → +DriveVQA 74.31/66.52 → +双数据集 76.35/66.66。DriveVQA 单加在非反应场景还**掉了 0.11 分**（74.42→74.31），双加才涨——说明指令微调本身不直接转成规划分，推理数据（ReasoningVQA）才是涨分的主力，尽管它只有 1099 条。

## 表 1/2/3：涨分是真的，但要放在"Hard20"的语境里读

评测集是自建的 **Hard20**：每类场景随机抽 100 个，用 PDM（nuPlan 2023 冠军）跑，取最差的 20 个——14 类 × 20 = 280 个长尾难例。注意：**这是在"冠军都翻车"的子集上比**，分数天然低，分差也容易被放大。

开环（表 1）：Ours(PlanTF) **79.12** vs PlanTF 78.86（+0.26）；Ours(GameFormer) 76.54 vs 76.22（+0.32）。涨了，但 0.3 分的量级——280 个场景上的平均分，统计显著性未知（无误差棒）。

闭环非反应（表 2）：Ours(GameFormer) **76.35** vs DTPP 75.09（+1.26，+1.68%）；闭环反应（表 3）：**66.66** vs GameFormer 64.51（+2.15，+3.33%）。**增益主要来自安全项**：Coll 85.18→89.33、TTC 76.28→79.05（表 2）；表 3 Coll 72.53→76.88、TTC 66.40→70.36。VLM 的贡献是"少撞"，不是"开得快"（Prog 90.27→84.90 反而掉了——更保守了）。

**最诚实的一行：AsyncDriver 在 GameFormer 上开环 75.24 < 76.22。** 加了 LLM 指导，分数反而比原版低。作者没有藏这个数字（表 1 原样列出），它说明：**LLM/VLM 指导不是无脑增益**——AsyncDriver 吃压缩感知输入，在 GameFormer 上水土不服。这也是 VLMPlanner 存在的理由：输入的信息量（原图 vs 压缩感知）决定了 VLM 是帮忙还是添乱。

## 图 3 定性：两个"原图救场"的案例

(a) 行人过斑马线：前视左视角图像里行人已经迈上斑马线，AsyncDriver（吃压缩感知）没检出、直接开过去撞了；VLMPlanner 从原图看到行人，原地等到人过完。(b) 全红灯：前视图像里所有方向红灯，AsyncDriver 没识别、闯灯撞前车；VLMPlanner 等灯。这两个案例是"原图细节 > 压缩感知"论点的存在性证明——**感知漏检的长尾，VLM 用原图补上了**。

## 怀疑式阅读：四个不舒服的地方

**第一，导航指令的数据泄漏嫌疑。** 3.2 原话：训练时导航指令"直接来自自车未来轨迹的 GT"（转成 "Go straight for 110.9m" 这种文本），推理时才从地图生成。训练时指令里**编码了未来 8 秒的真实去向**——模型完全可以学会"读指令"而不是"看图做规划"。DriveVQA 预训练（49,673 条，全带这种指令）和微调都在这个泄漏下进行。开环 +0.26 分里有多少是"指令泄漏"贡献的？论文没做"推理时指令 vs 训练时指令"的消融。**这是全文最大的方法论疑点**，审稿人应该问。

**第二，"闭环"是 NavSim 式的伪闭环。** 4.1 原话：nuPlan 闭环只给首帧图像，所以"8 秒只测首帧、预测完一直执行"。这本质是**单次开环 rollout**，不是每步重规划的真闭环。NavSim 证明过它和真闭环"高度一致"，但那是 NavSim 的结论，在 Hard20 长尾子集上是否成立未知。表 2/3 的"闭环"二字要打引号读。

**第三，提升幅度与统计显著性。** 开环 +0.26/+0.32、闭环 +1.26/+2.15，没有种子、没有误差棒、没有显著性检验。在 280 个场景上，2 分的差距可能是 3–4 个场景的翻转。结论"state-of-the-art"在统计上是薄的。

**第四，无代码。** "Code will be available"——截至 2026-10-11 未找到。3D-aware 模块、CAI-Gate 的 rule-based 细节、Hard20 构建脚本都不可复现。复现者只能按论文描述自己实现。

公道话：AsyncDriver 掉分的数字敢原样列出、CAI-Gate 涨分薄如实呈现（没吹成"自适应大幅提升"）、Limitation 虽短但承认了延迟问题——写作上不藏拙。双规划器实现（GameFormer/PlanTF 都涨）证明了框架的通用性，这是加分项。

## 与 RAMP 的血缘 / 划界

**血缘（可借鉴的三处）：**

1. **CAI-Gate 是 RAMP 场景驱动动态旁路的直接先例。** "按场景复杂度动态调整重型模块（VLM）的调用频率"——这正是 RAMP 时延优化里"场景驱动动态模块旁路"的思想。VLMPlanner 的表 4（91 步一问 ≈ 每步都问）是这条设计线的定量证据，related work 里可并置引用，互相印证。
2. **Adaptive Injection 的接口范本。** VLM hidden state → FeatureAdapter → 注入规划器解码器（式 7）。RAMP 里"世界模型中间分布复用"也需要一个"重型模块输出 → 规划器"的注入接口——VLMPlanner 的 $g$ 门控注入是现成的接口模式参考。
3. **"VLM 只看压缩感知丢失的东西"的分工思想。** VLMPlanner 让 VLM 专注原图细节、规划器专注几何——分工带来效率。RAMP 的"LLM 调度器只做离散选择、规划器做连续优化"是同一分工哲学的另一个实例。

**划界（本质不同的四处）：**

1. **指导 vs 调度。** VLMPlanner 的 VLM 是"参谋"（输出 hidden state 注入单个规划器）；RAMP 的 LLM 是"调度官"（在多个异构规划器之间做选择）。前者是单规划器增强，后者是多规划器编排——问题设定不同，VLMPlanner 不是 RAMP 的竞品，是"VLM 进规划"的另一条支线。
2. **无世界模型、无记忆。** VLM 看的是当前帧原图，没有未来预测、没有历史经验库。RAMP 的两个核心创新在这里无对应物。
3. **评测是 nuPlan（开环 + 伪闭环），无 Bench2Drive。** 闭环部分实际是首帧单次 rollout，不能作为 RAMP 闭环对标的 baseline。引用其数字时必须加这个限定。
4. **门控信号不同。** CAI-Gate 的复杂度是"场景 crowded 程度"（车数/行人数/车道数），RAMP 的旁路/调度信号是**风险**——前者是静态场景属性，后者是动态风险估计。RAMP 的信号更细，但也更难标定；VLMPlanner 的做法是"风险代理"的廉价版，可在 RAMP 论文里作为对比基线提及。

**一句话定位**：127 是"VLM 指导规划器"支线上把工程做细的一篇——原图输入的论点成立，CAI-Gate 的"省算力"证据实在（涨分就别指望了）；对 RAMP 的价值在**时延优化侧**（动态门控的先例+定量证据），不在调度主线。注意它的导航指令泄漏疑点，引用其开环数字时要打折。
