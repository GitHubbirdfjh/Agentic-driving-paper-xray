**先说这篇论文真正回答的问题**：LLM 推理慢（13B 参数量级，单次前向几百毫秒），车载规划器必须快（10Hz 回路内仿真，每步留给规划的时间是百毫秒级）。2024 年上半年，LLM 驾驶规划的主流做法是让 LLM 当决策主体——每步都做一次完整 LLM 推理（LMDrive），或者让 LLM 直接输出轨迹点坐标（DriveGPT4）。AsyncDriver 的作者换了一个思路：**把 LLM 从驾驶座请到参谋席**。LLM 不输出轨迹，只输出一个高层指令特征向量；真正的轨迹回归仍由原来的实时规划器（GameFormer 解码器）完成；两者推理频率解耦，LLM 可以几十帧才想一次。

## LLM 慢、规划器要快：这个矛盾的真实形状

论文图 1 把三类框架并排摆出来，值得一个一个看，因为作者的全部设计都是对这张图的回应。

**(a) 实时规划器**：输入向量化地图，编码器提特征，解码器直接回归轨迹。快，但有两个结构性毛病。第一，纯数据驱动，长尾场景一到就退化——训练集里没见过的路口，网络只能靠插值猜。第二，可控性低：你没法用一句话告诉它"前面路口右转后靠边停"，它的输入里没有语言通道。

**(b) LLM 规划器**：把场景描述翻译成文字喂给 LLM，LLM 用文字输出决策。论文点了三个具体的技术卡点，不是泛泛的"太慢了"：

1. **token 长度装不下场景**。一个复杂路口的向量化信息（自车 + 20 个周边智能体 × 20 帧历史 + 全局地图）展开成文字，轻松超出上下文窗口；压缩描述又会丢掉精确几何信息。这是结构性矛盾：驾驶需要的恰恰是精确的相对位置和速度，而语言天生是粗粒度的。
2. **LLM 不擅长输出浮点数轨迹**。两种做法都有代价：输出"右转"这类高层命令再转成控制信号，翻译过程丢精度；直接输出 `[(0.12,1.14), (0.43,2.18), …]` 这样的 waypoint 坐标，LLM 的 next-token 训练目标根本不是为连续数值回归设计的，数值误差会累积。
3. **每步一次完整 LLM 推理**。LMDrive 这类工作每规划步都跑全量 LLM 前向 + 自回归解码，延迟直接写在关键路径上，车载部署不现实。

**(c) AsyncDriver**：保留 (a) 的整条实时通路，在旁边挂一个低频的 LLM，只负责产出"场景关联指令特征"注入解码器。

这里有一个被推翻的默认假设，值得明确写出来：**当时默认的假设是"LLM 越强，越应该让它直接做决策"**——LLM 当司机，规划器当执行器。作者的起点是反过来的：LLM 当参谋，规划器仍是司机。这个反转是整篇论文的赌注，后面所有设计（特征而非轨迹、门控注入、异步间隔）都是它的推论。

**作者的底牌是什么**（推断，依据在下面各节展开）：第一，GameFormer 的解码器结构原样保留、权重直接加载，训练起点就是一个在 nuPlan 上 62.05 分的 SOTA 级实时规划器——性能下限是锁死的，做不坏；第二，"高层指令在短时间窗口内几乎不变"是一个可以直接用实验验证的经验事实（图 3 的异步间隔曲线）；第三，表 3 的对照实验设计得很干净，能证明提升来自预训练知识而非参数量。这三张牌里最硬的是第一张：**一个以 SOTA 规划器为起点的改进，天然不怕退化**，门控零初始化（后文细讲）就是这张牌的技术表达。

## 作者的赌注：高层指令在几十帧里几乎不变

异步解耦能成立，当且仅当一个经验假设成立：**LLM 输出的高层指令特征，在短时间窗口内变化很慢**，慢到可以缓存复用。

想清楚这个假设在说什么。论文里的 routing instruction 长这样（图 2 与附录图 S3 的实例）："Go straight in 9.01 m. Turn right in 119.93 m."——"直行 9.01 米，前方 119.93 米处右转"。这是一句**战略级**描述：未来 8 秒的大致意图。自车以 10m/s 行驶，1 秒走 10 米，"119.93 米处右转"这句话在接下来几十帧里都是对的——右转点不会因为自车挪了 3 米就变成"直行"。变化的是战术细节（旁边那辆车逼近了 0.5 米），而战术细节本来就由每帧运行的实时规划器处理。

所以分工是：**LLM 管战略（慢变量），规划器管战术（快变量）**。战略慢变量缓存复用，战术快变量每帧重算。这个分工成立，异步才有意义；不成立，缓存的旧特征就是过期误导。

论文 4.3 节和图 3 就是拿实验给这个假设背书：LLM 推理间隔从每帧一次拉到每 149 帧一次（一个场景只想一次），分数几乎不掉，仍比 GameFormer 高 1 个点以上。注意这个实验的逻辑顺序——**先有假设，后有曲线**，曲线是假设的证据，不是设计的起点。怀疑式审读一节会回头挑这条曲线的毛病。

## 指令特征提取模块：向量化场景是怎么喂进 Llama2 的

Scene-Associated Instruction Feature Extraction Module 是 LLM 那一侧的全部。它做三件事：多模态输入、LLM 推理、对齐辅助（只训练用）。

**多模态输入**。每个规划步，从仿真环境拿到向量化场景：自车 + 20 个周边智能体的历史轨迹与状态（20 帧），加上以自车为中心的全局地图数据——做法沿用 GameFormer，**所有向量都是以自车为原点的相对坐标**。这组向量走 Vector Map Encoder + Map Adapter 变成 map embeddings；与此同时，系统提示词 + 一串 routing instructions 走分词变成 language embeddings。两组 embedding 拼在一起喂进 **Llama2-13B**（LoRA 微调，R=8，α=32，即秩为 8 的低秩适配器，缩放系数 32/8=4）。

关键细节在附录图 S3 的 prompt 模板里：模板中有一个 `<map>` 占位 token，输入时被替换成向量化场景的 token 序列。也就是说，**地图不是被翻译成文字的，而是作为连续向量直接插进 LLM 的 token 流**——这正是为了绕开引言里卡点 1（文字装不下精确几何）。LLM 看到的序列是：`[系统提示词 tokens] [routing instruction tokens] [<map> 展开后的场景 tokens]`，然后输出全部 $N_h$ 个位置的最后一层隐藏状态：

$$h = \{h_0, h_1, \dots, h_{N_h-1}\} \in \mathbb{R}^{N_h \times D_{llm}}$$

其中 $D_{llm}=5120$（Llama2-13B 的隐藏维度；论文没明说，但表 3 用 5120 维 transformer 做对照实验，佐证了这个数——此为推断）。

**对齐辅助模块（Alignment Assistance Module）**。五个独立的 2 层 MLP 预测头，接在 LLM 隐藏特征后面，做五个多任务预测，**只在训练时用，推理时整个扔掉**：

| 预测头 | 目标 | 损失 |
|---|---|---|
| 自车状态 | 未来速度 $(v_x,v_y)$ 与加速度 $(a_x,a_y)$，$\tilde{x}_{va}\in\mathbb{R}^4$ | L1 回归 |
| 相邻车道 | 左右两侧相邻车道是否存在，$\tilde{x}_{adj}\in\mathbb{R}^2$ | 二元交叉熵 |
| 交通灯 | 当前车道相关信号灯状态（4 类），$\tilde{x}_{traf}\in\mathbb{R}^4$ | 交叉熵 |
| 变道需求 | 未来轨迹是否需要变道，$\tilde{x}_{chg}\in\mathbb{R}^1$ | 二元交叉熵 |
| 速度决策 | 加速 / 减速 / 保持，$\tilde{x}_{dec}\in\mathbb{R}^3$ | 交叉熵 |

这五个头的作用是给 LLM 的隐藏特征提供**向量化监督信号**：光靠语言建模目标，LLM 的隐藏状态没有压力去精确编码"左边有没有车道""灯是什么颜色"这类几何/语义事实；五个头把梯度直接打进 LLM 特征，逼它把场景信息和指令语义对齐到同一个表示里。推理时扔掉，所以是零成本的训练期脚手架——后面"可迁移想法"会单拎出来讲这一招。

## 公式(1)：凭什么是最后一个 token 的隐藏状态

$$\hat{h} = \text{Linear}(h_{-1}) \tag{1}$$

$h_{-1}$ 是 LLM 最后一层、**最后一个输入 token** 位置的隐藏向量（维度 $D_{llm}=5120$），Linear 把它投影到规划器解码器的特征维度 $C$，得到 $\hat{h}$——这就是所谓的"场景关联指令特征"（scene-associated instruction feature），一个向量，整篇论文的信息瓶颈。

为什么是最后一个 token？自回归 LLM 里，每个位置的隐藏状态只能看到它之前的 token（因果掩码）。最后一个位置是唯一一个**看过全部输入**的位置：系统提示词、routing instructions、`<map>` 展开的场景 tokens，它全看过。它的隐藏状态因此是"读完整个 prompt 之后模型脑子里的总结"。这是一个标准做法（很多 LLM 特征提取都取 last-token），但在这里有一个额外的含义：**信息被有意压缩成一个向量**。LLM 对场景的全部理解、对指令的全部推理，最后只允许通过这一个 $C$ 维向量影响规划器。这既是优点（解耦干净、缓存便宜——每帧复用只需存一个向量），也是风险（瓶颈太窄会不会丢信息？论文没有做多 token vs 单 token 的对照，这是个缺口）。

## 公式(2)：Adaptive Injection Block 的两路注意力，和那个从零开始的门

这是全篇的承重设计。作者把 GameFormer 的 transformer 解码器层改造成 Adaptive Injection Block：第 $l$ 层的更新公式是

$$s^{l+1} = \underbrace{g \cdot \text{softmax}\!\left(\frac{QK_{\hat{h}}^T}{\sqrt{C}}\right) V_{\hat{h}}}_{\text{新增：指令注入}} + \underbrace{\text{softmax}\!\left(\frac{QK_{s^{l}}^T}{\sqrt{C}}\right) V_{s^{l}}}_{\text{原来：场景注意力}} \tag{2}$$

符号逐个落实（形状以上文为准，$C$ 为解码器特征维度，论文未给具体数值，标未确认）：

- $s^l$：第 $l$ 层解码器的场景特征序列（query 的来源，也是被更新的对象）；
- $Q$：**原来解码器层算出来的 query**，计算方式和 GameFormer 完全一样，没有动；
- $K_{s^l}, V_{s^l}$：原来解码器层的 key/value，来自场景特征——第二项就是 GameFormer 本来的自注意力/交叉注意力，一字未改；
- $K_{\hat{h}}, V_{\hat{h}}$：由指令特征 $\hat{h}$ 线性投影得到的 key/value——第一项是新增的，同一个 $Q$ 去"查"指令特征；
- $g$：**可学习的标量门控，初始化为 0**。

**几何直觉**：想象解码器的每个 query 是一个"问题"（比如"我左前方那个 query 槽位想知道该往哪走"）。原来它只能查场景这本账（第二项）；现在它同时查指令这本小抄（第一项），两本账的答案按 $g$ 加权相加。$g$ 是一只水龙头：拧开多大，指令特征就流进多少。

**$g$ 初始化为 0 是整篇论文最聪明的一笔工程选择**。训练开始时第一项恒为零，Adaptive Injection Block **数学上恒等于原来的 GameFormer 解码器层**——预训练好的 GameFormer 权重可以直接加载，模型第一步的输出就是 GameFormer 的输出，性能下限锁死在 62.05 分。训练过程中 $g$ 慢慢长大，模型逐渐学会"在哪些场景下听指令的"。这是一种**残差式的能力接入**：新能力以"不改变旧行为"为起点接入，而不是一上来就把旧行为搅乱再重新学。消融表里 "+Ada" 带来 +0.83 分（62.01→62.84），说明这只水龙头确实拧开了一点有用的流量。

**一个用手算的小例子**（数字为示意，维度按 $C=4$ 缩小，真实 $C$ 未确认）：

取解码器某层的一个 query $q = [0.5, -0.2, 0.8, 0.1]$。指令特征 $\hat{h}$ 投影后得到**单个** key $k_{\hat{h}} = [0.3, 0.9, -0.4, 0.2]$ 和单个 value $v_{\hat{h}} = [0.1, 0.2, -0.3, 0.4]$。

先算点积：$q \cdot k_{\hat{h}} = 0.5{\times}0.3 + (-0.2){\times}0.9 + 0.8{\times}(-0.4) + 0.1{\times}0.2 = 0.15 - 0.18 - 0.32 + 0.02 = -0.33$。除以 $\sqrt{4}=2$ 得 $-0.165$。

然后 softmax——**但只有一个 key**。单个元素的 softmax 恒等于 1，不管输入是什么。所以第一项 $= g \cdot 1 \cdot v_{\hat{h}} = g \cdot [0.1, 0.2, -0.3, 0.4]$。

这个小算例暴露了一个论文没有明说的事实：**因为指令特征只有一个向量，这里的"交叉注意力"数学上退化为一个门控加性偏置**——softmax 和 $\sqrt{C}$ 缩放在单 key 情况下不起任何作用（softmax 输出恒为 1，除法不改变它）。公式写成注意力形式，是为了保留扩展到多 token 指令特征的可能性，但在这篇论文的实现里，它就是 $g$ 乘上一个由 LLM 特征算出的向量，加到原来的注意力输出上。训练初期 $g=0$，加的是零向量；训练后期比如 $g=0.3$，加的是 $[0.03, 0.06, -0.09, 0.12]$ 这样一个与场景无关、只与指令和场景整体理解有关的偏移。

这个观察不是否定设计——加性门控注入简单、稳定、易训练——而是说：**读者不要被"交叉注意力"的字面迷惑，以为 query 在多个指令 token 之间做了选择；这里没有选择，只有一条可调节流量的指令通道**。如果你想改进这篇论文，第一个自然的尝试就是把 $\hat{h}$ 从单个向量换成多个 token 的特征序列（比如把 routing instruction 的每个子句编码成独立 token），让 softmax 真正有东西可选。

## 训练数据三段：Planning-QA、Reasoning1K 与 18 万帧微调

论文的训练分三个阶段，数据全部自造。附录 A 把模板贴得很全，这是论文可复现性做得好的地方。

**第一段：Planning-QA（预训练，语言 QA）**。作者先用 zero-shot 测了 Llama2-13B，发现它交通规则懂不少，但**数学不行**——给它 waypoints 和加速度，它算不对两者是否一致。于是用规则方法从 nuPlan 日志批量生成 QA，把"高级指令—控制量—轨迹点"三层表示之间的换算关系灌进去。六种题型（附录图 S1）：

- Q1：给定 waypoints 和一条高级指令（"右转 9.402 米，途中减速"），判断是否一致，不一致则纠正；
- Q2：给定 waypoints、初速度、加速时间，验算加速度数值是否匹配；
- Q3：给定车道中心线、初速度、加速度，推未来 0.5 秒的 waypoints；
- Q4：给定初速度和减速度，判断 3 秒内能否停住；
- Q5：给定 waypoints、车道线、初速度加速度，判断一致性并反推加速度/行驶时间；
- Q6：给定初速度、加速度、中心线，反推应有的高级指令，并与给定指令比对。

每道题都有正例和反例答案。本质上是在教 LLM：**文字指令和数字轨迹之间是同一件事的两种说法**，看到 "decelerate" 要能对应上 waypoint 间距在缩小。

**第二段：Reasoning1K（预训练，GPT-4 生成的推理数据）**。1000 条样本，每条给场景描述（含自车状态、车道、红绿灯、他车）、交通规则、实时规划器给出的"锚定轨迹"，要求输出修正后的轨迹 + 决策 + 逐步思考过程。附录图 S2 的例子很具体：输入轨迹偏离车道中心，目标输出是"保持 X 向速度、略增 Y 向速度以回正"，并分"他车相对位置""交通规则"两条写出理由。这是把**带因果链的驾驶推理**蒸馏进 Llama2。

预训练阶段用全部 Reasoning1K + 从 Planning-QA 随机抽的 1500 条，训练 LoRA。目标是把通用 LLM 变成"懂驾驶指令语义"的专用模型。

**第三段：微调（多模态对齐，18 万帧）**。从 nuPlan 训练/验证集里按 14 种官方挑战场景类型抽 10,000 个场景，每 8 秒取一帧，得到 18 万训练帧 + 2 万验证帧（场景类型分布与 nuPlan trainval 整体一致）。每帧的语言 prompt 是固定系统提示 + 一串 routing instructions；**训练时的 routing instructions 是用规则方法从自车未来 8 秒的真值轨迹反推出来的**——"turn left / turn right / go straight / stop" 四类，配距离信息（stop 只在 8 秒内实际行驶距离不足 0.5 米时用）。评测（仿真）时没有真值，改用 hand-crafted 的寻路算法从当前观测找一条最长路径生成指令。

这里埋着一个后面要审的点：**训练时 LLM 见到的指令是"开卷"的**（由未来真值生成，天然正确且与场景完美对应），评测时的指令是启发式算法生成的，质量和分布都不同。指令通道的鲁棒性——指令错了/含糊了规划器会怎样——论文没有测量。

## 损失函数：每一项在罚什么，为什么没有权重系数

微调阶段总损失是两项直接相加：

$$L = L_{align} + L_{plan} \tag{5}$$

**$L_{align}$（对齐辅助损失）**，五个头各罚各的：

$$L_{align} = L_1(\tilde{x}_{va}, x_{va}) + CE(\tilde{x}_{dec}, x_{dec}) + CE(\tilde{x}_{traf}, x_{traf}) + BCE(\tilde{x}_{adj}, x_{adj}) + BCE(\tilde{x}_{chg}, x_{chg}) \tag{3}$$

逐项：自车速度加速度回归用 L1（对异常值比 L2 宽容，驾驶数据里急刹这种离群点不少）；速度决策三分类、红绿灯四分类用交叉熵；左右邻车道存在性、变道需求用二元交叉熵。注意这五个量纲完全不同——L1 回归的数值尺度（m/s 量级）和交叉熵（log 概率量级）直接相加，没有看到任何权重系数。**公式(5)里 $L_{align}$ 和 $L_{plan}$ 也是等权重相加**。整篇论文没有任何 $\lambda$。这有两种读法：一种是作者试过加权但发现不敏感（那应该写一句）；一种是根本没调，默认权重恰好 work。论文两种都没说——这是超参数诚实度上的一个缺口，后面怀疑一节会记一笔。

**$L_{plan}$（规划损失，沿用 GameFormer）**：

$$L_{plan} = \sum_t L_{NLL}(\tilde{\mu}_{m^*}^t, \tilde{\sigma}_{m^*}^t, \tilde{p}_{m^*}, \tilde{s}_t) + \sum_t L_1(\tilde{s}_t - s_t) \tag{4}$$

第一项管**周边智能体**的多模态预测：每个邻居的未来被建模成 $m$ 个高斯模态的混合（GMM），每个模态在时刻 $t$ 有均值 $\tilde{\mu}^t$、协方差 $\tilde{\sigma}^t$ 和模态概率 $\tilde{p}$。训练用 winner-takes-all：先找出与真值最对齐的那个模态 $m^*$，只对它最小化负对数似然——**不 penalize 其他模态**，这是为了保留多模态多样性（"那辆车可能直行也可能右转"，只要求其中一个模态猜对）。第二项管**自车**：预测轨迹点 $\tilde{s}_t$ 与真值 $s_t$ 的 L1 距离按时间求和。自车只用单轨迹 L1，没有 GMM——自车轨迹是规划器要输出的决策，不需要多样性。

背景补一句（GameFormer 的核心思想，用到即止）：GameFormer 把"预测他车"和"规划自车"放在同一个 transformer 解码器里交替做，认为自车规划应该建立在"他车会怎么走"的预测之上。AsyncDriver 原样继承了这套解码器结构，所以公式(4)不是这篇论文的创新，是地基。

**没说什么**：
1. 推理时间的**绝对值**没有文字交代。图上纵轴 0.2–0.8 秒量级，但图注没说明是"单个场景总耗时"还是"单帧平均耗时"，提取的文本无法辨认曲线具体取值——"接近实时水平"到底是多少毫秒，论文没给数字。

## 怀疑式审读：论文没说清楚的七件事

1. **百分比与归属的两处出入**（上节已验算）：4.6% 按表重算应为约 4.8%；drivable +3.23 分实际属于 AsyncDriver\*（带 PDM scorer 精修）而非裸 AsyncDriver（+1.08）。后者是明确的归属错误。
2. **AsyncDriver\* 的成分**：67.48 这个 SOTA 数字里，有多少来自 LLM 特征、多少来自 PDM scorer 的轨迹精修与重打分？论文披露了 scorer 的存在（README 也有 `with_pdm_scorer.sh`），算诚实；但表 4 的消融没有 "scorer" 这一行，无法分离。读者要知道：67.48 不是纯学习方法的分数，是"学习 + 规则精修"的分数——对比的 PDM-Hybrid/PDM-Closed 也是"规则 + 精修"，双方都有精修，对比本身是公平的，但不要把 67.48 理解成端到端学出来的。
3. **训练指令"开卷"**：训练时 routing instructions 由未来 8 秒真值轨迹生成——LLM 在训练时见到的指令永远正确、永远与场景精确对应；评测时指令来自 hand-crafted 寻路算法。指令噪声的鲁棒性没被测量，指令错了规划器会不会被带偏，不知道。
4. **缺失的训练细节**：batch size、epoch 数、训练总时长/GPU 天数、随机种子数、分数方差，全部没给。优化器只说了 AdamW + warm-up decay、学习率 1e-4。损失五项等权重相加，没有权重敏感性讨论。
5. **type9 的退化没被讨论**：直行过红绿灯路口大输 GameFormer 12.38 分，正文和附录都没解释。一个可能的猜测（推断）：routing instruction 在路口场景下是"Go straight in X m"这类粗粒度指令，对"红灯停/绿灯行"的时变语义覆盖不足，而 GameFormer 的纯场景特征反而对灯态更敏感。但这只是猜测，论文没给证据。
6. **门控 $g$ 的行为没被可视化**：$g$ 在各层、各场景下学到了多大的值？直道上是不是接近 0（不需要指令）、复杂路口是不是变大？这个量直接反映"模型在何时听参谋的"，是最值得画的一张图，论文没画。
7. **只做了反应式回路内评测**：nuPlan 还有非反应式（non-reactive）设置，论文只报了 reactive。以及，Hard20 是按 PDM 得分挑出来的"PDM 觉得难"的场景——对学习型方法是难是易，分布上有没有偏向，论文没讨论。

**公允的一面**：表 3 的对照设计干净，结论硬；表 4 第一行 33.91 的负结果诚实；附录把数据模板、prompt、指标公式、14 种场景定义全贴出来了，可复现性在同类论文里算好的；代码、数据、checkpoints 全公开（README 步骤具体到脚本名和参数范围）。ECCV 2024 的工程完整度是够的。

## 可迁移想法：五个可以带走的招式

**招式一：慢快解耦——高频执行器配低频思考者**。通用条件只有一条：思考者输出的东西变化得比执行频率慢。AsyncDriver 里是"战略级路由指令 vs 战术级轨迹"。这个模式不限于驾驶：任何"高层语义慢变、低层控制快变"的系统都能用——机械臂的任务规划 vs 关节伺服，对话系统的意图理解 vs token 生成。落地的关键动作是**先验证慢变假设**（像图 3 那样拉一条间隔曲线），而不是先搭系统。

**招式二：零初始化门控的残差式能力接入**。新模块以"输出恒为零"接入旧系统：$g=0$ 时系统数学上恒等于旧系统，性能下限锁死；训练只负责把门慢慢拧开。这招的适用面很广——给任何已训好的模型加新能力（新传感器、新指令通道、新记忆模块），都可以用"零门控 + 残差相加"起手，避免新模块初期的随机输出把旧行为冲垮。它本质上是残差连接思想在"能力扩展"上的应用。

**招式三：只在训练时用的辅助对齐头**。五个 MLP 头逼 LLM 特征编码可验证的场景事实，推理时整个扔掉，零成本。通用形态：**凡是推理时拿不到、但训练时有的监督信号，都可以做成训练期脚手架**。比如训练世界模型时，用真值未来状态做辅助预测头；训练记忆检索时，用人工标注的相关性做辅助排序头。代价是训练，收益是表示质量，推理账面上不体现——审稿人容易低估这一项，表 4 里它可是 +0.94 的最大单项贡献之一。

**招式四：不让 LLM 直接输出连续数值**。表 4 第一行 33.91 是花钱买来的教训：LLM 的 next-token 表示空间不适合直接回归 waypoints 坐标。通用原则：**LLM 输出离散的、高层的、语义的；连续的、精确的、物理的，交给专用解码器**。凡是看到"LLM 直接输出轨迹/关节角/控制量"的设计，先问它有没有经过一个数值解码层。

**招式四点五（附带）：指令做成规则可生成的结构化语言**。论文的 routing instruction 只有四类（左转/右转/直行/停止）加距离，是规则方法从轨迹反推的——不是自由文本。好处有三：LLM 输出方差小；训练数据可以无限生成；评测时能用启发式算法自动产生指令，形成回路内评测。代价是表达能力上限被锁死。开放式自然语言指令是这篇论文没碰、但你的课题要碰的部分，见下节。

## 与本课题的关联：把慢快解耦装进"LLM 调度多规划器"

你的课题架构是：LLM 调度多个专家规划器，执行开放式自然语言驾驶指令，配世界模型未来预测、自适应衰减情景记忆、回路内风险校验/冲突仲裁，在 Bench2Drive 上验证；时延优化里有一项"异步流水线"。AsyncDriver 与这套架构的咬合点很具体：

**1. 异步流水线的现成样板**。AsyncDriver 就是一条跑通了的异步流水线：LLM（慢，Llama2-13B + LoRA）每 $N$ 帧产出一个指令特征向量 $\hat{h}$ 并缓存；实时规划器（快，GameFormer 解码器）每帧用缓存的 $\hat{h}$ 做 Adaptive Injection。你的"LLM 调度器"可以直接套用这个节拍：调度器低频运行，输出的不是单一特征向量而是**调度决策**（选哪个专家规划器、给什么参数偏置）；各专家规划器每帧用缓存的调度结果推理。AsyncDriver 证明了"间隔拉到 149 帧仍可用"，你的调度器间隔选择就有了经验起点——但注意前提差异（下文第 4 点）。

**2. 零门控思想可以推广为"调度即加权注入"**。你的架构里，LLM 调度多规划器，一个自然的实现是：每个专家规划器输出一条候选轨迹，LLM 输出权重做加权/选择。AsyncDriver 的 $g$ 门控提示了一个更细的粒度：**调度不必是二选一的硬切换，可以是连续门控的软注入**——每个专家的特征按 LLM 给的门控值注入共享解码器，$g_i=0$ 初始化保证新专家接入时不破坏已有行为。这对"多个专家规划器"的扩展性很友好：加第 $k+1$ 个专家，就是加一路零初始化的注入通道。

**3. 世界模型可以给 LLM 做"前视"，而不是只看当前帧**。AsyncDriver 的 LLM 每 $N$ 帧看一次**当前**场景。你的架构里有世界模型未来预测——一个直接的升级是：LLM 的输入换成"当前场景 + 世界模型预测的未来 $T$ 秒场景"，让慢思考者基于未来做调度决策。战略级决策本来就应该看未来，这与"慢变量"的假设自洽：看得越远，越不需要频繁重算，异步间隔可以拉得更长。

**4. 指令有效期：AsyncDriver 没做的自适应**。AsyncDriver 用**固定间隔**，赌的是结构化短指令慢变。你的指令是**开放式自然语言**（"超过前面那辆慢车""找个地方靠边停"），语义变化速度因指令而异——"跟车"可以几十帧不想，"超车"每一帧的战术细节都不同。固定间隔在这里会出事。你的"自适应衰减情景记忆"里的衰减思想，可以直接搬到指令特征上：**给缓存的调度特征加一个有效期/置信度衰减**，场景变化剧烈（或世界模型预测到未来风险）时强制 LLM 提前重算。这就是把 AsyncDriver 的固定异步升级为**事件驱动的异步**——论文没走这一步，但图 3 的曲线证明了这条路走得通，这是你论文里可以明确写出增量的地方。

**5. 风险校验与冲突仲裁的位置**。AsyncDriver 没有显式的风险校验——它的安全来自 GameFormer 本体 + PDM scorer 精修。你的架构里有回路内风险校验/冲突仲裁，一个自然的放法是：**校验模块跑在快通路上**（每帧，轻量），对 LLM 缓存指令指导下的规划输出做安全兜底；当校验发现缓存指令与当前场景冲突（比如指令说"直行"，但前方突然出现行人），触发 LLM 提前重调度。这样"慢思考—快执行—快校验"三层节拍就齐了：AsyncDriver 只做了前两层，第三层是你的增量。

**6. 一个要小心的差异**：AsyncDriver 的评测是 nuPlan 回路内反应式，你的目标基准是 Bench2Drive。两者场景分布、指标口径不同，AsyncDriver 的数字（65.00、间隔曲线形状）不能直接搬到 Bench2Drive 上当预期——只能搬方法论。另外，AsyncDriver 训练指令"开卷"（由真值生成）的问题，在你的开放式指令设定下会更严重：自然语言指令没有真值可反推，指令数据的构造本身就是一个研究问题（人工标注 / VLM 生成 / 规则模板三选一，各有利弊）。

一句话收束：AsyncDriver 给了你**异步解耦的可行性证明 + 零门控注入的具体手法 + 三个没填的坑**（固定间隔、单向量瓶颈、无风险校验）。你的课题如果把"事件驱动的自适应异步"和"调度即门控注入"做出来，就是在这篇论文的肩膀上往前走了一步，而且是审稿人能看懂的一步。
