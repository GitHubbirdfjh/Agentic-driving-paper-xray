## "传什么"，是多车协同里最先卡住的问题

多智能体协同驾驶这条线，2022 到 2024 年的主流答案是传特征：V2VNet、V2X-ViT、CoBEVT 那一串工作，基本思路都是各车抽 BEV 特征，传给邻居车做融合。特征比传原图省带宽，又比传检测框保留更多信息，看起来是个不错的折中。LangCoop 的起点，就是指出这个折中有四个结构性毛病，论文引言里一条一条列了出来：

第一，带宽。原图、点云自不必说，特征图其实也不便宜，多车、高频、长时，就是一笔持续开销，还附带延迟和丢包风险。

第二，异构。两辆车的 backbone 不一样，抽出来的特征不在同一个空间里，对齐本身就是一篇论文的量级。这里有个值得玩味的作者动线：第一作者 Gao 在 2025 年初刚挂过一篇 STAMP（本文引用 [15]），做的正是"异构特征协同感知"——想办法让不同模型的特征能对齐。三个月后同一作者交出 LangCoop，姿态完全变了：特征对齐太累，不如换个介质，让大家都说人话。这很可能是真实的研究心路：先在旧范式里做到头，发现天花板是结构性的，才换赛道。（这是推断，依据是引用关系和时间线。）

第三，信息损失。传检测框、occupancy grid 这类"感知结果"，等于发送方先做一次有损压缩再寄：框里装不下的东西——比如"那个行人看起来犹豫了一下"——在压缩那一步就丢了，接收方永远拿不回来。

第四，传什么都不支持规划层协同。特征和检测框都是感知层的东西，到了"我打算让行，你先走"这种意图协商，现有介质没有位置放它。

四个毛病合在一起，作者的判断是：问题不在压缩算法，在介质本身。于是赌注就清楚了。

## 作者的赌注：自然语言"紧凑且富表达"，四个理由撑不撑得住

论文给出的理由有四条。第一，语言横跨机器可读和人类可读：消息人能看懂，调试、验尸、接管都方便。第二，复用视觉语言大模型这几年的能力红利：看图、推理、决策，LVLM 本来就会。第三，语言天然支持规划层、控制层的协商：传的不只是"我看到了什么"，还有"我打算做什么、为什么"。第四，可扩展：自动驾驶车、人类司机、路侧单元，只要会说话就能进这个协同网络，跟传感器配置、模型架构无关。

四条里，第一条和第四条是语言独有的，别人给不了；第二条是时代红利，2025 年任何人都能搭便车；第三条是真正的增量主张，但论文里支撑它的主要证据是一个定性例子（后文会细说）。

第一条有个极好的例证，论文引言里讲了一个 Waymo 的真实事故：一辆 Waymo 无人车在施工路段里突然停死，后车完全不知道它在想什么，交通乱成一团。传感数据再丰富，也解释不了"我为什么停"。如果车能实时说一句"我停下是因为施工标志看不清"，误会当场解除，还能让远程接管员用一句话把它指挥出来（"慢慢靠边"）。这个例子是全文最硬的一张牌：它不依赖任何模型能力，只依赖"人能读懂"。一个协同协议如果人类可读，就自动多了一条调试和兜底的通道，这是特征介质永远给不了的。

所以作者的赌注可以压缩成一句话：**用自然语言做多智能体之间的窄腰接口**，感知多样性在上层，决策多样性在下层，中间只过人话。这个赌注在直觉上成立，剩下的全部问题都是工程问题：话怎么说、怎么打包、说完怎么开车。

## M³CoT：把"看懂路况"拆成四句问话，"混合"的是模型

M³CoT 全称 Mixture Model Modular Chain-of-thought。它的第一层意思是把"理解驾驶场景"拆成四个阶段的提问，每段提示词只问一件事：

1. **Driving scene description**：整体环境理解——天气、交通、路况。对应提示词大意是"描述驾驶场景，包括天气、交通和路况"。
2. **Interactive objects description**：找出跟驾驶任务相关的交通参与者并刻画它们。"识别场景中重要的道路使用者。"
3. **Navigation goal prompting**：把下一个导航目标的相对位置告诉模型，比如"目标在你左方 0.112 米、前方 36 米"。这一步有个巧妙的视角转换：不让模型直接预测轨迹，而是先把它拧到"目标导向的规划"视角——先知道要去哪，再想怎么去。
4. **Future intent description**：让模型把打算怎么做、为什么这么做讲出来。"描述你会如何操控车辆到达目标。"

"Mixture Model"混合的不是 MoE 意义上的专家，而是**四个阶段可以用不同的 LVLM**。论文给的理由有两层。第一层是能力匹配：场景描述和对象描述主要吃视觉理解，导航目标解读和意图形成更吃逻辑推理，给每段提示词配它最需要的模型，理论上比一个通用大模型通吃四段更强。第二层是省钱：zero-shot LVLM 推理不便宜，贵的模型只用在刀刃阶段，不用为一个大而全的模型处处付费。

这里要诚实地拆一下增量。论文自己写了，M³CoT 是"在 OpenEmma [52] 的链式思考基础上扩展"——OpenEmma 是同组（Tu 组）此前的开源多模态端到端驾驶工作。所以 M³CoT 的真实构成是：OpenEmma 式的结构化 CoT，加上"按阶段换模型"的调度自由度，再把它用到"生成通信消息"这个新位置上。单拎出来看，每一块都不算大；但合在一起，它恰好回答了"话怎么说"这个问题。

然后是怀疑的部分。Table 6 测了两种混合配置：Exp6.A 用 Gemini-2.0 做场景/对象描述、Llama-3.2 做导航目标/意图描述、GPT-4o-mini 生成驾驶信号；Exp6.B 把前两段换成 Qwen-2.5。结果是，两个混合配置都没跑赢纯 GPT-4o-mini（一辆车 DS 31.4/35.2 vs 33.1，另一辆 37.2/42.1 vs 48.8）。论文的措辞也退了一步，只说混合方案"有竞争力"，真正的卖点是 Gemini-2.0 和 Llama-3.2 的 API 更便宜。也就是说，"混合"这张牌目前是**省钱卡，不是性能卡**，"mixture of models  potentially outperforms monolithic"还停留在"理论上"三个字里。读者要分清：论文证明了"可以混"，没证明"混了更强"。

## LangPack：一封 1.8KB 的电报里，到底装了什么

M³CoT 四段话说完，LangPack 负责打包。Table 1 给出的包结构分五块：**Agent Metadata**（位置、速度、加速度等元数据）→ **Scene Description** → **Objects Description** → **Navigation Goal** → **Intent Description**。整包小于 2KB。

附录里有两个真实的包，可以看作"电报原文"。我用自己的话转述其中一封（Agent 1 发给 Agent 0，1.5KB）：先报家门——坐标、当前速度 4.5 m/s；场景——晴天白天，多车道双向路，车流中等，路边有树，郊区公路；对象三个——同向摩托车（中间车道、中距离、直行）、黑色 SUV（右车道、很近、静止、像在等并线）、红色慢车（左车道、偏中间、可能要转向）；目标——右偏 0.15 米、前方 32 米；意图四条——观察环境、控速、微调方向对准目标、前车太近则减速保持距离。

接收端收到包之后做两件事，论文各用一句话带过，但工程上都不轻：**坐标变换**（把对方描述里的"右车道"那辆车，落到我自己的坐标系里）和**时间对齐**（对方看到的是半秒前的世界）。然后把处理过的消息和自车感知拼在一起，喂给 LVLM 做决策。

这里藏着一个论文没展开的风险点：语言消息的指代是脆弱的。"右车道那辆黑 SUV"——如果两车的相对位姿估计偏了 2 米，接收方可能把这句话安到错的车身上。传特征的范式里，位姿误差的影响是连续的、可建模的；传语言的范式里，指代一旦错位，就是离散的错误，而且错得"言之凿凿"。论文没有讨论位姿误差对语言消息可信度的影响，这是后续工作必须补的一块。

## 从一句话到方向盘：三种"驾驶信号"，为什么离散轨迹点输得最惨

话说完要开车。论文给了三种把语言推理翻译成动作的写法：**Discrete Trajectory**（输出未来 n 秒的一串离散航点坐标）、**Continuous Trajectory**（输出速度和转弯曲率这类连续参数）、**Direct Control Signal**（直接输出油门、刹车、转向）。

Table 2 的结果很干脆：离散航点 DS 只有 5.0 / 1.3（两辆车），基本等于不会开；连续轨迹 33.1 / 48.8；直接控制 33.7 / 18.1。作者的解释是：zero-shot LVLM 不擅长输出平滑且动力学可行的离散航点。

这个失败值得多停一会儿，因为它讲出了一个一般性道理。LVLM 的输出是 token，token 没有度量概念。让它写一串 "(3.42, 1.18), (6.91, 2.05)……" 这种精确到小数点后两位的坐标，等于逼它做它没被训练过的连续数值回归——小数点后一位抖一下，整条轨迹就歪了。而"保持 5 m/s、曲率 0.02"是一组语义参数，落在语言模型的舒适区里：它不需要精确，它只需要"大概对"，下游的控制器会把参数变成平滑的动作。直接控制信号同理，油门刹车转向都是有界、有语义的量。

所以连续轨迹和直接控制赢，不是因为它们"更高级"，而是因为它们的动作空间**更像语言**。这是一个可以带走的结论：让 LVLM 做控制，优先选参数化、语义化的动作空间，别让它写坐标点序列。作者最后选连续轨迹做默认配置，理由是它在两辆车上最均衡（Vehicle 2 最好，Vehicle 1 的 33.1 只比直接控制的 33.7 低一点）。

顺带说一句，离散航点这个负面结果是论文里最诚实的数据之一。很多工作会把这种"试了但不行"的配置藏进附录，作者把它摆在 Table 2 还给了机制解释，加分。

## 遮挡路口：同一场景下，传图像和传一句话，接收方各看到了什么

构造一个场景。A 车沿主路接近一个无信号灯路口，右前方一排建筑物把右侧支路挡得严严实实；B 车停在路口另一侧，正好能看到被建筑物挡住的那条支路——上面有个行人正从右往左穿行。A 看不见行人，B 看得见。两车相距 80 米，在 200 米通信范围内。

**方案一：传图像。** B 把 800×600 的前视 JPEG（约 43KB）发给 A。A 的 LVLM 现在手里有两张图：自己的前视图（干净的主路、右前方一堵"墙"般的建筑物），和 B 的前视图（路口、支路、一个正在过马路的行人）。A 要回答的问题是：B 图里那个行人，在**我的**坐标系里处于什么位置、会不会进入我的行驶路线？

这一步是跨视角空间推理：从"别人相机里的像素位置"换算到"我车头前方多少米、左偏多少"。像素都在，信息论意义上什么都没丢，但接收方要从头做一次完整的视觉理解，外加一次视角变换的认知负担。而跨视角的空间换算，恰恰是 VLM 公认的弱项——它能说出"图里有个行人"，很难说准"这个行人在我前方 23 米处、2 秒后进入我的车道"。

表 4 的数字给这个推演做了注脚：Image-only 的 DS 是 15.3 / 31.3，只比不协同的 13.5 / 11.35 高一点。像素传过去了，理解没跟上。带宽花了 43.1KB，换来的主要是"我知道你那边有情况"，而不是"我知道该怎么做"。

**方案二：传 LangPack。** B 先在自己车上跑完 M³CoT，把结论写成结构化文本，大意是：对象——行人，右侧支路，正从右向左穿行，从你的视角被建筑物遮挡；意图——我正在减速让行。整包约 1.8KB。A 收到后做坐标变换，把"行人"落到自己的车辆坐标系里，得到的是**符号化的事实**（行人位置、运动方向、被遮挡状态）加上**对方的意图**（减速让行）。A 的决策模块不需要再理解一张图，直接输出：减速，准备停车让行。

论文 Figure 2 记录的就是这个模式的真实实例：CAV 1 接近路口决定减速，把 slow down 的意图发出去；CAV 2 原本的打算是继续往前走，收到消息后跟着减速。注意这里协同发生在**意图层**：两车不需要看到同一张图，甚至不需要看到同一个物体，只需要同步"接下来要发生什么"。

两种方案的对比可以压缩成一句：传图像是"把原材料寄过去，对方自己加工"；传语言是"在产地加工成半成品再寄"。省的不只是带宽，还有接收方的理解成本。代价是对称的：发送方必须先理解对了——看错了，寄出去的就是错的半成品，而接收方拿到的是"言之凿凿"的文字，比噪声像素更难起疑心。这是语言介质的结构性风险，论文没有讨论，后文第 11 节会展开。

## 96% 是怎么算出来的：分子分母都摆出来看

摘要里"带宽下降 96%"的算式是：(43.1 − 1.8) / 43.1 = 95.8%，约 96%。分母是表 4 里 Image（JPEG）行的 TB = 43.1KB，分子是 LangPack-only 行的 TB = 1.8KB。数字本身没算错，但三个口径问题要摆出来：

第一，**分母选的是最朴素的基线**。2024 年协同感知的主流基线是传特征（V2VNet、CoBEVT、Where2comm 那条线），特征压缩后本来也就几 KB 到几十 KB。论文没有和任何一个特征传输方法比过带宽，96% 是"相对传原图"，不是"相对通信效率最好的现有方法"。这个数字真实，但引用时要注明口径。

第二，**Image-only 基线弱得可疑**。它的 DS（15.3 / 31.3）只比不协同（13.5 / 11.35）高一点。论文的解释是"原始视觉数据未经处理，不是最优的车际理解结构"。但反过来问一句：图像组和语言组在提示工程上的投入对等吗？语言组有四阶段 CoT 精心伺候，图像组的接收端是怎么用那张图的，论文没细说。如果图像组只是把两张图粗暴地拼在一起喂给模型，那这个基线输得不冤，但也不能说明"图像介质不行"，只能说明"没好好用的图像不行"。

第三，**摘要把两个配置的数字拼进了一句话**。"96% 带宽下降（<2KB）"来自 LangPack-only 配置，而"DS 最高 48.8、RC 最高 90.3%"的 headline 数字来自 Image+LangPack 配置（TB = 44.9KB，一点也不省）。LangPack-only 自己的成绩是 DS 35.1 / 42.8——Vehicle 2 上比组合配置低约 12%。论文用 "competitive" 一词把两者缝在一起，读者要自己拆开看：<2KB 和最高分，不在同一个配置里。

第四，**样本量和噪声**。10 个场景、2 辆车，没有报告随机种子和方差。Vehicle 1 上 LangPack-only（35.1）反而高于 Image+LangPack（33.1）——如果组合真的严格更优，不该出现这种交叉，说明噪声不小。所有"X 比 Y 好"的结论，都要打这个折扣。

## 真正的承重墙可能是提示词：Naive 到 CoT 的一跃

Table 3 是全论文 delta 最大的一张表，值得单独拎出来。Naive prompting（直接让 LVLM 输出驾驶信号，不做结构化推理）：DS 2.7 / 0.7，基本不会开。加上标准 CoT：37.0 / 41.1。Concise CoT（每段提示词末尾加一句 "Please be very concise"）：33.1 / 48.8。

对比一下：换介质（不协同→LangPack）带来的 DS 增益约是 13.5→35.1；加结构化推理带来的增益是 2.7→37.0。**后者更大**。这意味着 LangCoop 里"语言"有两个角色要分开看：角色一是推理脚手架（M³CoT），角色二是通信介质（LangPack）。实验里两者是绑定的，但增益的大头可能来自前者。一个干净的消融应该是：传图像 + 同样的四阶段 CoT，看看到底差多少。论文没做这个消融，所以"语言作为介质到底贡献了几个点"，目前是个未确认数。

"Please be very concise" 是个便宜又有效的技巧：一句话让模型输出变短，Vehicle 2 反而拿到全场最高的 DS（48.8）。短回答逼模型抓重点，还省 token 钱、省延迟。工程上这种技巧的性价比极高。

§5 Discussion 里还有一句诚实的自白：明确告诉模型 "avoid collisions"（别撞），就能明显涨分。作者写出来是加分，但这句话反过来暴露了脆弱：驾驶常识并没有内化在模型里，全靠提示词外挂。今天靠一句话涨的分，换个场景、换个模型，可能靠另一句话丢回去。凡是把核心能力放在提示词上的系统，都要面对这个"提示词一动，性能地震"的问题。

## 换模型、混模型：语言的"模型无关"承诺，兑现了几分

Table 5 测了六个 LVLM。第一梯队是 GPT-4o（DS 41.3 / 47.7，TC 79.0 秒）、Claude-3.7（32.0 / 72.1，RC 94.1 全场最高）、GPT-4o-mini（33.1 / 48.8，默认配置）。第二梯队 Gemini-2.0、Qwen-2.5、Llama-3.2 明显弱一档。

Gemini-2.0 那行有个漂亮的反直觉数据：它跑完全程只用了 46.5 秒，全场最快，但 DS 只有 12.1 / 25.6，垫底。作者解读为激进驾驶牺牲了安全。TC 这个指标要结合 RC 一起看：跑得快不一定开得好，死得快也"省时间"。Image-only 组的 TC 只有 65.8 秒，RC 却只有 38.9 / 60.7——大概率是早早撞停了。所以读这张表时，TC 短 + DS 低 = 开得又快又莽，不是效率高。

Table 7 测异构：两辆车装不同的模型。7.A（GPT-4o-mini + Gemini-2.0）协同后 DS 59.1 / 45.3，不协同 18.2 / 12.6；7.B（GPT-4o-mini + Llama-3.2）协同后 51.9 / 12.6，不协同 16.7 / 11.5。协同确实让两组都变好了，这是语言"模型无关"最直接的证据：消息是人话，什么模型都能读。

但两处细节要抠。第一，异构实验用的是 Image+LangPack（贵的那档，约 44.9KB），不是 <2KB 的 LangPack-only。论文行文容易让人误以为便宜配置也验证了异构，实际没有。第二，7.B 里弱的那辆车（Llama-3.2）DS 只从 11.5 涨到 12.6，RC 反而从 51.0 掉到 40.1——语言消息能帮到接收方的程度，取决于接收方自己听不听得懂。异构协同的收益目前看是单向的：强者带着弱者走，弱者不一定跟得上。考虑到样本只有 10 个场景，RC 掉 11 个点也可能只是噪声，但无论如何，"异构=大家都好"的叙事在这里没有得到干净的支持。

## 论文没说、但决定这个想法生死的三件事：延迟、幻觉、场景规模

**延迟。** 一次决策要调几次 LVLM？按流程走：M³CoT 四个阶段各一次调用，加上驾驶信号生成一次，单车单步至少 5 次 LVLM 调用，用的还是 GPT-4o-mini 这类云端 API。CARLA 闭环跑在多少 Hz？论文没给任何墙钟数字。§5 用"模型效率提升很快""可以蒸馏小模型""双系统设计能缓解"一笔带过。带宽省下来了，延迟花出去了——而驾驶是实时系统，200ms 和 2s 的区别是生死线。这是全文最大的未量化项，也是任何想复用这条路线的人第一个要测的数。

**幻觉。** 整篇论文没有讨论 VLM 幻觉。VLM 看错一个行人、编一个不存在的障碍物，在传特征的范式里只是数值噪声，在传语言的范式里会变成一条"言之凿凿"的假消息，被对方车当作事实执行。Figure 2 的 slow down 之所以动人，是因为发消息的车看对了；看错了呢？论文写了"坐标变换+时间对齐"，但没写"收到消息后要不要验证"。一个没有校验机制的语言协同系统，等于把单车的感知误差广播给了全队。这是这个想法从 demo 走向量产必须回答的问题，论文完全没碰。

**场景规模。** 10 个场景、一张 Town05、2 辆车、交通参与者由 CARLA traffic manager 控制。和 Bench2Drive（上千场景、多城镇、长尾 corner cases）不是一个量级。"语言介质可行"这个结论成立，但"好到什么程度"的数字不要外推。作者自己也在 §5 承认了两处短板：没做车辆动力学（future work 写了 bicycle model + quintic polynomial 轨迹规划），V2X 扩展也只是展望。

公允地说，论文也有两处诚实加分：离散航点的负面结果摆在正文 Table 2（上一节说了）；批评 V2X-VLM 不开源，自己把代码开了（taco-group/LangCoop）。以及在 2025 年的 LVLM 驾驶论文里，坚持做闭环评测而不是开环比划，本身就是加分项。

## 可迁移想法

1. **语言是异构模块间的窄腰。** 网络世界有 IP 做窄腰，多智能体系统可以拿自然语言做窄腰。任何模块只要会读、会写人话就能接入总线，不用对齐特征空间、不用统一 backbone。这对"多个专家规划器并存"的架构是天然的总线设计。
2. **协同放在意图层，而不是感知层。** Figure 2 证明了意图消息可以直接改变对方的决策，而不需要共享一张 BEV。凡是"仲裁、协商、让行"这类问题，先问能不能在意图层用语言解决，再考虑感知层融合。
3. **结构化 CoT 是 LVLM 驾驶能力的总开关，介质切换是第二位的。** Table 3 的 delta（2.7→37.0）大于 Table 4 的 delta（13.5→35.1）。做任何 LVLM-in-the-loop 的驾驶模块，先搭"场景→对象→目标→意图"四阶段脚手架，再谈别的优化。
4. **动作空间要选"像语言"的参数化形式。** Table 2 的教训：让 LVLM 输出速度/曲率/控制量，别让它写离散航点坐标。凡是让 LLM 直接输出轨迹点的设计，先怀疑一遍。
5. **人类可读的消息是免费的可调试性。** Waymo 施工区那个例子反过来用：Bench2Drive 上每个失败 case，如果规划器能用一句话说出"我当时以为___"，失败分析的效率会完全不同。建议把"自然语言自述"做成所有规划器的标配输出，哪怕暂时不用于仲裁，光是可调试性就值回成本。
6. **反面清单（照着补功课）。** 延迟必须量化：每次决策的墙钟时间、LVLM 调用次数、闭环频率，缺一个都不要谈"实时"。幻觉必须有校验：收到的语言消息先过一致性检查再用，不能当事实直接执行。样本量和方差必须报告：10 场景、无方差的数字不要当结论引用。

## 与本课题的关联

用户的课题是：世界模型引导 + 自适应衰减情景记忆的闭环多规划器自动驾驶 Agent——LLM 调度多个专家规划器，执行开放式自然语言驾驶指令，在 Bench2Drive 上验证。LangCoop 至少在四个位置上能直接装进去：

**第一，冲突仲裁的语言形态。** 这正是任务里点出的那个想法，展开说透：让每个候选规划器在输出轨迹的同时，用 M³CoT 式的结构化模板陈述自己的"场景理解—关键对象—导航目标—意图—自评风险"；仲裁器（LLM）读 N 份陈述，在语言层比较、质询、裁决。这比"仲裁器读 N 条轨迹点序列"更符合 LLM 的能力模型——Table 2 已经证明了 LLM 读不懂离散航点，但读得懂意图。仲裁的输入不应该是 N 组坐标，而应该是 N 份"自述"。LangCoop 的 LangPack 就是这份自述的现成模板：元数据 + 场景 + 对象 + 目标 + 意图，五个空填上就能用。

**第二，开放式自然语言指令的执行。** LangCoop 证明了两个方向都走得通：场景→语言（M³CoT 看图说话），语言→控制（驾驶信号生成）。用户的"开放式自然语言驾驶指令执行"正好是这两个方向的闭环：指令进来（语言→意图），执行中各规划器持续用语言自述（场景→语言），仲裁器在语言层统一。M³CoT 的四阶段可以直接复用为指令理解的脚手架：一条开放式指令（比如"前面路口右转后靠边停"）的落地，本质上就是把"场景描述、交互对象、导航目标、未来意图"四个空填上——指令给目标，M³CoT 填其余三项，仲裁器负责发现填不上的空（比如"靠边停"但右侧有连续护栏，意图不可行）并打回。

**第三，情景记忆的条目形态。** LangPack 消息是天然的记忆条目：带时间戳、带自车位姿、结构化文本，直接进向量库，不用再设计一套记忆 schema。自适应衰减可以直接作用在"语言条目"上：越久远、越常规的场景描述权重衰减越快；带风险、带意图冲突关键词的条目衰减更慢，长期保留。检索出来的记忆条目本身就是人类可读的，组会上讲失败 case 时可以直接贴出来，这是特征向量记忆给不了的。

**第四，世界模型与仲裁器之间的窄腰。** 世界模型 rollout 出来的未来，可以用 LangPack 式的模板总结成一句话（"未来 3 秒右侧车辆将切入我车道，冲突概率高"），作为仲裁器的输入；反过来，仲裁后的意图（"减速让行"）可以作为世界模型下一轮预测的条件。语言在这里是世界模型和仲裁器之间的窄腰：世界模型不用学会输出仲裁器能直接读的张量，只要会"说话"就行。

**必须正视的代价。** 多规划器本来就要并行跑多个模型，再叠一个 LVLM 做调度/仲裁，延迟是第一风险。LangCoop 的教训有三条可以直接抄：一是 concise 提示词（"Please be very concise"这种零成本技巧，输出越短延迟越低）；二是分层用模型（关键仲裁用强模型，常规自述用便宜模型——这正是 M³CoT mixture 的省钱逻辑，Table 6 证明了便宜组合"够用"）；三是先量化再谈（LangCoop 没做的，正是课题要补的：Bench2Drive 闭环下，每次仲裁的端到端延迟、LVLM 调用次数、控制频率，三个数先摆出来，再谈架构优劣）。

补一个定位判断：LangCoop 是一篇 workshop 级别的工作，实验证据薄（10 场景、无方差、延迟未量化），但它的**问题选得准**——"传什么"是多智能体协同里真正的问题，而"语言做窄腰"是一个值得认真对待的答案。对用户课题而言，它的价值不在数字，在四个可直接复用的设计：意图层协同、自述式仲裁输入、语言条目记忆、窄腰接口。复用时把它的三块短板（延迟、幻觉校验、评测规模）当作自己实验设计的 checklist，就是一篇扎实的迁移。
